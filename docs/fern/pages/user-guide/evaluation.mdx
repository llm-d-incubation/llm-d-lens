The Evaluation creation wizard uses automatic cleanup for deployments created from
configurations; it does not offer a deployment-retention checkbox.

Once every benchmark case succeeds and the comparison report is ready, the
evaluation shows **Succeeded** and stops counting time. Final deployment cleanup
continues in the background without an evaluation progress step. A successful
result does not mean accelerators have already been released. Cleanup failures
are recorded separately and do not change successful benchmark results. Deleting
the evaluation waits for any in-flight cleanup before removing its history.

The creation wizard refreshes the selected cluster's **Available** accelerator
count every five seconds while the tab is visible, and when you return to the tab.
Counts reflect Kubernetes allocations, so a newly queued task may not reduce the
count until deployment allocates its devices. You do not need to leave and reopen
the wizard. Background refreshes preserve your configuration inputs and retain the
last successful count if a request temporarily fails.

## Hardware configuration across evaluation stages

Evaluation deployment and generated baselines resolve the same hardware profile as
the selected configuration. Baselines preserve the source accelerator request type
(DRA or an extended resource), including when a hardware family supports both.

Benchmark runs resolve hardware from the deployment and record its profile snapshot.
The profile supplies device metrics, label names, scaling and allocation attribution.
Declared device metrics are added to llm-d-benchmark monitoring settings; live
snapshots and profiling use the same registry contract. Missing telemetry remains
unavailable instead of falling back to another hardware family's metrics.

Use the **Evaluation** area to create benchmark tasks, compare deployment configurations, and review the evidence collected for each run. The operations below only mention controls that exist in the current task list, creation modal, wizard, and result screens.

Benchmark result scenario and outcome selectors retain their existing options and selection behavior while using the shared select control.

If setup reports **Unable to continue** because no valid cluster is selected or
its Software Versions must be downloaded, click **Select or manage a cluster**
in the error message to open **Clusters**. Select or prepare a ready cluster,
then return to Evaluation and choose it in the **Cluster** field.

New P/D Disaggregation evaluations default to two **Load stages**: concurrency 1
with 16 requests and concurrency 8 with 32 requests, for each token-length pair.
Use **Add concurrency stage** for a larger capacity sweep. Existing custom settings
and saved evaluations retain their configured stages.

## Workload size and execution time

New optimized-baseline and precise-prefix routing tasks default to a **Lightweight
check**: 24 measured requests per target and worker, with 512 shared input tokens,
128 unique input tokens and 64 output tokens. **Full routing workload** remains an
explicit traffic preset for longer performance evaluations. Existing saved tasks
keep their workload and manual timeout settings; retrying an old task does not
replace them with new defaults.

**Timeout mode** defaults to **Automatic (workload-based)**. Lens computes a
per-invocation budget from the configured request counts, lengths, stages and
parallel instances, with setup and safety allowances. Automatic budgets are
bounded between 15 minutes and 4 hours; workloads without a supported estimate
use a 2-hour fallback. **Manual limit** preserves your chosen hard limit and warns
when it is shorter than the estimated execution time.

The benchmark settings show an estimated time range per target, not the duration
of the entire deployment/comparison workflow. These are low-confidence estimates
based on stated throughput assumptions, not measured hardware predictions. Runtime
installation, deployment and final analysis are excluded. Repository profiles,
custom YAML, unsupported harnesses and multi-turn workloads currently show timing
as unavailable rather than inventing a completion time.

During execution, the details page shows only a compact remaining-time badge
above the benchmark result tabs. If execution outlasts the estimate, the badge
displays **Taking longer than estimated**. Terminal runs hide the badge.
Matrix points and warm-up are separate invocations, each with its own hard limit.
Rate-stage duration is the offered traffic window: queued requests still need to
finish afterward. More parallel benchmark instances multiply the request count.


## Concurrent backend instances

Evaluation execution is protected by operating-system locks under
`LENS_DATA_DIR/metadata/evaluations/locks`. Backends sharing evaluation records
must share this directory on a filesystem supporting `flock`; sharing only the
database with independent data directories is not supported by this guard.
All participating backends must run the updated code. Separate development
installations should use independent databases and data directories.

Starting another backend does not mark a live owner's benchmark interrupted or
launch the same workflow again. Locks remain held through asynchronous cleanup
and are released automatically when the owning process exits. Automatic deployment
cleanup is deferred while a benchmark still uses the deployment. A delayed duplicate
executor cannot replay a completed workflow.

Cancel, retry, and delete requests targeting work owned by another backend return
HTTP `409` before changing records or cluster resources. Send the request to the
backend executing that evaluation. Local cancellation retains ownership until its
cleanup completes. The Python control callables enforce the same ownership checks.

## Find an evaluation task

1. Open **Evaluation** from the left navigation.
2. Use the summary cards **Evaluation Tasks**, **Succeeded**, **Running**, **Queued**, **Failed**, and **Cancelled** to narrow the task list.
3. Type in **Search evaluation, workload, or harness...** to match a task by name, model, ID, mode, workload, or harness.
4. Open **Mode** to switch between **Deploy + benchmark** and **Existing endpoint** tasks.
5. Open **Workload** to filter by workload name.
6. Click **Clear Filters** to reset the current filters.
7. If needed, change **Tasks per page** and use **Previous** or **Next**.

## Create a new task from the Evaluation dashboard

1. Click **New Task**.
2. In **Create a new task**, choose the target type:
   - **Deploy configurations** to benchmark saved deployment artifacts.
   - **Use existing endpoint** to benchmark a live service without creating a deployment.
3. If you chose **Deploy configurations**, stay on the **Select** tab to pick deployment artifacts, use **View YAML** to inspect one, or click **Create configuration** if you need a new artifact first.
4. If you chose **Use existing endpoint**, choose **Deployed services** or **Enter URL**, then fill **Ready endpoint** or **Endpoint URL**.
5. Continue to **Benchmark & comparison**.
6. Pick a benchmark suite such as **Custom workload** or one of the built-in suites.
7. When the footer shows the target is ready, click **Launch evaluation**.

**Enter URL** must match a discovered deployment's service or forwarded endpoint. Arbitrary external URLs cannot be submitted through this flow. The dashboard and full wizard apply the same target validation.

## Run the full New Benchmark Task wizard

1. Open the full wizard when Prism routes you to **New Benchmark Task**.
2. In **Evaluation Setup**, enter **Task name**.
3. Under **How should this evaluation run?**, choose **Use existing endpoint** or **Design configurations**.
4. If you are benchmarking an existing service, choose **Deployed services** or **Enter URL**, then fill **Ready endpoint** or **Endpoint URL**.
5. If you are designing a deployment-backed run, fill the shared setup fields such as **Cluster**, **Model ID**, **Model Cache Storage**, **Deployment Name**, and **Deployment description**.
6. In **Configurations**, review the selected deployment artifacts. Use **Edit setup**, **Use saved configurations**, **Edit**, **Edit YAML**, or **Delete deployed configuration** only when you need to change the candidate set.
7. In **Benchmark**, configure the benchmark plan and resolve any validation messages.
8. In **Execution plan**, review the sections **Execution plan**, **Targets & execution order**, and **Performance targets**.
9. Click **Start Evaluation**.

While checking an existing endpoint, the wizard displays **Probing /v1/models…**, followed by the detected model or a probe error.

Editing a saved configuration's YAML creates a new artifact with updated checksums and edit provenance; the original artifact is preserved. This applies to both creation surfaces.

## Open task results and export evidence

1. In the task list, click **Results** on the task card.
2. On the detail page, use the section tabs **Benchmark results**, **Compare**, **Live monitoring** or **Recorded monitoring**, **Resources**, **Benchmark logs**, and **Deployments**.
3. Click **Download Report** to export the benchmark report.
4. Click **Send to Simulate & TCO** if you want to pass the benchmark data into the simulation workflow.
5. Use the refresh action with tooltip **Refresh deployment status and details** when you need a fresh status snapshot.

Active result pages refresh persisted progress every five seconds without showing the initial loading state again. Refresh pauses while the browser tab is hidden and resumes when visible; it stops when the task reaches a terminal state. Deployment readiness refresh remains an explicit action. A task that is **Stopping** is still active until cleanup finishes.

### Read guide and baseline comparisons

Matrix comparisons pair results with the same input length, output length, and concurrency. Rate comparisons pair stages with the same target rate. Missing or ambiguous load values are excluded instead of matching by row position. A valid zero measurement stays zero; a missing measurement or zero baseline does not produce a ratio. Suite throughput comparisons include only matched pairs with token counts and positive durations on both sides.

Ratios are guide divided by baseline: higher throughput ratios favor the guide, while lower latency ratios favor the guide. Older cached comparison reports are refreshed from saved evidence when results are opened; unavailable historical measurements are not invented.

## Inspect benchmark logs and deployment cases

1. Open a task’s **Results** page.
2. Click **Benchmark logs** to review **Harness pod logs**, **Benchmark output**, and **Benchmark diagnostics**.
3. Click **Deployments** to review **Deployment cases**.
4. Use the deployment filters **All**, **Failed**, **Active**, **Ready**, and **Retry history** or **Hide history**.
5. In a deployment case, click **Deploy logs** to open the deployment diagnostics.
6. Review **Deploy and Kubernetes logs**, **Kubernetes pods**, **Kubernetes events**, **Modelserver logs**, and **Latest readiness check**.

## Retry, cancel, resume, or delete evaluation-created deployments

1. Open the task’s **Results** page and go to **Deployments**.
2. If a deployment case failed, click **Retry**.
3. If a deployment case is paused, click **Resume**.
4. To stop execution, click **Cancel benchmark & deployment** for evaluation-created services, or **Cancel benchmark** for tasks that target an existing endpoint.
5. If a failed or cleaned deployment is no longer needed, click **Delete**.
6. If the run requires a private model token for the retry, fill **Hugging Face token for this retry** before clicking **Retry**.

## Remove or retry tasks from the task list

1. In the task list, use the task-card actions on the right.
2. Click **Results** to open completed evidence.
3. For a failed or cancelled task, use the action with aria-label **Retry task** and tooltip **Retry**.
4. For a running task, use the action with aria-label **Cancel task**.
5. For a terminal task, use the action with aria-label **Delete task** and confirm the deletion.

## Verify profile-driven Guide configuration

Choose a cluster with downloaded Software Versions and refresh the page. The
hardware profile selects the Guide source root; the selected llm-d checkout
supplies its model servers and Kustomization variants, including nested paths.
Root overlays display as `Default (vllm)` or `Default (vllm-rdma)` instead of `.`.
Selecting a sibling runtime variant remains stable while editing other fields.

For official sources, cache and NIC controls appear after source preparation:
CPU capacity requires a supported cache connector in the rendered containers;
NIC count requires a claim matching the profile's NIC device class. Inspect the
generated YAML and source provenance before deployment. Access-mode settings
come from `deployment.modes`; DRA uses a device claim and plugin mode uses the
declared extended resource. User-selected runtime images remain overrides.

In Evaluation results, open Resources during benchmark. Device allocation
failures display a reason even when engine metrics are available. Plugin device
metrics require kubelet-reported, profile-recognized device identities; an
exporter alone cannot establish which devices belong to the workload. Profile
file edits require restarting the development services and refreshing the page;
this is not a live JSON editor. Existing saved results are not recollected.


## Harness exits and retries

Each benchmark invocation, including warmup and individual matrix points, uses a
unique harness Pod label. Cleanup and diagnostics are scoped to that invocation,
so a failed Pod from a previous run cannot fail the next one or be confused with a
parallel evaluation. A local backend restart interrupts active evaluations;
retry the interrupted case after the services are ready.

Exit 137 indicates SIGKILL, not proof of an out-of-memory condition. Lens reports
host-memory guidance only when Kubernetes explicitly records `OOMKilled` for the
harness container. Optional Hugging Face tokenizer-file 404 responses are not
fatal when the load stages subsequently start. Some benchmark revisions warn
that `harness.extraEnvVars` is absent from their strict schema even though their
Pod template supports it; this warning is distinct from a harness exit.


New Guide configurations start with two load stages, including their default
scenario: Optimized baseline and Precise prefix-cache routing use 3 and 10
requests/s for 60 seconds each; Tiered prefix cache uses 1 and 1.5 requests/s
for 60 seconds each; P/D uses concurrency 1 / 16 requests and 8 / 32 requests.
Add stages explicitly for a larger sweep. Existing saved configurations retain
their stages; create a new configuration to use these defaults.

### Monitoring readiness and missing recorded flow

Before traffic starts, Evaluation waits for every discovered serving Pod to have
healthy Prometheus scrapes and at least two inference gauge samples. A discovered
EPP service must also have a healthy target. Creating a Monitor does not mean
Prometheus has loaded it. The preparation deadline uses the resolved benchmark
**Timeout mode / Manual limit** budget, separately from each traffic invocation.
A missing budget on a legacy run uses 600 seconds. The phase remains
`preparing-monitoring` with heartbeat updates until ready. A timeout or setup
error fails the run before traffic; check Monitor selection, Prometheus reloads
and targets, then retry. This applies equally to existing endpoints and workflows.

Recorded monitoring keeps the saved topology, resource charts and Pod resource
ranking visible even when request/token samples are missing. Missing traffic is
explained inline; it never hides CPU, device memory or network measurements, and
resource measurements are never converted into invented traffic values.

Benchmark collection measures the Prometheus clock offset before querying the
saved window. Queries use the Prometheus timeline; returned chart timestamps are
mapped back to the evaluation timeline. This prevents a clock difference between
the Lens host and the cluster from selecting a window before benchmark traffic.
Previously saved results are not automatically rewritten.
