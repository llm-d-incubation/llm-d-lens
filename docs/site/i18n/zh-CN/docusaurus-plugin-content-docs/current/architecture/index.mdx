Lens 由统一的服务器控制平面、独立的引擎 CLI 以及集群本地推理数据面共同构成：

- **Web 控制台与 Agent MCP（`apps/frontend` + `apps/backend`）**：单进程 Python FastAPI
  后端（`llm_d_lens`，默认端口 `3000`）统一提供构建后的 React 界面（`apps/frontend`，开发模式通过
  Vite `:5173` 代理）、REST API、RBAC 与审计校验、外部 Agent Task MCP 端点（`POST /api/mcp`）
  以及内部 Lens Assistant 工具目录（`/api/assistant/mcp`），并负责领域逻辑、PostgreSQL 持久化、
  制品存储、集群操作与模型服务协调。
- **独立 `llmd` CLI（`apps/lens`，`llm-d-lens-engine`）**：纯 Python 3.11+ 与 `PyYAML`
  客户端，无需任何 Lens 服务器、数据库或 Node 进程，即可在单个 Kubernetes/OpenShift 命名空间内
  直接驱动 `kubectl`/`oc`、`helm`、`git` 与 `kustomize`（`llmd` 为完整 CLI，`lens` 当前仅是
  `--version`/`--help` 存根）。
- **集群数据面**：模型推理流量不经过 Lens 服务器，而是直接发送到各集群本地的共享 llm-d
  网关（`Istio` 或 `Envoy AI Gateway`），经 `lens-authz` 鉴权后通过 `HTTPRoute / Inference Payload Processor (IPP)`
  与 `EPP` 路由到 `InferencePool` 中的 Prefill/Decode `vLLM` Pod。

## 分层

| 层 | 职责 |
| --- | --- |
| 客户端与使用方式 | **Web 控制台**（浏览器中的 `apps/frontend`）、**Agent Tools**（`opencode`、Claude Code、Cursor、Codex 调用 `POST /api/mcp`）、**独立 `llmd` CLI**（`apps/lens` 直连 Kubernetes）以及**模型客户端**（OpenAI/Anthropic SDK 或 `curl` 调用已发布网关）。 |
| 统一 Python 后端（`apps/backend`，`llm_d_lens`） | 提供 Web UI、REST API、会话/PAT 鉴权（`lens-pat-*`）、RBAC 与按集群划分权限、审计日志、`/api/mcp`（6 个 profile 共 46 个任务工具）、`/api/assistant/mcp`（内部助手与规划器目录）、领域服务、部署规划、集群操作与模型服务控制平面。 |
| 数据面 | 集群本地共享的 llm-d 网关（创建集群时可选择 `Istio` 或 `Envoy AI Gateway`）、`lens-authz`（`ext_authz`）以及按模型配置的 `HTTPRoute / Inference Payload Processor (IPP)`；每个部署拥有独立的 `InferencePool` + Endpoint Picker（`EPP`，`ext_proc`）与 `vLLM` Prefill/Decode 副本。 |
| 存储 | PostgreSQL（内置或外部）保存应用状态、RBAC、目录条目与 API 密钥；文件/制品存储保存部署包、规划方案、轨迹与基准测试日志。独立 `llmd` 在各命名空间中使用 `ConfigMap`（`lens-instance-<name>`）保存实例状态。 |

## 请求流程

1. **Web 控制台（`apps/frontend`）**：浏览器向统一 Python 后端（`llm_d_lens`）发起同源 `/api/...` 请求。
2. **Agent Tools（`POST /api/mcp`）**：外部智能体（`opencode`、Claude Code、Cursor、Codex）携带 `Authorization: Bearer lens-pat-*` 发送无状态 Streamable HTTP JSON-RPC 请求；内置 Lens Assistant 与智能体规划器则调用内部 `/api/assistant/mcp`。
3. **鉴权、RBAC 与领域执行**：统一 Python 后端解析调用方的会话或 PAT，校验路由权限（MCP 需 `mcp:tool:invoke` 或 `playground:chat:use`）与 CSRF 检查，读写 PostgreSQL 与制品存储，并在调用方可访问的集群范围内执行集群操作。
4. **独立 `llmd` CLI（`apps/lens`）**：在本地使用调用方的 kubeconfig，直接在单个命名空间内运行 `helm template`、`kustomize` 与 `kubectl`/`oc`（阶段流转 `Applying → Applied → Deleting → Removed`）。
5. **模型推理（数据面）**：模型客户端携带 `Authorization: Bearer lens-mk-*` 直接请求集群本地共享网关；`lens-authz` 校验密钥，`HTTPRoute / IPP` 匹配模型路由，`EPP` 在对应部署的 `InferencePool` 中选出目标端点。

## 访问模型

访问控制围绕拥有全局、集群或资源范围角色绑定的主体建模。全局管理员可以访问每一个集群；
按集群划分范围的维护者只能访问被授予给他们的集群。请求默认被拒绝，每个路由都映射到一个所需的权限，
并且相同的范围划分规则在 Web UI 页面、REST 端点与 `/api/mcp` 工具调用中保持一致。
对于不具备 `cluster-admin` 权限的集群接入，Lens 会执行预检并将集群级前置步骤拆分为编排管理员交接脚本。

## 部署规划

智能体部署规划是一个部署时的、检索增强的推荐步骤，而不是一个运行时调度器。
它会校验请求、收集实时的集群信息，并从容量估算、历史部署、已完成的 **Trace Replayer** 运行结果
和 **Evaluation** 基准测试结果中检索支持性证据。然后它只对通过校验的候选方案进行排序，
并保存一条推荐结果；在有人批准之前，不会部署任何东西。

设计细节参阅[智能体部署](/architecture/agentic-deployment)，了解规划器与审批流程；
参阅[规划证据与 RAG](/architecture/agentic-planning-evidence)，了解证据来源与检索方式。

## 模型服务网关

模型服务网关将集群部署发布为位于集群本地共享 llm-d 网关之后的兼容 OpenAI 与 Anthropic 的服务。
统一 Python 后端管理 **Model Services**、提供方、`lens-mk-*` 密钥与用量统计，并在创建集群时安装共享网关；
`lens-authz` 对每次请求鉴权，随后由 `HTTPRoute / IPP` 与 `EPP` 路由到对应模型服务的 `InferencePool`。
各个部署保留自己的 `InferencePool` + `EPP`，不运行额外代理。
