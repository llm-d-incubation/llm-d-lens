# 智能体部署（Agentic Deploy）证据

本文档描述智能体部署如何处理结构化与非结构化证据、当前的实现方式，以及后续计划。

## 数据与权威性

### 结构化数据

结构化数据由 `BenchmarkRecord` 组成：模型、硬件、运行时、工作负载、候选配置、实测性能指标、结果以及失败原因。记录存放在 `agentic_benchmark_records` 中，对于性能数字、失败事实和候选级别的预测具有权威性。

实时集群概览同样是结构化证据，且具有最高权威性：它决定候选方案是否满足当前的显存、GPU、CPU 缓冲区等硬约束。历史基准测试、AIC 和 AI 都不能覆盖实时资源的结论。

### 推荐链路中的公共 benchmark RAG

创建和细化推荐时，服务端会先调用 `PublicRagQueryService`，按精确模型过滤，
设置 `include_internal=false`，每路 SQL 最多选择 50 个已排序的已发布实验/配置与 series 案例，
并返回所选案例的完整测量。先校验实际请求主体的权限，
再从目标集群的实时概览获取硬件 profile 和具体加速卡型号。
profile 声明的家族标签不作为设备型号。匹配已发布的硬件名称时，仅忽略 profile 声明的
厂商/加速器修饰以及分隔符和大小写差异；保留显存大小和 PCIe/SXM 区别。
选中的已发布硬件名称作为精确过滤条件，在实验数量截断前生效。
未知或混合型号记录 `rag_hardware_unresolved`；没有匹配硬件时记录 `no_matches`，
不会回退到无硬件过滤或跨硬件搜索。`planning_evidence.details.target_hardware`
记录目标集群、profile 和探测型号，`details.query.filters.hardware` 记录实际查询名称。
细化时重新解析实时硬件。实际请求主体必须
通过现有的已认证全局 `benchmark-rag:query:read` 权限校验。无权限、无匹配和检索错误
在进度事件、`planning_evidence` 和追加式快照中分别记录；公共 RAG 不可用时继续使用原有证据规划。

公开 benchmark 的契约和服务统一位于 `llm_d_lens.agentic.public_benchmark_record`。
它作为 Agentic 子包维护，不再保留顶层兼容包；DAO 和 ORM 模型仍位于统一数据库层。
`PublicBenchmarkRecordDao` 直接继承 `BaseDao`，同时管理不可变记录与发布生命周期；
查询与备份恢复 DAO 复用这一实现，不再保留独立的 item DAO 或旧模块包装层。
Python 命名与内部 `agentic_benchmark_record` 对齐，但不改写已有记录、数据库版本、
`benchmark-rag.*` 格式契约、查询权限或原始文件归档路径。

`PlanningRequirements` 保留显式负载、延迟目标、来源和未知字段。
表单字段初始为空，占位示例和 AIC/场景默认值不是显式要求，平均输入长度不会复制成 P95。
公开查询使用实时硬件确定的具体加速卡型号；未知或混合型号明确报告，不跨硬件回退。
模型别名用于召回，不代表身份唯一或兼容性证明。

每次创建或细化计划时，规划事实与公开证据检索复用同一份请求内硬件发现快照。
新一轮细化会重新发现硬件；批准部署仍独立刷新资源校验。
历史匹配从部署运行时配置取得服务后端，未经验证的运行时版本保持未知。
TPOT 要求支持 `20 ms/token`、`0.02 s/token` 等每 token 单位，并规范化为毫秒；
这不会放宽其他指标的单位校验。

`ConfigurationCase` 保留实验、配置和 series 身份、原始测量、单位、统计口径、配置、
来源、差异与未知项。每路 SQL 先聚合完整实验，再排序并最多选取 50 个案例。
有显式负载时先比较负载匹配度，再比较同口径的较低延迟；没有显式负载时不施加负载惩罚。
延迟目标确定比较的指标和统计轴，不按距目标的距离排序。
不同统计口径不混比；Pareto 比较要求可用指标轴一致。
缺失或非正延迟保持未知；既无可比较负载也无有效延迟的案例标注为回退参考，而非低延迟证据。

导入和查询比较共用数值负载、指标与百分位的规范化规则。
`target_qps=1.5` 等数值筛选匹配等价的已存小数表示；
`latency` 与 `e2e` 都表示端到端延迟，`p99p9` 与 `p99.9` 表示同一百分位。
这些等价关系不会合并不同统计口径，也不会丢弃原始来源证据。

共享证据包在 16,000 字节序列化预算内最多保留 10 个完整案例，并保持实验排序。
历史观测可指导生成和选择，但不能证明当前 SLO 达标，也不能覆盖实时资源校验。
AIC 估算仍为独立证据类型。真实来源保留在服务端审计中；
模型侧别名和解释不能冒充已独立验证的来源使用情况。

服务端从 `run_id`、`source_path`、`source_info.file_identifier` 识别明确的技术标签，
按 provider 去重后向模型提供 `related_provider_ref`、`technique_description` 和
`mapping_basis=source_label`。名称命中即建立技术到 provider 的映射，生成器和评分器
不应再将这层关系描述为“未验证”或要求额外证明。配置等价性与性能可迁移性仍需单独验证：
技术映射不能证明部署参数相同、性能更优或当前 SLO 达标。缺少 TTFT 仍表示未知；
AIC 不适用属于中性信息，不能因此惩罚该技术。原始来源路径和匹配依据保留在服务端审计中，
不直接发送给模型。

规划仅消费 SQL 实验。公开文档采集、检索、文档包契约和搜索页面不属于此能力。
原有私有诊断搜索适配器保持独立，不受影响。

管理命令 `rebuild` 必须显式提供本地 `--snapshot`、`--manifest` 和 `--approval`。
外部 `benchmark-rag.snapshot.v1` manifest 包含完整且按路径排序的 `PinnedInventory`
（来源、快照日期、文件路径、SHA-256 和格式），以及非负整数 `expected_experiments`。
来源和路径审批仍是独立输入；激活前必须核对完整清单、文件哈希和实验数量。
业务代码不再硬编码初始快照日期、文件列表或实验总数。初始批次清单仅作为测试 fixture
保留，不包含原始数据；后续快照无需修改代码即可导入。`refresh` 仍使用审核后的 plan
以及当前发布基线。

经明确审批、使用空 inventory 且设置 `allow_empty=True` 的刷新会发布空版本，
将原有文件移出当前激活的发布。正常审批与发布 generation 校验仍然生效；
未显式允许时，空 inventory 仍会被拒绝。

部署工作区分别呈现内部 SQL 实验和公开 SQL 观测，保留失败和未知信息。
无权限、无匹配和不可用不是同一状态。批准仍需重新校验资源和模型缓存就绪状态，
并获得用户明确批准；检索不能授权部署。

### 非结构化数据

非结构化数据包括部署日志、性能剖析（profiling）轨迹、制品摘要、Guide、GitHub 内容、论文、规划快照摘要，以及来自云存储的、计划纳入的原始基准测试报告。可搜索的投影（projection）存放在 OpenSearch 中；原始制品保留在受控的文件系统中，云端报告则保留在其授权的存储位置。

云端基准测试报告的集成尚未实现。计划是先对受 ACL 控制的摘要和对象版本建立索引以便发现，然后在租户/ACL 控制下获取固定的源版本，并在使用前验证其内容哈希。需要提取模型、硬件、运行时、工作负载、拓扑、实测指标、结果和溯源信息；校验单位与必填字段；归一化为请求级别的局部 `BenchmarkRecord` 对象。字段缺失、来源不可验证，或只有估算值的报告无法成为实测记录。未提取或未校验的报告文本仅用于诊断，不能影响数值预测、失败阻断或确定性排序。合格的记录仍需经过结构化的基准测试兼容性过滤和相似度计算；仅凭检索到并不能确立性能结论。

日志、轨迹、制品和快照摘要仅用于诊断与解释。经过 ACL 过滤、版本固定的 Guide、GitHub 和论文摘要，也可以为方法适用性、兼容性约束和偏好权衡提供 AI 推荐功能。非结构化数据对 TTFT、TPOT、吞吐量、置信度或 SLO 不具有权威性；它不能直接生成或阻断候选方案，也不能改变确定性排序。

## 构建证据

### 结构化基准测试证据

服务端首先针对加速器、后端、量化方式、拓扑、单 GPU 显存以及安全的时间窗口应用粗粒度的数据库过滤。成功和失败的记录都会被保留。随后 `BenchmarkEvidenceRetriever` 计算模型、硬件、由用例推导出的工作负载、候选配置以及 SLO 性能相似度，并叠加时间/运行时衰减，从而生成两个独立的视图：

| 视图 | 内容 | 消费方 |
| --- | --- | --- |
| 原始样本 | 每个候选方案最多五条相关的 `BenchmarkRecord` 对象，包括实测指标、结果、失败原因以及 `match_similarity` | AI 评分 |
| 聚合输入 | `PerformanceScoreInput`，包含预测指标、状态、置信度、有效样本量、失败阻断情况以及引用 | 确定性规划器（Deterministic Planner） |

`match_similarity` 仅表示某条历史记录与当前目标的相关程度。它不是部署成功概率，也不是对当前性能的保证。聚合的 `confidence` 和有效样本量只属于确定性路径。

工作负载输入是可选的。历史查询画像 $q$ 只使用显式规范化负载和已验证身份。
用例默认值仅作拓扑启发，不是实测流量；不为缺失的输入 P95、输出长度、并发、请求速率、
架构、量化和运行时补造值。身份不完整不能建立精确兼容性或合格历史候选种子。

对于通过数据库硬过滤的历史记录 $r$ 和当前候选查询 $q$，检索器会计算配置/工作负载以及性能目标的相似度 $S$：

$$
S = 0.20S_{model} + 0.15S_{hardware} + 0.15S_{workload} + 0.15S_{configuration} + 0.35S_{SLO}
$$

这些权重反映的是实测历史性能对决策的价值，而不是为了拟合有限的历史样本。$S_{SLO}$ 具有最大的单项权重 $0.35$，更偏向于那些 TTFT、TPOT 和工作负载承载能力都符合当前目标的记录；下文的"最弱分量"约束可以防止配置相同但性能不合适的记录获得过高分数。模型、硬件和工作负载分别保留 $0.20$、$0.15$ 和 $0.15$ 的权重，以确保性能是在可比的环境和请求形态下被解读的。配置的权重为 $0.15$，使得 TP、副本数和优化手段能够影响排序。硬过滤已经确保了加速器、后端、量化方式、拓扑和单 GPU 显存以及时间窗口的兼容性，这里不再重复计入。

这些系数、子分量系数、时间/运行时半衰期、最小 `match_similarity`，以及失败阻断阈值目前是固定的，并与模式版本（schema version）一起记录在规划快照中。未来应该可以按租户或部署策略选择一个带版本号的 `EvidenceSimilarityPolicy`。只允许使用经过离线回放验证、服务端加入许可清单的预设；并记录策略 ID 和所有参数。禁止任意按提示词或按 UI 调整权重。新策略在成为默认策略之前，必须在历史回放中与默认策略对比排序稳定性、SLO 命中率和漏判的负面证据。

如果量化方式或模型架构不同，则 $S_{model}=0$；否则：

$$
S_{model} = 0.45S_{family} + 0.25 + 0.20e^{-0.8|\ln(p_r/p_q)|} + 0.10S_{tokenizer}
$$

对于同一模型家族，$S_{family}$ 为 $1$，否则为 $0.15$；对于相同的分词器（tokenizer），$S_{tokenizer}$ 为 $1$，否则为 $0.5$。对于 MoE，$p$ 优先取激活参数量。硬件相似度仅比较 GPU 数量：

$$
S_{hardware} = 0.7 + 0.3e^{-|\ln(g_r/g_q)|}
$$

$S_{workload}$ 使用对数比值比较平均输入长度、P95 输入长度、平均输出长度、
并发量和请求速率，并使用 $1-|x_r-x_q|$ 比较共享前缀比例和预填充比例。
$q$ 只来自显式规范化字段；缺失维度不是匹配，也不能建立精确实测适用性。
候选配置相似度为：

$$
S_{configuration} = 0.4e^{-|\ln(TP_r/TP_q)|} + 0.4e^{-|\ln(R_r/R_q)|} + 0.2J_{optimization}
$$

$J_{optimization}$ 是两个优化手段集合的 Jaccard 重叠度；数据库硬过滤已经确保了拓扑完全相同。

用户显式指定的 SLO 优先级最高。当对应目标缺失时，`UseCasePerformanceEstimate` 中的 TTFT、TPOT 和工作负载上限会作为考虑不确定性的软目标。对于每一个必需的延迟上限 $L$ 和历史实测延迟 $m_r$，计算：

$$
s_{latency} = e^{-2\max(0, \ln(m_r/L))}
$$

当达到目标时该项为 $1$，达到目标延迟两倍时为 $0.25$，并随偏差增大迅速趋近于 $0$。对所需工作负载承载能力 $c_q$ 和历史上能支持的承载能力 $c_r$ 施加相同的单边惩罚：

$$
s_{capacity} = e^{-2\max(0, \ln(c_q/c_r))}
$$

$$
S_{SLO} = \min(s_{TTFT}, s_{TPOT}, s_{capacity})
$$

只对请求中实际存在的目标取最小值。如果历史记录缺少某项显式 SLO 所需的指标，该记录就不能成为高相似度的性能证据，尽管它仍可以保留作为诊断用途。如果估算的目标过于不确定，或指标不可用，则不会捏造 $S_{SLO}$：此时会降级证据状态，以确保一个没有性能目标支撑的高分记录无法取代那些满足显式 SLO 的记录。

$S$ 是基础相似度：它描述的是某条基准测试记录的模型、硬件、工作负载、配置和实测性能与当前目标的契合程度。

当前实现还会计算时间衰减和运行时衰减：

$$
W = S \times D_{time} \times D_{runtime}
$$

本文档中将 $W$ 称为**匹配相似度（match similarity）**。它在基础相似度 $S$（已包含 SLO 性能契合度）的基础上叠加了时间/运行时效应，表达的是该历史记录与当前决策的相关程度。AI 评分读取按 $W$ 排序后的原始样本。确定性回退路径使用 $W$ 来计算加权指标平均值、有效样本量、确定性的 `confidence`、失败阻断以及 SLO/性能排序。AI 不会接收这些聚合值。当前负载字段仍然命名为 `match_confidence`，但其携带的是本文档中定义为 `match_similarity` 的 $W$。

### 非结构化诊断证据

日志、轨迹、制品和外部材料会被转化为有界的 `DiagnosticEvidenceProjection` 对象，具有固定的 `evidence_id`、内容哈希、源版本、租户、ACL 以及必要的运行时元数据。使用前，制品必须通过针对其 manifest 和文件 SHA-256 的来源校验。

未来私有诊断检索必须先应用租户/ACL 过滤，不得复用公开 RAG 索引。
当前公开 OpenSearch 适配器提供默认全文检索、显式选择的向量检索和受控混合融合，
返回前均核验发布状态和原文字节。向量影子 alias 不替换全文 alias；
每次请求固定物理构建及模型，混合检索两路使用同一固定向量构建。
工程能力不代表 S3 质量或性能验收。公开检索故障明确失败，
不伪装成空诊断特征，也不自动切换 PostgreSQL；这些路径均不改变确定性规划。

### 受控公开文档接入 {#controlled-public-document-integration}

S4 后端控制和 D2 接入并行推进，不建设独立 RAG 前端，也不作为独立产品发布。
Agentic 创建和 refine 每次重新解析服务端运行策略及实际调用者。
公开文档检索与公开 SQL 观测、已授权内部 benchmark 保持分离；修改文档开关不会授予其他数据权限。

文档模式默认关闭。影子模式执行有界、已核验的检索并记录脱敏状态，
但文档正文、ID、引用均不进入生成器/评分器提示词或候选决策。
启用模式仅面向显式稳定用户 ID 白名单，且调用者仍需独立 GLOBAL 查询权限；管理员不会自动绕过。
默认 lexical，hybrid 必须由运行策略显式选择。质量门槛不豁免，S3 性能验收放到最后。

启用后的文档包有界且固定版本，与实测观测使用不同合同。
规范来源引用及文档引用 ID 均由服务端产生，不接受模型自行构造。
生成器和 AI 评分器的引用必须属于本阶段实际提供的文档包。
正文是非可信来源数据，不是工具或系统指令。
文档可解释方法前提、文中声明的版本条件和操作者偏好，但不证明实际兼容性或实测性能，
不能提供 TTFT、TPOT、吞吐量、SLO 达标或确定性置信度。
已有 benchmark/AIC 校验和硬约束仍然有效。

refine 替换而非累积旧文档上下文和引用。关闭灰度停止后续消费；
撤销权限也会阻止保存方案中的文档暴露。
关闭、无权、不可用、滞后、降级和无匹配均提供脱敏明确状态，不伪造证据或静默宣称成功。
取消继续沿规划链传播。恢复时须复核目标本地灰度策略；文档备份恢复不会复制或启用该策略。

### 云端基准测试报告的两阶段检索

未来的受控导入器会定期或按事件从已配置的云端位置读取历史报告，仅为了发现而创建 OpenSearch RAG 投影。它必须校验来源身份、租户/ACL、报告模式版本、内容哈希、采集时间以及制品 manifest。使用稳定的源报告 ID 和哈希进行幂等去重。无法验证的报告不会生成投影；无法完整归一化的报告仅用于解释，不能作为性能规划输入。

第一阶段通过租户/ACL 过滤检索报告投影，以定位可能相关的原始报告。BM25/kNN 命中只表示文本相关性，而不是基准测试的可比性、`match_similarity` 或性能结论。外部报告不会被写入 `agentic_benchmark_records`；投影只保留云端 URI、生产者/模式版本、哈希、源报告 ID，以及获取原始报告所需的受控元数据。

第二阶段只处理被检索到的报告。服务端会重新校验来源 manifest/哈希、ACL 和模式，然后在本次规划请求范围内，将完全可解析的报告临时归一化为与在线采集相同形态的 `BenchmarkRecord`：模型、加速器/运行时、工作负载、候选配置、TTFT/TPOT/吞吐量、结果以及失败原因。临时记录不会被持久化。缺少性能比对字段的报告只能用于诊断/解释，不能用于给候选方案打分。

通过第二阶段的临时记录与本地持久化的记录会经历相同的硬过滤和 $S \rightarrow W$ 计算，得到含义相同的 `match_similarity`。对于每个通过硬过滤的候选方案，原始样本视图会为 AI 评分提供按 $W$ 降序统一排序的、最多五条基准测试证据样本，每条样本都包含 `match_similarity`、指标、结果、失败原因以及可追溯的来源引用。不存在单独的来源配额。

## 两条消费路径

### 确定性路径

只有当 AI 未配置、生成/评分失败，或响应无效时，确定性路径才会成为最终的决策路径。对于每个通过硬过滤的候选方案，它会在所有匹配样本上计算 $D_{time}$、$D_{runtime}$ 和 $W$，然后构建 `PerformanceScoreInput`。

聚合后的历史记录只有两种作用：

1. 如果存在数量足够多、且足够相似的失败记录，则设置 `has_blocking_negative_evidence` 并排除该候选方案，以避免再次推荐一个已知会失败的配置。
2. 如果成功的历史记录数量足够多、且足够相似，能够支撑稳定的性能结论，则首先比较所请求 SLO 的达标情况；若打平，则依次比较确定性 `confidence`、有效样本量、TTFT、TPOT、吞吐量和错误率。

样本过少或相似度不足、指标缺失，或存在未解决的失败证据时，都不意味着性能上的优势或劣势。此时改为使用精确的 AIC 匹配结果和现有启发式方法为该候选方案排序。

该路径不消费非结构化的 OpenSearch 内容，也不允许 AI 改写失败阻断、SLO 结论或排序。

### AI 路径

AI 的生成和评分是两个独立的阶段。生成器首先检索与模型、可用资源和所请求 SLO 匹配的历史基准测试记录。只有经过验证的候选配置及其受控的溯源信息，才可以作为候选先验（candidate priors）进入生成器的 prompt。如果没有符合条件的历史记录，则省略先验，仅从常规输入生成提案。每个提案都必须通过 `CandidateValidator`。

对于每个可行的 provider，AI 生成器必须首先提出最小资源拓扑方案：满足内存约束的最低 TP，以及每个服务角色一个副本。显式的 provider 偏好只能用于选择方法，不能自行提高 TP 或副本数。额外的资源需要显式的 SLO 或完整的 AIC 预测来支撑。从一个放宽搜索得到的锚点进行扩展，仍然只是一个需要验证的估算值。

AI 评分首先会筛选出最多十个通过硬过滤的候选方案：
按确定性顺序为每个 provider 保留最佳候选方案，然后按排名补足剩余名额。
只有入选的候选方案才会进入 AI，每个候选方案最多附带五条按相似度排序的真实历史基准测试记录。
原始基准测试记录描述的是实测的历史行为：AI 可以比较 TTFT、TPOT、吞吐量、结果和失败原因，
例如避免选择之前在类似工作负载下导致 OOM 的候选方案。
由文档策略显式启用时，独立校验的公开文档包可提示方法前提、文中声明的版本条件和操作者偏好；
它们不是实测数据或已验证的硬件兼容性，不能确立 TTFT、TPOT、吞吐量、SLO 或确定性置信度。
影子文档包不进入此阶段。

AI 不能生成新的候选方案，也不能将非结构化特征解读为性能实测数据。响应只能从服务端提供的候选方案 ID 中选择。无效、超时或不可用的响应会回退到确定性路径。

`rationale` 是面向用户的解释正文。历史技术以可读描述提供，
不附带原始导入标签、路径或内部引用标记；候选方案 ID 仍可用于比较入选方案。
服务端不会仅因正文出现类似内部标记的文本而拒绝、删词或重新生成响应，
原有 JSON、候选、分数及 SLO 校验仍然有效。
完整溯源保留在后端参考材料中，而非由模型声明历史引用。

### 生成器 Prompt 的构建与示例

生成是一个工具调用（tool-calling）阶段，而不是一个可以直接部署的配置目录。服务端构建的第一条用户消息只包含 `cluster_id`、`model`、`operator_preference` 和 `deployment_intent`，并剥离了实时资源/AIC/证据相关字段。系统 prompt 固定了 provider 的许可清单/语义、最小资源拓扑原则、PD 字段契约，以及只读 MCP 许可清单。它禁止臆造 provider、硬件、AIC 结果或基准测试事实，也禁止写入、部署、审批、删除和端口转发操作。

第一轮只暴露 `get_cluster_overview` 和 `search_candidates`，且要求并行调用；`sourceIds` 必须包含 `aic`。服务端使用 `cluster_id` 和 `sourceIds` 对参数进行归一化，并返回有界的结果。后续调用仍然被限制在许可清单内的只读工具范围内。模型只能通过 `submit_candidate_proposals` 提交一到十个提案；`CandidateValidator` 会独立地重新计算内存、GPU、CPU 缓冲区、PD 完整性和去重情况。当前实现不会注入任何历史基准测试先验。未来的先验必须是一个单独的有界字段，只包含经过验证的候选方案/溯源信息，不包含聚合指标、置信度、$N_{eff}$、SLO 结论或未经授权的数据。
