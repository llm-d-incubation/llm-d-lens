## Python 领域契约

`llm_d_lens.deploy.contracts` 中的模型与
`llm_d_lens.deploy.service.DeploymentService` 协议定义 Configuration 到 Deploy
的内部边界，不是额外的 HTTP 端点。Configuration 负责不可变配置产物的校验和生成，
Deploy 负责提供方执行与生命周期证据；Evaluation 负责工作负载校验和基准执行，
Simulation 不负责部署生命周期。

### 命令与不可变产物

| 契约 | 字段与约束 |
| --- | --- |
| `VersionedPayload` | 非空 `schema_version`；对象 `value` 默认为 `{}`；封装本身不规定生产方管理的字段。 |
| `ConfigurationArtifact` | `artifact_id` 默认为 UUID；`schema_version`、`kind`、`provider_ref`、`checksum` 非空；`media_type` 默认为 `application/yaml`；必须至少提供 `content` 或 `content_ref`。 |
| `DeploymentCreateRequest` | UUID `request_id`；`input_schema_version="v1"`；非空 `configuration_artifacts`；`deployment_policy` 默认为非 null 的 `VersionedPayload(schema_version="v1", value={})`；可选 `cluster_snapshot_ref`/`cluster_snapshot`；对象 `provenance`。 |
| `DeploymentKillRequest` | UUID `request_id`；`input_schema_version="v1"`；必填非空 `execution_id`；可选 `expected_namespace`/`reason`；对象 `provenance`。 |
| `DeploymentArtifact` | UUID `artifact_id`；非空 `artifact_hash` 和 `configuration_artifact_ids`；可选 `source_ref`、`manifest_ref`、`manifest_checksum`、`values_checksum`；必填 `rendered_payload`；`created_at`。 |

`provider_ref` 选择部署提供方，不转移配置所有权。当前
`GuideAdapterDeploymentService` 比通用 DTO 的限制更严格：每次 create 必须提供
**恰好一个包含内联 JSON 对象的产物**，且 `media_type="application/json"`。
运行规划器会将公开的运行请求拆分为 Case；不能直接向该适配器传入通用 YAML
或只有内容引用的产物并假定它支持。

`create(request, *, model_token=None, on_initial_execution=None)` 返回
`DeploymentExecution`；运行时绑定不改变配置所有权。
`kill(request, execution)` 在清理前验证执行 ID、可选的预期命名空间，以及该服务
所管理的提供方状态，不接受任意资源选择器。

### RuntimeClass 发现与策略

`GET /api/v1/deployments/runtime-classes?cluster_id=CLUSTER_ID` 要求部署读取权限和目标
集群访问权限。可选的 `accelerator`、`access_mode` 用于查询已注册 profile 的建议值。
返回 `items`（`name`、`handler`、`scheduling`、`overhead`、`matching_nodes`）、
`profile_suggestion`、`available_suggestion`、`requirement="unknown"`、
`node_runtime_readiness="unknown"` 和 `warnings`。Kubernetes 连接或读取权限失败返回
HTTP 503，不会伪装成空列表；未知硬件或访问模式返回 422，Lens 授权失败返回 403。

在 `POST /api/v1/deployments/runs` 中指定 `runtime_binding.runtime_class`：

```json
{"runtime_binding": {"runtime_class": {"mode": "named", "name": "custom-runtime"}}}
```

Python 对应 `llm_d_lens.deploy.contracts` 中的
`RuntimeBinding(runtime_class=RuntimeClassPolicy(...))`。Standard 和 Agentic 创建请求
通过顶层 `runtime_class` 接受同一策略。

- `auto`：保留并校验清单已有的显式类；否则仅在目标集群提供 profile 访问模式建议的类时
  使用它，没有可用建议时省略 `runtimeClassName`。
- `node-default`：明确移除 `runtimeClassName`，使用节点默认运行时；此模式不依赖
  RuntimeClass 发现权限，也不验证设备注入是否可用。
- `named`：必须提供合法 DNS 子域格式的 `name`，并校验目标集群是否提供该类。
  类缺失或与 Pod 节点选择器、节点名称冲突时，在修改集群前失败。

省略运行时覆盖时沿用配置的 `provenance.runtime_class`，未保存偏好时默认 `auto`。
显式 `auto` 会覆盖已保存偏好。选择保存在部署 Case policy 中，供重试和恢复沿用。
五种模型 provider 共用部署适配器，生成新的部署产物，不改写原始 Configuration 或已有
执行；仅路由的 Pod 不受影响。离线渲染不再注入未经集群验证的 profile 默认类。
报告位于 `artifact.rendered_payload.value.deployment_contract.runtimeClass`。

类存在、节点选择器匹配，不代表必须使用该类，也不能证明各节点的 handler、CDI、驱动
或完整调度约束已就绪。不能仅凭 device-plugin 或 DRA 判断是否需要 RuntimeClass。
只有确认集群默认运行时已经提供设备访问时，才应选择节点默认模式。自动和指定名称模式
在部署时依赖可解析的显式目标集群；离线 provider 渲染不构成集群验证。

### 执行、观察与证据

普通 provider 渲染会把各角色的 `maxModelLen`、`maxNumSeqs`、
`gpuMemoryUtilization`、`blockSize` 和 `maxNumBatchedTokens` 映射为对应的 vLLM 参数。
P/D 分别使用 `prefill` 和 `decode`；其他 provider 使用 `decode`
（`precise-prefix-cache-routing` 也接受 `serving`）。角色未指定长度时，
使用 `model.maxModelLen`。显式整数控制项必须为正整数；
`gpuMemoryUtilization` 必须为有限数，且大于零、不超过一。
非法值会使验证或渲染失败，不会静默回退。匹配目标角色的 `customParameters`
覆盖结构化控制项。普通渲染会替换 `--name=value` 和 `--name value` 两种形式；
省略的字段保留 Guide 默认值。精确发布的 `officialGuide` 清单继续走现有清单验证路径，
不会由普通 provider 参数映射重写。

`DeploymentExecution` 包含 `execution_id`、`request_id`、`status`、`artifact`、
`configuration_artifacts`、可选 `endpoint`/`namespace`/`resource_snapshot`、
`provenance`、`evidence_refs`、可选版本化 `diagnostics` 和时间戳。
当前还包含 `forwarded_endpoint`、`monitoring_setup`（安装审计，不是实时监控状态）、
`data_plane`，以及与来源证据分离的可编辑描述性
`metadata`（`display_name`、`description`）。

完整的 Run、Case、Execution 状态枚举见下文。`ready` 执行必须具有
`DeploymentEndpoint`，包含 `url`、`protocol="http"` 和可选
`service_ref`、`model_ref`、`baseline_url`。端点元数据不得包含凭据、
kubeconfig 或授权值。

共享内存检查结果保存在
`artifact.rendered_payload.value.deployment_contract.sharedMemory`，并复制到
`diagnostics.value.snapshot.shared_memory`。报告包含 `defaultSizeLimit`（`4Gi`）、
`addedMounts`、各容器的 `mounts`、`warnings`，以及共享内存处理阶段的
`manifestChecksum`（在后续放置和追踪处理之前）。普通渲染会补充模型容器缺少的
`/dev/shm` 挂载；已有挂载和主机 IPC 设置保持不变。发布的 `officialGuide` 清单
只检查，不修改共享内存配置。警告也会写入日志；无效或重复挂载绑定会使渲染失败。
这不会修改传入的 Configuration 产物。

`get(execution_id)` 返回 `DeploymentExecution`，而非另一套状态 DTO。
具体服务查询内存中的执行状态，未知 ID 会抛出 `KeyError`，它本身不是数据库查询。
Worker/DAO 边界负责持久化记录并在需要时恢复执行上下文。协议还提供
`restore_execution`、`refresh_diagnostics`、`stop` 和 `clean`；
外部客户端应使用下方经过认证的 REST 操作。

`get_logs(DeploymentLogRequest(...))` 返回独立于执行元数据的 `DeploymentLogPage`：

- 请求字段：`execution_id`、可选非负整数字符串 `cursor`、范围 1 到 1000 的
  `limit`（默认 100）、`follow=False`、`sources=[]`。
- 当前来源为 `workload` 和 `events`，不是任意 Kubernetes 选择器。
  日志条目包含 `timestamp`、`source`、`message` 和可选 `severity`。
- 响应字段：`execution_id`、`entries`、`next_cursor`、`complete`、`evidence_refs`。
  `follow=True` 会设置 `complete=False`，但方法仍只返回一页，不是流式迭代器，
  也不保证等待新日志。
- 归档诊断由 `ExecutionLogArchive` 管理，引用格式为
  `deployment-log://<execution_id>/archive`。证据文件与数据库记录分开保留；
  参见[存储设置](/environment-variables)。保留的快照是局部诊断，不是完整集群日志历史。

### 消费方投影

这些是纯 DTO 辅助方法，不执行生命周期操作或 REST 权限检查。
`benchmark_input()` 要求执行处于 `ready` 且具有端点，否则抛出 `ValueError`；
输出执行 ID、产物、端点、命名空间和来源证据。
`simulation_input()` 接受任意执行状态，并额外输出部署状态和可选资源快照/端点；
它保留执行时的证据，不用当前可变集群状态替换。当前 Evaluation/Simulation
路由并不直接调用这两个辅助方法，不能将投影描述为它们实际的请求 API。

```python
from llm_d_lens.deploy.contracts import (
    BenchmarkDeploymentInput,
    DeploymentExecution,
    SimulationDeploymentInput,
)


def benchmark_projection(execution: DeploymentExecution) -> BenchmarkDeploymentInput:
    return execution.benchmark_input()


def simulation_projection(execution: DeploymentExecution) -> SimulationDeploymentInput:
    return execution.simulation_input()
```

## 后端 API

Guide 兼容端点保留 `{ "error": "..." }` 响应结构。
预期的校验失败保留可操作的错误提示及状态码。
目录加载和准备阶段的非预期错误返回通用 `502` 响应；
规划阶段的非预期错误返回通用 `500` 响应，并保留 `Server-Timing`。
异常详情仅记录在服务端日志中，不返回浏览器。

### 准备 Guide 源码

`POST /api/guide-planning/prepare` 接受 `guide`、`accelerator`、`modelServer`、
`guideVariant` 和选定的 `clusterId`。它准备官方源码但不部署，返回提交标识及从清单解析的能力：

```json
{"ready": true, "commit": "selected-source-commit", "capabilities": {"cacheCpuGiB": false, "rdmaNicCount": true}}
```

布尔值表示是否支持 CPU 缓存修改以及是否存在匹配硬件 profile 的 NIC 声明，
不依赖变体名称。处理函数为 `llm_d_lens.deploy.guide_planning.prepare`，
源码加载位于 `llm_d_lens.deploy.guide_sources`。部署提供方复用 `guide_overlays`
和 `llm_d_lens.hardware.resolver.deployment_mode(profile, access_mode)`。

当前单仓库启动和 Lens 存储根目录参见[安装](/installation)及
[存储环境设置](/environment-variables)。旧 `.llm-d-bench/deploy` 和主机专属的
`/root/.llm_d_lens/run_store` 不再是当前存储契约。
执行发现使用 `execution_id` 作为跨模块引用，列表查询不会建立端口转发。
需要主机可达地址时应调用执行端点连接操作，不能假定持久化的集群内地址或旧隧道仍然可达。

| 记录 | 生命周期状态 |
| --- | --- |
| Run | `queued`、`running`、`succeeded`、`partially_succeeded`、`failed`、`cleaned`、`cancelling`、`cancelled` |
| Case | `queued`、`rendering`、`deploying`、`ready`、`failed`、`stopped`、`cancelling`、`cancelled`、`cleaned`、`cleaned_up` |
| Execution | `draft`、`validated`、`rendered`、`deploying`、`ready`、`failed`、`rolling_back`、`rolled_back`、`cleaned`、`cleaned_up` |

停止的 Case 对应 `rolled_back` Execution，两者不是同一个状态枚举。
评测要求执行处于 ready、有端点且集群会话有效。下方 worker 示例在已配置的 Lens 后端内运行；
外部客户端应使用已认证的 HTTP，以执行路由权限和资源范围校验。

智能体创建和细化流使用 `llm_d_lens.agentic.streaming.planning_stream_response`。
这些路由保留了主体解析、预期错误分类以及它们现有的通用错误信息。
流会先发出 `progress`，然后是 `complete` 或 `error`；断开连接时的清理
操作会取消并等待尚未完成的规划。网关操作/日志流是单独处理的。

Agentic 的生成器和规划器用户消息均以完整用户偏好开头，随后才是 JSON 上下文。
提示词的优先级为：平台和硬件有效性、明确用户要求、软偏好、证据与候选多样性。
多样性不得引入用户禁止的拓扑，最终可以返回少于三个方案。
这是提示词约束，并不等同于服务端具备通用的自然语言硬约束解析能力。

规划快照（schema version 2）完整保留 `request.planner_prompt`，不做内容脱敏。
`planner_prompt_present` 仅作为兼容性标志保留，不再替代原文。
运行记录的 `generator_requests` 和 `planner_requests` 保存每一次实际 HTTP 尝试
最终发送的提供方原生请求体、原始响应、时间戳、HTTP 状态与错误类型，包括重试。
快照中对应字段为 `generator.requests` 和 `planner.requests`。
阶段审计文件位于 `session-artifacts/agentic-planning/<run_id>/requests/`，
在发送前和完成后落盘，因此取消、失败或未生成最终运行记录时仍可排查。
不记录认证头和 API Key；完整提示词和工具上下文属于私有应用数据。
审计只适用于修改后的新请求，无法补回过去没有记录的交互。

### Agentic 计划中的多来源证据

`AgenticDeploymentService.create()` 和 `.refine()` 使用实际请求主体解析证据，
REST 与流式调用均保留该身份。公开 Prism 观测按精确模型和实时硬件过滤，
要求全局 `benchmark-rag:query:read`；内部实验保留资源授权。
不信任客户端提交的公开观测和案例；包含公开观测的计划保留相同读取权限要求。

每次 `create()` 或 `refine()` 调用中，规划事实与公开证据检索复用同一份请求内硬件发现快照。
后续调用和批准部署会重新发现资源。加速器身份和可用显存仅来自实时自动识别，
不再支持 test-only 的硬件型号和显存环境变量覆盖。无法识别可用显存时会停止规划，
不会补入模拟容量。此前创建的模拟计划仍禁止部署。历史匹配使用部署运行时的服务后端；
公开记录的后端缺失、为空或为 `unknown` 时，SQL 匹配和返回的实验/案例上下文默认按 `vllm`
处理；明确标注的其他后端不会被重新归类。已存记录和原始来源证据不变，未知运行时版本仍保持未知。
提示词中的 TPOT 目标支持 `ms/token` 和 `s/token`，统一换算为毫秒。

基准数据比较按数值匹配等价的小数负载，将 `latency`/`e2e` 识别为端到端延迟别名，
并规范化 `p99p9`/`p99.9` 等小数百分位；原始来源证据仍保留。

服务端规范化显式负载和延迟要求，按配置和 series 聚合实验后，
每路 SQL 最多选择 50 个案例，再在 16,000 字节证据预算内保留最多 10 个完整案例。
显式负载匹配度优先，其次比较同口径的较低延迟；无负载时不施加负载惩罚。
缺失测量保持未知，不跨统计口径或实验拼出 SLO 结果。
既无可比较负载也无有效延迟的案例明确标注为回退参考。
只有所有请求的延迟指标及其统计口径都有对应数据时，候选才会获得 SLO 结论。
缺失指标保持 `unknown`，既不算达标，也不算失败。
仅有 TTFT/TPOT 证据不能证明端到端延迟目标，因此此类计划的 SLO 状态保持 `unknown`。

`planning_evidence` 使用 `id="public-rag:query"` 保存公开检索状态，
区分可用、无匹配、无权限和不可用。配置案例详情保留源条件、差异、未知项、
分支状态和截断信息。候选解释和服务端审计保持证据边界：
历史测量不能证明当前性能，AIC 仍为估算。

规划使用公开和内部 SQL 实验，不包含文档检索分支、embedding/向量检索或文档包契约。
模型提示词将来源称为公开基准证据和内部历史基准，并要求决策解释使用这些术语。
未包含在完整案例中的公开观测使用模型上下文字段 `published_benchmark_evidence`；
上下文为空只说明本次请求未提供证据，不代表数据库中没有数据。
已存储的 `public_rag_evidence` 字段、`public-rag:query` 证据 ID 和
`benchmark-rag:query:read` 权限保留为历史兼容标识，不代表具备文档检索能力。
原有私有诊断适配器不受影响。

创建校验已注册模型缓存存储卷，但不要求模型文件已下载；细化同样跳过下载就绪检查。
批准时要求缓存模型已就绪、解析当前凭据策略、刷新资源校验，并获得用户明确批准。

细化仅在重新核验了证据读取权限并保存新审计快照后，才会替换当前计划；
细化失败保留上一份计划。重算或批准期间计划发生变化时，需要重新加载后再操作。
手动选择备选候选会同步更新决策的 SLO 状态与证据，但不会改写先前的审计快照。
批准会在提交 Deploy 前离开 `awaiting_approval`，避免同一计划被重复提交。
提交失败或中断时，Agentic 运行标记为 `failed`；创建替代计划前应先检查部署运行记录。

部署相关功能位于 `llm_d_lens/deploy/router.py` 中的 FastAPI 路由下，
前缀为 `/api/v1/deployments`。

优化路由和精确路由的能力元数据复用了 `llm_d_lens.deploy.capabilities`
中的 `shared_prefix_routing_workload()`。每个场景和推荐的工作负载都会
获得各自独立的嵌套值；提供方专属的基线和目标保持不变。精确提供方的
校准和模型发现共享惰性的 modelserver 调用遍历逻辑，同时各自保留了
自己的"取最后一个值"和"取第一个模型"选择规则。

Agentic 候选提交接受 `optimized-baseline`、`pd-disaggregation`、`tiered-prefix-cache`
和 `precise-prefix-cache-routing`；生成器 schema 拒绝 `baseline-vllm`，规划器排序也会
排除它。AIC 聚合推荐映射到 `optimized-baseline`，包括负载目标和宽松锚点路径。

智能体规划会针对每个经过校验的 optimized-baseline 和
pd-disaggregation 候选方案，根据其工作负载和 GPU 拓扑结构，分别估算
缺失的精确 AIC 预测值。候选方案的估算值会以 `aic_estimate` 的形式
提供给 AI 评分；如果估算值不可用，则保持为未知状态，而不是一种
性能或 SLO 保证。智能体估算不会沿用原始搜索的 TTFT/TPOT 目标；
它们只是在没有 SLO 过滤的情况下，对固定的拓扑结构和工作负载进行校验。
当失败的生成器没有留下任何工具调用轨迹时，生成器回退逻辑也会使用
已解析的工作负载，对内置的前三个候选方案进行估算。不受支持或不可用的
拓扑结构保持为未知状态。宽松 AIC 搜索会接受任何不超过可用 GPU
预算的完整配置。它的预测结果并不能确立对原始 SLO 的符合性。
即使生成器只建议了一个更小的拓扑结构，智能体仍会将宽松的锚点方案
保留为一个经过校验的候选方案，然后估算其精确的拓扑结构和工作负载。
已知估算值未能达到原始延迟目标的候选方案会被标记为 `not_satisfied`；
在同样未达标的候选方案中，相对目标偏差更小的方案排名会优先于
GPU 节省量更大的方案。未知的估算值不会被视为失败。
当外部规划器对多个候选方案进行评分时，其选择理由会根据提供的
规划事实，解释为什么每一个评分较低的返回候选方案排在最高选择之后。
只有返回的前三个候选方案会被评分；对于该集合之外的候选方案，
不会推断出任何理由。

### 搜索或估算 AIC 负载容量

上文的 MCP 生成和普通 estimate 回退行为适用于未提供负载目标的请求。
Agentic 负载目标规划会直接校验 AIC 原生推荐的精确拓扑，包括普通候选网格之外的副本数。

<Tabs>
  <TabItem value="rest-api" label="REST API">
    **`POST /api/v1/aic/search`**

    `mean_input_tokens` 默认 `4000`，`mean_output_tokens` 默认 `1000`，与 AIC 原生
    search/recommend 一致。可以提供正数 `target_concurrency` 或 `target_request_rate`
    （每秒请求数），二选一；两项均不提供时保留固定 GPU 数搜索。
    同时提供会被拒绝，错误中会明确说明 AIC 不支持联合负载目标。
    Agentic 将 `planning_facts.workload_profile.concurrency` 和 `.request_rate`
    映射到这些字段；QPS 和 request rate 是同一项。

    存在负载目标时，`gpu_count` 是 Lens 的验收预算，不传给原生 recommend。
    Lens 会扩展推荐的各 worker 池，只接受所需 GPU 不超预算且满足 TTFT/TPOT 目标
    （原生默认 `2000`/`30` 毫秒）的配置。预测不可用、容量不足或 SLO 无法满足时，
    会明确报错，不会悄悄选择没有负载目标的预测。Agentic 会将原因传到前端错误提示区。
  </TabItem>
  <TabItem value="python-api" label="Python API">
    ```python
    from llm_d_lens.aic.models import AICRequest
    from llm_d_lens.aic.service import search

    result = await search(AICRequest(
        model_name="Qwen/Qwen3-8B", aic_system_name="a100_sxm",
        gpu_count=8, target_request_rate=10,
    ))
    ```

    要指定目标并发请求数，使用 `target_concurrency` 替代 `target_request_rate`。
    两项都不设置则保持原来的固定 GPU 数搜索。

### 扩缩容部署执行

修改处于就绪或失败状态的执行的 Prefill 和/或 Decode 模型服务器实时副本数。此操作只修改 Kubernetes 副本数，不改变已保存的配置。支持 Deployment 和 DisaggregatedSet 工作负载。DisaggregatedSet 扩缩容只修改角色副本数，不修改 `spec.slices`；Lens 新建的 DisaggregatedSet 固定使用 `slices: 1`。

### 刷新部署用例

<Tabs>

### 重启部署用例

:::warning 当前重启限制

路由存在，但当前 worker 清理旧执行并把用例标记为 `cleaned` 后，再调用

## Remote SSH 部署

SSH 传输和远程命令失败返回 `502` 及
`{ "error": "Remote deployment failed" }`；内部异常详情及失败命令的输出
记录在服务端日志中，不暴露在错误响应中。
预期的输入和策略错误保留原有状态码及可操作的提示。

这些旧版端点由 Python 模块 `llm_d_lens.deploy.remote_deploy` 实现。
它们通过 SSH 执行命令，不创建 v1 部署运行。当前仅支持单节点 Intel Data Center GPU/XPU，
这是旧实现的限制，不代表由硬件 profile 驱动的 v1 API 的能力范围。

生产环境必须设置 `PRISM_REMOTE_DEPLOY_ENABLED=true`，非生产环境默认启用；
生产目标还必须匹配 `PRISM_REMOTE_HOST_ALLOWLIST`。
即使 SSH 操作被禁用，默认值接口仍可读取，但需要认证及相应权限。

| 操作 | Lens 权限 |
| --- | --- |
| Defaults | `remote-deploy:target:read` |
| Fingerprint、test | `remote-deploy:target:connect` |
| Start、status、logs | `remote-deploy:deploy:execute` |
| Teardown | `remote-deploy:deploy:teardown` |

需认证的 SSH 操作要求 `target.host`、`username`、`hostFingerprint`
以及非空、由数字 ID 字符串构成的 `cards` 数组。`port` 默认 22；
`authMethod` 默认 `agent`，还支持 `key`、`password`。
Agent 模式要求 BFF 有 `SSH_AUTH_SOCK`；key 模式要求服务端 `keyPath`
位于 `PRISM_SSH_KEY_DIR` 下，默认 `$HOME/.ssh`。
Password 模式在每次请求的 `credentials.password` 中提供密码，不保存也不返回。
指纹发现不执行认证，也不要求 cards。使用前应通过可信渠道确认指纹；
接口返回一个指纹本身并不能证明主机身份。

路由错误结构为 `{ "error": "..." }`：输入／凭据无效为 `400`，
生产目标不在允许列表为 `403`，SSH 操作被禁用为 `503`，
SSH／命令失败通常为 `502`。网关认证和权限错误使用网关的 Problem Details 格式。

### Remote 操作的 Python HTTP 客户端

这些 Node 端点**没有 Python 服务层等价方法**，下方 Python 页签使用此 HTTP helper。
示例环境变量只是客户端输入，不是新增的 Lens 服务端配置。
从已登录的 Lens 会话取得值，切勿提交其内容。

```python
import os
import httpx

def remote_request(method: str, path: str, body: dict | None = None) -> dict:
    with httpx.Client(
        base_url=os.environ["LENS_URL"],
        cookies={
            "prism_session": os.environ["LENS_SESSION"],
            "prism_csrf": os.environ["LENS_CSRF"],
        },
        headers={"x-prism-csrf": os.environ["LENS_CSRF"]},
        timeout=300,
    ) as client:
        response = client.request(method, path, json=body)
        response.raise_for_status()
        return response.json()

target = {
    "host": "192.0.2.20",
    "port": 22,
    "username": "operator",
    "authMethod": "agent",
    "hostFingerprint": os.environ["VERIFIED_SSH_FINGERPRINT"],
    "cards": ["0"],
}
```

下方 REST 请求示例展示操作字段；需认证的操作还要加入上述完整 `target`
以及可选的每次请求 `credentials`。Python 示例展示完整请求组装。

<Tabs>

## 配置准备 API

这些配置领域的路由会为部署和评估准备制品。请求和响应模型位于
`llm_d_lens.configuration.models`。示例中使用了用于说明的集群/会话
ID 和指南提交记录；请将它们替换为一个活动的集群会话和真实渲染过的
指南溯源信息。保存操作会发布一个制品；单独的渲染操作不会部署它。

流程为来源选择/编辑、resolve、render、save，最后才是部署。Resolve 先归一化各输入，
再进行能力检查与校验，并逐配置返回反馈。Candidate source 标识输入来源，不是部署类型。
Render 将候选意图与实际 Guide 资源绑定；save 发布不可变制品、身份信息与校验和。
Configuration 负责归一化、校验与制品发布，Deploy 负责运行时校验、资源生命周期、拆除与回滚。
校验和不能单独证明拓扑或资源语义正确。以下 REST 端点及 Python 服务函数遵循同样的边界。

HTTP 边界使用 `application/problem+json` 格式的错误。共享的
`DomainError` 实例会保留其原始的状态码和错误码（例如冲突仍然是
409）；它们不会被转换成一个操作专属的 500 错误。Python 服务调用
会抛出其原始异常；`llm_d_lens.configuration.router` 中的路由适配器
应用下面的 HTTP 映射关系。

### 部署访问 API（已移除）

部署分享和 `deployment:run:share` 已退役。请改用
[模型服务推理授权](/api-reference/modules/model-services#模型推理授权)。
迁移会审计并清理旧部署授权，不会自动扩大为模型授权。

<Tabs>
  <TabItem value="rest-api" label="REST API">

原 GET/POST/DELETE `/api/v1/deployments/executions/{execution_id}/access`
和 `/api/v1/deployments/runs/{run_id}/access` 路由，包括 `/access/options`
及 `/access/{binding_id}`，均已取消注册，不再提供授权、列表或撤权功能。
  </TabItem>
  <TabItem value="python-api" label="Python API">

将部署分享调用替换成模型服务的、带 scope 校验的授权方法：

```python
from llm_d_lens.model_service.service import default_service

def revoke_model_grant(model_id: str, binding_id: str, principal) -> None:
    default_service().revoke_access(model_id, binding_id, principal=principal)
```

该方法要求调用方在模型所属集群拥有 `model-service:group:share`，并拒绝撤销其他模型的绑定。
通用绑定创建方法也会拒绝已退役的 `deployment_run` 和 `deployment_execution` 资源类型。
  </TabItem>
</Tabs>
