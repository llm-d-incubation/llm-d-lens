## Harness 代理兼容性

Lens 保留用于外部下载的 HTTP(S) 代理，同时通过 `NO_PROXY` 传递集群地址和
CIDR。Kubernetes Python client 35.0.0 可能丢弃该值，导致加速器检测通过代理
访问 Kubernetes API，进而发生证书校验失败。

运行时准备会将已知 SDK 修复应用于宿主机 CLI 环境和所选检出目录的 harness
Pod 模板。新建 Pod 会在执行原有 harness 命令之前修复受影响的客户端，涵盖预热
和矩阵运行。已修复的客户端保持不变，TLS 校验和下载代理仍然启用。如果模板不兼容，
或无法写入受影响的容器软件包，启动会明确报错并停止，而不是在未修复的状态下继续。

现有 Pod 不会被修改。未启用自动重载的后端进程需要加载更新代码后再开始新的评估；
不要在该进程仍负责运行中的评估时重启它。

## 后端 API

评估相关的路由位于 `llm_d_lens/evaluation/router.py` 中，前缀为 `/api/v1/evaluate`。请求模型定义在 `llm_d_lens.evaluation.models` 中；命名的 HTTP 响应模型定义在 `llm_d_lens.evaluation.api_models` 中。

运行、工作流、用例和详情响应会保留额外的已存储字段。记录中不存在的可选字段会保持省略状态；显式存储的 `null` 值会保持为 `null`。列表响应会保留其 `{ "items": [...] }` 信封结构。Python 路由函数返回字典；FastAPI 会在 HTTP 边界处应用对应的命名响应模型。

错误使用应用的 `application/problem+json` 响应格式，包含 `type`、`status`、`title`、`detail`、`code` 以及可选的 `requestId`。`detail` 字段可以包含结构化的校验错误。认证和资源权限仍然适用；声明一个响应模型并不会授予访问权限。

### 启动一次基准测试运行

配置驱动工作流和已有服务评测都调用 `create_run()` 并使用同一执行器；工作流另外负责部署编排和比较。
当前 UI 的已有目标入口选择已发布的 Model Service，而非任意 URL。
`deployment_ownership` 控制清理归属，不改变指标语义：取消已有服务的评测不会停止模型服务。

两者都使用 `BenchmarkSpec` 默认值：`parallelism=1`、`wait_timeout_seconds=1800`、
每个 worker 的 `harness_memory_gib=8`，以及矩阵的 `warmup_requests=2`。
显式设置优先，UI 预设的预热次数可能不同。旧调用方如需 7200 秒或 32 GiB，必须显式传入。

| 证据操作 | 当前行为 |
| --- | --- |
| 监控准备 | 优先复用健康的 Prometheus target（`up == 1`），否则尝试创建监控资源及配套 RBAC。发现、配置和就绪等待共用 30 秒时限；失败会记录，但不使压测失败。 |
| Prometheus 采集 | 即使准备失败，仍查询压测时间窗口，时限 120 秒。仅发现集群的中心 Prometheus，不根据模型端点推断外部 Prometheus URL。缺失序列保持不可用，不记为零。 |
| KV capture | 使用已有探针的容器，通过 `kubectl exec` 启停采集。压测不会安装探针、修改模型清单或重启服务。不支持的布局、缺失探针或请求 ID、采集冲突、worker 并行度不为一都会产生不可用证据。 |
| 资源快照 | 在完成时、清理前尽力采集，时限 30 秒。缺失的历史快照不会用当前资源补写。 |

探针安装属于独立的部署渲染步骤：符合条件的新 vLLM 清单会加入探针，当前注入器跳过 PD 清单。
已有探针的部署不需要重新部署即可采集。KV 工作集采集要求兼容的 vLLM V1、
prefix caching、单个 FullAttention cache group 和 `parallelism=1`。
测量范围是成功请求中完整 prompt 块去重后的逻辑工作集，不包括生成 token 和不完整的尾块。
记录缺失或请求关联不完整时返回不可用结果；整轮证据不会自动分配给各负载阶段。
相同负载与探针条件保证指标覆盖和语义一致，不保证测量数值完全相同。

用户操作步骤见[选择评测方案](/evaluation/guides)。

### 启动一次多配置评估

对于 `pd-disaggregation` 源配置，独立部署的基线默认匹配 Prefill 与 Decode 的总 GPU 预算：

```text
baseline replicas = (prefill replicas * prefill TP + decode replicas * decode TP) / baseline TP
```

基线 TP 默认继承源配置 Decode／Serving TP，可用
`benchmark_plans[].baseline_parameters[baseline_type].tensor_parallel_size` 覆盖。
仅覆盖 TP 会重新计算副本数；显式 `replicas` 优先，允许刻意选择不等预算。
例如 2P2D、两侧 TP=1 默认生成四个 TP=1 的普通 vLLM 副本；基线 TP=2 时为两个副本。
自动匹配必须产生 `1..32` 范围内的精确整数，否则在保存及排队前返回 `409`，不会取整或截断。
非 PD 源配置继承 Decode／Serving 副本数；同 Pod 的 `kubernetes-service` 比较复用候选资源池，
不分配独立副本。此默认规则仅作用于新建评估，不改写已有／运行中快照或重试；
历史上的不等预算比较不会因此变成等预算。覆盖字段范围参见[评估参数](/evaluation/parameters)。

### 获取详细的评估工作流结果

关联的压测及用例结果与独立压测详情共用补全逻辑。用例快照是完成时保存的证据。
`deployment_cases` 还可能包含供查看的当前 Kubernetes 快照；这些实时快照不属于历史压测测量。

获取展开后的评估工作流结果以及部署关联信息。

对于包含用例的工作流，报告使用 `comparison_version: 2`。在读取详情时，较旧的缓存报告会根据保留下来的证据数据重新生成。矩阵行会匹配唯一的、成功的 `(isl, osl)` 数据点以及显式的 `concurrency`；速率阶段会匹配显式的 `rate`。缺失、非有限、负数或重复的负载键不构成匹配，数组位置也永远不会作为回退依据。没有匹配行时，对应的统计信息为 `null`。
