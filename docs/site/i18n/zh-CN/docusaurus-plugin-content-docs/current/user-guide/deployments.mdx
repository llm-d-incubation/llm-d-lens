模型选择和本次部署参数覆盖使用 [Model Catalog](/user-guide/model-market)。自定义条目和 API 字段参见[目录 API](/api-reference/modules/model-market)。

打开 **Deployments（部署）**，确认模型是否就绪、排查失败原因或管理已有部署。

新建 llm-d Router 部署默认保留完整 Standalone 入口，即使集群已有就绪的共享 Gateway。发布会增加 Gateway 路由，解绑后仍可独立访问。详见 [Standalone 部署与 Gateway 发布](/user-guide/model-services#standalone-部署与-gateway-发布)。

## 打开部署创建流程

1. 在左侧导航中，打开**部署**。
2. 在页面标题栏，点击**创建**。
3. 按[创建部署](/user-guide/model-market)完成操作。提交后，新部署会出现在列表中。

Manual 直接进入部署方案；Agentic 先提供目标选项，所有数值参数都可选。不预设请求长度、前缀复用或负载形态，
这些是收益参考而非兼容性门槛。Agentic 选择 AI 提供方后，
可从自然语言目标提取明确表达的定性负载特征，提取结果可见、可修改。
未使用 AI 时依赖结构化输入；数值资源上限和性能目标不会由 AI 推测。

Manual 在已支持组合中依次按 SLA 状态、P/D 决策、源码校验后的优化覆盖排序，而非选第一个能渲染的 Guide；覆盖相同时优先 P/D 组合。
Manual 仅在你填写请求长度时限制 `--max-num-seqs`，否则由 vLLM 按空闲 KV 缓存接纳请求。
这不等于占满集群，也不代表实测最优。不支持的组合会明确说明。
**Ready for your confirmation（等待确认）**给出简洁结论；检查失败时阻止部署并提供 **Retry checks（重试检查）**。
部署确认会重新检查当前资源。

前缀亲和路由、P/D 分离和 CPU KV 卸载可以独立组合。路由组合保留 P/D 调度配置，
并使用同一固定源码版本中的亲和插件；插件或镜像不兼容会明确报错。
基础注意力 KV 缓存与跨请求前缀缓存、CPU 卸载不是同一功能。
vLLM 源码未显式配置的运行开关可在添加强制启动能力检查后配置；
检查在选定镜像内执行，不代表运行时支持已验证。

构建方案前，在设置卡片中选择 **Pod placement（Pod 放置）**：优先单节点（默认）、要求单节点（可指定节点）、
跨节点均匀分布或要求分散到不同节点。该选择作用于 Deployment、LeaderWorkerSet 和 DisaggregatedSet 模型服务。已有部署 API 和独立 Configuration 编辑器
保留放置控制。TP 设备由各模型服务 Pod 请求；部署前的计划放置不会显示为实际放置。

P/D 的 Prefill、Decode 与 KV 传输设置包含 **P/D slices and placement**：slice 数量、每个 slice 的 Prefill/Decode 副本数与 TP、
slice 放置策略（`None`、`ExclusiveSlice`、`ExclusiveTopology`）及其节点标签拓扑键。Lens 根据各拓扑域当前空闲设备给出推荐，
优先最窄的域（节点，其次机架类标签、可用区、地域）：把角色副本拆分为最少的等份 slice，使每个 slice 能放进一个域，从而让 KV 传输保持本地。
Low latency 与可靠性目标在空闲独占域足够时使用 `ExclusiveTopology`；没有域能容纳完整 slice 时放置保持 `None`。
自动硬放置还会将角色 Pod 限定到能容纳完整 slice 的域，避免首个 Pod 将整个 slice 锁定到容量不足的节点。
这不会预留设备；可用容量变化后应重新生成方案。
已审阅的值固定在方案中，仍可编辑；非 `None` 策略是硬调度规则，没有域能容纳 slice 时 Pod 会保持 Pending。
推荐会遵循 Pod 放置：选择均匀分布或分散到不同节点时不推荐按节点放置 slice，要求单节点时只保留一个 slice。
slice 面板会禁用冲突的拓扑键，显式冲突会在应用修改时报错。

创建部署要求模型已在 [Model Cache](/user-guide/model-cache) 中注册。请选择同一集群上包含就绪模型及其修订版本的已注册缓存卷。高级配置编辑器仅提供 **Model Cache** 来源。对于本地磁盘存储，请在部署前同步新节点。常规 Provider 渲染会配置带只读缓存挂载的离线服务。请先在 Model Cache 中下载或修复缓存，然后再创建或重试部署。

缓存检查遵循当前启用的服务角色：P/D 会分别检查 Prefill 和 Decode；其他 Provider 使用 Decode。每个角色默认使用修订版本 `main`。显式指定的 tokenizer 也必须在同一缓存卷中处于就绪状态；除非提供了 `tokenizer-revision`，否则其修订版本默认与对应角色的模型修订版本一致。存在冲突的依赖参数会被拒绝。在继续部署前，渲染后的模型和 tokenizer 参数必须与已检查的依赖项匹配。

常规的 optimized-baseline 渲染不会应用自定义的 `revision`、`tokenizer` 或 `tokenizer-revision` 参数，因此这些输入会被拒绝。缓存预检不支持配置来源覆盖以及自定义的 `model`、`model-path`、`code-revision`、`hf-config-path`、`config` 和 `download-dir` 参数。

### Model Cache 强制执行限制

精确发布的 YAML 配置（`officialGuide`）会绕过常规 Provider 渲染流程。其最终清单尚不会强制应用相同的离线标志、只读缓存挂载或后端存储卷绑定，因此该路径不保证纯缓存部署。离线环境变量同样不构成网络隔离边界。

## 在列表中查找部署

1. 查看页面顶部的汇总卡片：**总计**、**就绪**、**进行中**、**失败**和**已清理**。
2. 在列表工具栏中，在**搜索部署**中输入内容，可按名称、描述、模型、命名空间、指南或 ID 匹配部署。
3. 打开**状态**以按部署状态进行筛选。
4. 打开集群选择器，选择**所有集群**或某一个集群。
5. 如有需要，更改**每页行数**，并使用分页器在列表中翻页。
6. 如果没有匹配的行，点击**清除筛选**。

**集群**和**命名空间**列各带一个复制按钮。

## 查看部署详情

1. 在部署行中，打开操作菜单并选择**查看详情**。
2. 在抽屉中，查看**基本信息**、**模型与服务引擎**、**集群与环境**、**网络与端点**以及**审计与时间线**各个部分。
3. 当你需要在别处复用诸如**命名空间**、**集群会话 ID**、**容器镜像**、**内部端点**、**转发端点**或**执行 ID**等值时，使用这些值旁边的复制按钮。
4. 如果部署失败，请先阅读失败提示横幅，再做任何改动。

等待状态变为 **Ready（就绪）**后再调用。处于 **In progress（进行中）**时，
打开 Pod 日志查看启动进度；处于 **Failed（失败）**时，结合失败提示和对应 Pod 的日志排查。

缺失的运行详情从已存储的最终 vLLM manifest 读取。P/D 部署的平铺运行字段标注
**(Decode)**；未设置的值保持未知，不会用推测的默认值填充。

正常 Pending 或 Running 但尚未就绪的 Pod 会让启动中的部署保持 **In progress（进行中）**。
镜像拉取失败、OOM 等明确 Pod 故障仍显示 **Failed（失败）**。
对于已标记 Ready 的部署，状态灯同时反映模型服务器 Pod 的实时状态：黄色表示就绪的模型服务器 Pod 少于请求数量，
服务能力下降；红色表示已没有就绪的模型服务器 Pod，服务不可用。这两种情况也会出现在 **Needs attention（需要关注）**中。

**Failed（失败）**并非终态。发布超过进度期限会被记为失败，但工作负载往往会自行恢复——
例如某个 Pod 一直崩溃，直到其模型缓存补齐后才正常启动。Lens 会持续拿失败的部署与集群实况
比对，一旦其 Pod 重新提供服务就把状态改回 **Ready（就绪）**，因此不必急于重建部署。
如果命名空间已不存在，则该部署会被更正为 **Cleaned（已清理）**。

当 Pending Pod 正在等待加速器资源时，包括 DRA 调度器报告的
`cannot allocate all claims`，即使超过发布进度期限，部署也会保持**进行中**。
刷新先前被标为**失败**的部署时，如果当前诊断确认仍在等待资源，状态会恢复为**进行中**，
调度原因仍可在诊断中查看。这不会释放其他部署占用的设备；需要停止或删除不再使用的部署来
释放资源。容器崩溃和镜像拉取失败仍被视为失败；仅有 Pending 状态不足以判定为资源等待。

调度成功后，Running Pod 可能仍在加载模型，尚未 Ready。如果发布报告超出进度期限，
只要当前容器仍在 `startupProbe` 的启动预算内（没有启动探针时使用 `readinessProbe` 的预算），
Lens 就会保持**进行中**，不会自动清理。预算从各容器实际启动时刻计算，Pending 等待时间
不会占用该预算。当前崩溃、镜像拉取失败、容器重启或探针预算耗尽不适用此宽限。
仅有 Running 状态不代表就绪，仍需通过 provider 的就绪检查。

## 查看 Pod 并查看实时日志

对于新渲染的部署，所有 provider 都会将显式设置的最大模型长度、最大序列数、显存利用率、
块大小和最大批处理 token 数传给 vLLM。P/D 分别应用 Prefill 和 Decode 的配置。
角色配置覆盖 Guide 默认值；角色未指定最大长度时使用模型级最大长度。
定向自定义参数优先，未设置的字段保留上游默认值。这不会重写现有 Pod 或精确发布的清单；
需要创建新部署才能应用变更。排查 KV cache 容量错误时，应核对模型容器启动命令及日志。

Lens 会检查所有部署 provider 渲染的模型服务 Pod 的 `/dev/shm`。普通渲染中，
如果缺少挂载且未启用主机 IPC，会补充每个 Pod 独立的内存型 `emptyDir`，上限为
**4 GiB**；`baseline-vllm` 的默认值也为 4 GiB。这避免了容器运行时默认的
64 MiB 共享内存限制，不会启用主机 IPC，也不会修改上游 Guide 仓库。

已有挂载及其容量设置保持不变，包括未显式设置上限的内存卷和其他卷来源。
未设置上限、其他卷来源、只读或子路径挂载，以及已启用主机 IPC 的情况，会在服务日志和
部署诊断（`snapshot.shared_memory`）中记录警告。内存卷省略 `sizeLimit` 并不表示
上限为 64 MiB，也不表示内存无限可用。重复的 `/dev/shm` 挂载和无效卷绑定会被拒绝。

原样发布清单（`officialGuide`）只检查，不自动补充共享内存挂载；缺少挂载时记录警告。
检查报告也保存在部署产物的
`rendered_payload.value.deployment_contract.sharedMemory` 中。
卷按实际使用量消耗内存，而非提前占用整个上限；规划 Pod 内存时应将共享内存计入。
已有部署仍保留原始清单，需重新创建才能获得新默认值或缺失挂载的补充。

1. 要在行内查看 Pod 状态，点击提示为**显示 Pod** 的行展开开关。
2. 在展开的行中，查看 Pod 表格的列：**Pod**、**状态**、**重启次数**、**节点**和 **Pod IP**。
3. 要使用完整的日志查看器，打开操作菜单并选择**查看 Pod 与日志**。
4. 使用节点筛选或搜索框找到需要查看的 Pod。
5. 点击某个 Pod 卡片，打开该 Pod 的**Pod 日志：**。
6. 如果某个 Pod 包含多个容器，请选择所需的**容器：...**条目。
7. 选择**100 行**、**200 行**、**500 行**或**1000 行**以更改日志尾部的长度。
8. 如果需要查看上一个容器的日志，请打开**上一个**开关。
9. 保持**自动刷新 (5 秒)**开启，以让 Pod 列表和日志保持实时更新。
10. 使用**筛选日志行...**来缩小日志输出范围，或点击**复制**来复制当前的日志文本。

## 优雅停止默认配置

Lens 为模型服务器 Pod 设置 **120 秒**终止宽限期和 **5 秒** preStop 延迟；vLLM 容器的启动命令如果是单条可识别的 `vllm serve` 或 `python -m vllm.entrypoints...`（包括 `sh -c` 脚本），还会设置 `--shutdown-timeout=90`；复合 shell 脚本、无法识别的入口以及已有的非字面量取值保持不变，并在部署时给出警告。缩容、滚动更新或节点驱逐时，Kubernetes 会先把 Pod 从路由中移除，vLLM 随后最多用 90 秒完成进行中的请求。在此默认配置引入前创建的部署需要重启或重新创建才能获得这些设置。SGLang 不支持该 vLLM 参数，因此仅适用端点移除和终止宽限期。对于 P/D 部署，请先缩容 Decode 再缩容 Prefill。当模型容器包含 `--kv-transfer-config` 时，Lens 会在该 JSON 中设置 `kv_load_failure_policy=recompute`，使 Decode 在 Prefill 的 KV 传输失败时本地重算。

## 为就绪的部署创建本地端口转发

1. 找到一个已经处于**就绪**状态的部署。
2. 在该行中，打开操作菜单并选择**创建本地端口转发**。
3. 等待成功提示**本地端点已连接**出现。
4. 如果你想从工作站调用该服务，可从表格中复制更新后的本地端点。

## 扩缩容部署

1. 在部署行中，打开操作菜单并选择**扩缩容**。
2. 对于 P/D 部署，设置 **Prefill replicas** 和 **Decode replicas**；对于聚合部署，设置 **Replicas**。
3. 点击**扩缩容**。

手动扩缩容只修改运行中的 Kubernetes 模型服务器副本。重启部署后会恢复配置中的副本数。DisaggregatedSet 部署按声明的 `spec.slices` 创建；手动扩缩容只修改角色副本数，永远不修改 `spec.slices`。对于 P/D 部署，请先缩容 Decode 再缩容 Prefill；Prefill 缩容可能中断进行中的 KV 传输，但只要存在 `--kv-transfer-config`，Lens 就会配置 `kv_load_failure_policy=recompute`。

## 对就绪部署运行基准测试

1. 在就绪部署行中打开操作菜单，选择 **Run benchmark（运行基准测试）**。该操作需要 `evaluate:run:create` 权限。
2. 选择负载：**Short chat**（1,024 输入 / 256 输出 token，并发 1、8、32）、
   **Long input, short output**（8,192 / 256，并发 1、8、16）或 **High concurrency**（1,024 / 256，并发 32、64、128）。
3. 可选填写 P95 TTFT 和 TPOT 目标，然后点击 **Start benchmark**。

基准测试通过 `POST /api/v1/evaluate/runs` 并携带该部署的 `deployment_execution_id`，在集群内运行测试程序。
无需选择 Standalone 或 Gateway：服务端会访问部署自己的路由入口，若部署通过共享 Gateway 对外服务则访问 Gateway。
部署本身不会被修改。任务排队后 Lens 会打开基准测试结果页。

## 打开部署监控与性能分析

1. 在部署行中，打开操作菜单并选择**监控**。
2. 如果监控尚未安装，点击**安装**。
3. 如果监控已存在但处于暂停状态，点击**启用**。

   在部署本身就绪之前，**安装**和**启用**均不可用——监控采集的是该部署的 Pod，
   在此之前没有任何数据可采集。等待期间菜单中会给出相应提示。
4. 当监控已启用时，使用**打开 Grafana** 或**打开 Prometheus** 在新标签页中打开相应的仪表盘。
5. 点击**性能分析**，跳转到该部署的性能分析视图。
6. 使用**禁用**可以在不卸载的情况下停止监控。
7. 使用**卸载**可以从该服务中移除部署监控。

## 编辑部署名称与描述

1. 在部署行中，打开操作菜单并选择**编辑名称与描述**。
2. 在**编辑部署**中，更新**显示名称**和**描述**。
3. 点击**保存更改**。
4. 如果你决定不保留这次编辑，点击**取消**。
要修改模型、镜像、资源数量或集群，请[创建新部署](/user-guide/model-market)；
此处只修改名称和描述。

## 模型推理访问

不再支持部署分享。admin 和 maintainer 在其集群 scope 内管理部署。
消费者不能访问部署页面或直接连接部署；请发布模型服务，再通过其
[Manage access 抽屉](/user-guide/model-services#管理模型访问权限)向用户或组授予推理权限。
旧部署授权不会自动转换成模型授权。

## 删除部署

1. 在部署行中，打开操作菜单并选择**删除部署**。
2. 在**删除部署**中，查看**执行 ID**、**集群**和**命名空间**。
3. 如果你希望 Lens 移除该命名空间及其中的所有内容，请保持**同时删除 Kubernetes 命名空间**选中；如果只想移除部署记录，请取消勾选。
4. 在**输入 `<短语>` 以确认**中，输入对话框中显示的确切确认短语。
5. 点击**删除部署**。
6. 如果你不想继续，点击**取消**。

## 找不到部署或操作按钮

先清除搜索、状态和集群筛选。仍然找不到时，请管理员检查角色的部署管理权限和集群 scope。

需要让应用调用已就绪的部署时，继续[发布模型服务](/tutorials/publish-a-model-service)。

## 配置和审阅 Manual 或 Agentic 方案

页面最上方是部署设置卡片：集群、部署名称、模型缓存和 Pod 放置。
存在就绪集群时会预选，部署名称自动生成，模型缓存自动检查。
四项均可在卡片内直接编辑，徽标显示模型缓存状态；模型缓存未就绪时可点击 **Prepare model cache** 准备模型文件。
然后在 **Planning mode** 中选择 **Manual** 或 **Agentic**。**Workload & limits** 始终可见且可选，
占位符显示计算出的默认值（模型上下文长度、全部空闲加速卡、按完整上下文估算 KV），留空即使用默认值；
**Reset to defaults** 清除全部覆盖值。
两种模式都不要求先填写硬件规格或选择 Guide。

**Generate plan**（Manual）在兼容时启用勾选的核心优化，其中 Prefill / Decode 分离默认开启，提供请求形态时由 AIC 决定，并进入配置审阅。

### 验证优化机制

Guide 可用、配置兼容、运行机制有效和性能收益已验证是不同证据层级。
不支持的组合必须保留原因，开启更多参数不等于性能更好。
验证应绑定固定源码版本、运行镜像、硬件与负载。

| 机制 | 必须具备的运行证据 |
| --- | --- |
| 多副本路由 | 共享前缀流量的 EPP 处理记录、各后端请求数与缓存命中，以及不同前缀负载在两个副本上的执行。仅 HTTP 200 不足以证明路由有效。 |
| Prefill/decode 分离 | 两种角色实际处理请求，KV 传输指标或关联传输日志增长，并排除普通合并服务回退。 |
| CPU KV 回读 | 先向 CPU 写入 KV，在隔离测试中仅驱逐设备 KV，重复前缀后观察 CPU 到设备的传输和外部缓存命中。仅 CPU 写入不能证明回读。 |

优先通过受限设备 KV 预算和正常流量触发驱逐，不要仅为重置缓存而开启生产服务的开发或 RPC 接口。
隔离测试部署、记录失败，并只清理这些测试拥有的资源。

## DisaggregatedSet 审核

所选 Guide 支持 DisaggregatedSet 时，配置直接暴露真实 API 字段：`spec.slices`、
`spec.placementPolicy.type`/`.topology`，以及 **EPP Topology Affinity**
（`topology-affinity-scorer` 或 `topology-affinity-filter` 插件）。Prefill 和 decode 副本数都是每 Slice 的数量。资源摘要展开全部 Slice
和 leader/worker Pod，不把 TP 当作加速器资源数量。

Deploy 和 Evaluation 的 P/D 配置都会在拓扑设置下方显示
**Slice Configuration（Slice 配置）**。只有来源被识别为 DS 后才启用参数；加载中、准备失败和
Guide 不包含 DS 时都会明确提示。**Recheck Slice support** 可重新检查官方来源，标题处显示固定的 Guide commit。
仅选择 P/D 不会将基于 Deployment 的 Guide 自动转换为 DisaggregatedSet。

Slice 数和放置策略从 Guide 默认值开始；EPP Topology Affinity 默认选择 Scorer：

- **Max feasible（最大可行 Slice 数）**按所选放置策略根据当前空闲资源估算：`None` 按装箱计算，
  `ExclusiveSlice` 统计可各容纳一个 Slice 的域，`ExclusiveTopology` 再排除已被其他 DisaggregatedSet
  使用的域。点击 **Generate YAML** 之前按 Guide 默认角色估算，之后按生成的角色估算。这不是预留。
- **Recommended（推荐 Slice 数）**只在有匹配证据时出现：同模型、同 Guide、同集群、同加速器、
  每 Slice P/D 副本数与 TP 相同，且记录了 SLO 稳定速率的成功 Evaluation 用例。输入 **Target load（目标负载）**
  后，取当前上限内实测速率满足目标的最少 Slice 数。实测使用了不同负载或 SLO 目标时，在
  **Evidence（证据负载与 SLO）**中选择其一，不同组的结果不会混用；否则显示
  `No verified recommendation — Guide default: N`。仅凭吞吐量永远不会选定 Slice 数。
- **预估资源**按所选 Slice 数乘以每 Slice 请求量；预算检查使用的加速器总量包含全部 Slice。
- **Placement（拓扑与放置）**选择放置类型，从已发现的节点标签中选择拓扑键（或填写其他键），
  并展示每个域的节点、空闲加速器及能否容纳一个 Slice。Guide 通过 DRA claim 申请加速器时，估算不计入这部分，
  域改为显示空闲 CPU 和内存，并提示上限只按 CPU、内存和 Pod 数计算。自定义标签会被标注，因为 Lens 无法验证其
  是否反映物理拓扑；节点标签由编排平台管理员修改，本页不修改。发现的放置方案以 **Suggested（建议）**提供。
- **EPP Topology Affinity** 只有 **Scorer** 和 **Filter** 两个选项。Scorer 为同 Slice 候选加分；
  Filter 在存在匹配项时保留同 Slice 候选。缺少对端拓扑或没有匹配候选时会放行全部候选，
  因此 Filter 并不保证严格的同 Slice 路由。生成配置时，未设置或旧的继承设置会转为 Scorer，
  已有的 Filter 选择会保留。
- **Evaluation evidence（评测证据）**列出近期实测结果，标注每 Slice 形态相同的记录，**Apply** 会复制该结果的
  Slice 数、放置策略和 P/D 参数。

部署 DS 配置会在原部署流程中运行预检，不再打开额外的审核弹窗。检查通过后直接部署；
失败或未知约束显示在页面内的 **Deployment checks（部署检查）** 区域。
其中的 **Slice deployment preview（Slice 部署预览）**显示所选与可行
Slice 数、每 Slice 角色、加速器请求总量、放置策略、EPP 路由，以及模拟的 Slice→域、Pod→节点
放置（实际调度器可能选择其他节点）。工作负载 YAML、Router values 和校验和可在 **Deployment resources（部署资源）** 中展开查看。
失败约束阻止执行（包括找不到可行放置的 Slice 数）。预检无法得出结论时需要明确确认。可行放置并不预留资源或保证集群准入。修改集群或部署输入必须重新
审核。最终计划冻结渲染输入和 Chart 字节，不安装缺失的 DS/LWS 控制器或 CRD。官方 Guide
快照要求将 Kustomize 依赖纳入源码。

本地来源会冻结资源、补丁、生成器输入和 Router values，并记录内容校验和，不将脏文件
误报为 Git HEAD。远程自定义 Kustomize 从精确 commit 快照渲染；外部依赖和越界路径必须
先纳入源码。独立部署的 DS 停止或失败后，可用 **restart-plan API（重试计划接口）**
准备新摘要，不删除旧资源；确认后创建新运行。Evaluation 所有的部署通过工作流重试。

Evaluation 在已审核的 DS 部署开始压测前自动执行有界推理探测。在评估详情的 **Deployments（部署）**
页签中，**Runtime verification（运行时验证）**分别显示 Kubernetes 就绪、Slice 放置、P/D 路由及 KV
传输的状态和原因。**Recorded evidence（已记录证据）**展示采集的 Pod/Node 与请求证据。
部署验证 API 还支持显式推理探测和只读指标快照；指标快照不是实时速率。
Pod 就绪、HTTP 成功、同 Slice 标签和聚合 KV 计数都不能证明单个
请求的传输。缺少关联证据时，路由/KV 状态保持未知。这些检查不认证物理网络带宽或在线滚动升级安全。

对于已注入探针的 vLLM 0.26.0 NIXL pull worker，验证会将响应 ID 与所有 TP rank 的接收完成、
发送端确认关联，检查 Pod/引擎稳定性及 P/D revision，并排除传输失败后重算。报告记录实际
P/D Pod、是否同 Slice/域及传输块数，以带校验和的部署证据持久化；重新打开详情仍可查看。
不支持的版本、连接器或不完整证据保持未知。

修改 Slice 数仍需新建配置并重新审核。

使用 Router 0.11 的 P/D 部署在创建或重试时会自动适配旧版插件设置。原始配置会被保留，部署诊断信息会记录实际生效的 Router 值。旧版 `disagg-headers-handler` 条目会被 profile handler 的内置请求头处理逻辑替代，同时保留已保存的 prefill/decode 决策。如果新旧 decider 设置存在冲突，必须在部署前修正。

## 硬件配置与 Guide 变体

部署渲染通过硬件配置注册表（profile registry）解析硬件。所选配置会提供运行时镜像、调度标签、加速器资源请求以及 PCI 选择能力。自定义运行时镜像仍由用户控制；未知硬件不会静默选用其他厂商的默认配置。

Guide 变体来自所选 llm-d 仓库修订版本中的实际 Kustomization 入口（包括嵌套 overlay）。更换硬件或来源可能会改变可用变体。列表中的 overlay 仍可能需要 NIC 设备类、存储或运行时支持等集群资源；规划阶段会在部署前校验这些要求。

自动通用入口选择优先使用根目录（`.`），其次是 `base`。如果两者都不存在，部署会报告 Guide、硬件配置和可用变体，而不会静默选择特定平台的 overlay。请选择兼容的 Guide 来源，或在支持的情况下显式选择列表中的变体。

Agentic 分层前缀缓存（tiered prefix cache）会请求原生 CPU 缓存，而不绑定特定源码目录结构。Lens 会从所选来源解析 `native/cpu` 或 `native/cpu/base`，并兼容旧路径。缺少原生 CPU 入口时会报错；Lens 绝不会替换为其他缓存实现、存储层级或平台 overlay。

部署列表会取消被新请求覆盖的旧筛选请求，确保旧结果不会替换当前选择。可用时会显示集群名称，否则回退显示 ID。删除操作仍要求输入显示的确认短语并保留命名空间选择；删除进行中时，提交按钮和弹窗关闭会被禁用。

为部署规划指定操作偏好时，请使用英文，例如 `prefer prefix cache`、`more GPU for performance` 或 `use fewer GPU resources`。确定性规划器仅匹配英文偏好关键词，不再支持中文关键词别名。

## 验证配置驱动的 Guide 配置

选择一个已下载软件版本（Software Versions）的集群并刷新页面。硬件配置会选择 Guide 源码根目录；所选 llm-d 检出版本会提供其模型服务器和 Kustomization 变体（包括嵌套路径）。根 overlay 会显示为 `Default (vllm)` 或 `Default (vllm-rdma)`，而不是 `.`。在编辑其他字段时，所选的同级运行时变体保持稳定。

对于官方来源，准备源码后会出现缓存与 NIC 控件：CPU 容量要求渲染后的容器中存在受支持的缓存连接器；NIC 数量要求与硬件配置中 NIC 设备类匹配的声明。部署前请检查生成的 YAML 与来源溯源信息。访问模式设置来自 `deployment.modes`：DRA 使用设备声明，插件模式使用声明的扩展资源。用户选择的运行时镜像仍作为覆盖项保留。

在 Evaluation 结果中打开 **Resources during benchmark**。即使引擎指标可用，设备分配失败也会显示原因。插件设备指标需要 kubelet 上报且被硬件配置识别的设备标识；仅靠 exporter 无法确定哪些设备属于该工作负载。修改硬件配置文件后需要重启开发服务并刷新页面，它不是实时生效的 JSON 编辑器。已保存的历史结果不会重新采集。

## 审阅生成的部署配置

Manual 使用上文所述源码编辑器，可明确排除前缀缓存或分块预填充，不虚构负载特征。
补全只修改源码支持的设置，不可用选项在指南和优化列表中保留原因。
显式运行参数优先。跨 Guide 组合支持同一固定官方版本中的“优化基线、精确路由或 NIXL P/D + 原生 CPU KV 缓存”，要求运行镜像相同。P/D 的 Prefill 和 Decode 均使用 MultiConnector，按顺序保留原 NixlConnector 并添加 OffloadingConnector，保留传输设置并为每个模型 Pod 预留本地缓存内存。同镜像初始化容器在启动前检查连接器导入及配置结构，并拒绝已知存在卸载缺陷的 vLLM 0.19.0（上游 #39500/#39617）。该检查不代表 GPU 正确性或性能验证。不支持的传输返回具体适配器错误，不支持任意连接器叠加。生成组合配置不代表性能最优。

P/D 的 CPU 缓存适配器目前要求两个角色均使用 `NixlConnector` 和 `kv_both`。
使用 `kv_producer`、`kv_consumer` 的源码仍可用于不叠加 CPU KV 卸载的 P/D 候选；
被拒绝的仅是额外缓存组合。Lens 不会改写这些传输角色，也不会静默删除用户明确要求的缓存功能。

通过节点参数按钮或 **All deployment parameters（全部部署参数）**编辑，再点击
**Apply changes and check resources（应用修改并检查资源）**。Manual 和 Agentic 均保留
已审阅源码包；编辑器不会悄悄把参数修改交给 LLM 或替换为其他候选。
只有明确重建负载需求时才请求新推荐。选择候选不是部署，**Review & deploy**仍需确认。

## 实测比较 Agentic 候选

打开 **Verify with real benchmarks**，选择候选，填写 GPU 上限、最长分钟数、
压测运行次数和重复次数，再选择吞吐、P95 端到端延迟或每加速器吞吐作为目标。
源码候选需要已审阅的推理 Service 和已渲染缓存变体。只有旧计划仍提供可选 CPU
缓存预算来增加测试变体，其运行次数预算应包含额外测试。
合成负载优先使用方案的平均输入 / 输出长度和并发；缺失时分别采用输入 512 token、
输出 128 token、并发 4，请求数为 100。恢复的测试使用已记录的负载。展开
**Test workload** 可修改，或填写代表真实业务的 inference-perf YAML；
缓存实验建议使用能体现前缀复用的实际负载。

**Start deployment and benchmark tests** 会创建真实集群资源。每个候选按相同
负载重复压测，清理后再测试下一个。只有完成全部重复且满足延迟 SLO 和错误率
约束的候选才进入排名；缺少指标和失败测试不会被当作优势证据。结果保留压测 ID，
选择最佳已测候选后，仍需要审阅并确认最终部署。

**Stop and clean up** 停止任务。清理可能超过测量预算；清理失败会阻止继续部署。
任务审计保留配置、负载和进度。服务中断后，任务标为中断并提供显式清理入口，
不会自动恢复部署。同一浏览器会话刷新页面可恢复当前方案。这是有预算的候选
搜索，不是无限自主调整或全局最优证明。

Overview 和 3D 分别展示每个角色的传输及本地 CPU 缓存。Agentic 的 CPU 缓存试验包含符合条件的 P/D 候选，使用相同负载比较原配置与组合配置。默认 NIXL 优先的顺序在多个连接器均命中时优先传输，不保证减少网络传输；正确性及性能仍需实际测量。

## 非管理员（`edit`）集群部署规划

当集群使用命名空间级非管理员（`edit`）kubeconfig 时，集群范围的 Kubernetes 资源读取（`kubectl get nodes`、`kubectl get pods --all-namespaces`）可能返回 `403 Forbidden`。在部署规划、切片放置和目标检查期间，Lens 会自动回退到基于 Prometheus 合成的节点与可分配加速器库存，从而在不出现 `403` 失败的情况下继续执行硬件配置驱动的 GPU/XPU 调度与容量检查。真实的 `401 Unauthorized` kubeconfig 错误不会被掩盖，会立即向上暴露，以便刷新或更换集群凭据。

## 按命名空间的权限预检与编排平台管理员命名空间初始化

每次部署都会使用独立的 Kubernetes 命名空间（`<deployment-ns>`）。在部署前，Lens 会执行按命名空间的 SubjectAccessReview（SSAR）预检：

- **管理员 kubeconfig**：当所有必需的命名空间、工作负载和 RBAC 检查均通过时，部署直接继续，无需额外步骤。
- **非管理员（`edit`）kubeconfig**：如果 `<deployment-ns>` 或其命名空间级 RBAC 缺失，Lens 会暂停在**编排平台管理员命名空间初始化**阶段，并生成一份自包含、幂等的 bash 初始化脚本（不包含任何明文密钥）。
  1. 下载或复制该初始化脚本并交由编排平台管理员运行。脚本会创建 `Namespace`、面向检测到的 kubeconfig 身份（或在无法自动检测时使用显式主体覆盖）的命名空间级 `Role` 与 `RoleBinding`、按命名空间的 EPP `system:auth-delegator` `ClusterRoleBinding`、在配置存储时创建可选的静态 `PersistentVolume` 与绑定的 `PersistentVolumeClaim`，以及非密钥的 `lens-deployment-bootstrap` 标记 `ConfigMap`。
  2. 点击 **Re-check & Deploy** 验证初始化标记与权限。
  3. 验证通过后，Lens 会将工作负载部署到 `<deployment-ns>`，在配置了 `hf_token_secret_namespace` 时从中复制 `HF_TOKEN`，并启用命名空间级 `ServiceMonitor`/`PodMonitor` 资源。

## 非管理员集群上的两阶段部署删除

在非管理员（`edit`）集群上删除部署采用两阶段流程：

1. Lens 首先删除 `<deployment-ns>` 内的所有命名空间级工作负载与配置资源。
2. 如果删除 `Namespace` 或其按命名空间的 `ClusterRoleBinding` 返回 `403 Forbidden`，Lens 会展示**编排平台管理员命名空间清理**交接界面。下载或复制生成的清理脚本交由编排平台管理员运行，然后点击 **Re-check & Delete** 确认移除并删除 Lens 部署记录。（若无法验证标记，可使用 **Confirm & Delete Record** 在手动清理后删除 Lens 记录。）

## 相关参考

在部署创建流程中，展开已验证备选方案下的 **Why this option**，可在存在精确拓扑估算时查看其 AISimulate TTFT、TPOT 和吞吐量估算。即使 AISimulate 候选搜索未找到满足原始 SLO 的配置，该估算仍可能显示；此时备选方案仍会标注 **SLO not met**。没有匹配估算的备选方案会提示无可用的精确 AISimulate 预测。

Agentic 候选旁显示的 **AI score** 是满分 100 的相对排序分，最高分候选归一化为 100。它不是基准测试结果、置信度或满足 SLO 的概率。确定性回退方案会改为显示 **Deterministic score**。

**Recalculate selection** 无需 AI provider 即可工作。它会使用确定性规划和新的偏好刷新推荐结果；如果 AI 评分失败，备选方案也会保留确定性评分。

Agentic 备选方案会使用所选的 vLLM GPU 显存利用率和最大模型长度进行检查。部署启动时会应用相同的值；实际可用 KV 缓存由 vLLM 在启动时测量，仍可能低于规划估算值。

如果在部署创建流程中使用 Agentic 规划器，请参阅[架构概览](/architecture)了解负载驱动规划的工作原理。
