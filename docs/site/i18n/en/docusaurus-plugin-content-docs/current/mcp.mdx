---
title: MCP integration
description: Connect an MCP client (MCP Inspector, an IDE agent, or your own tool) to Lens' MCP server.
---

Lens exposes its platform capabilities as a **Model Context Protocol (MCP)** server,
so an MCP-capable client can inspect and operate Lens the same way the built-in
[Lens Assistant](/user-guide/lens-assistant) does. The MCP layer is a **thin adapter**:
every tool calls Lens' own REST API over loopback — no cluster, auth or domain logic is
re-implemented in the MCP server.

## Endpoint and transport

| Property | Value |
| --- | --- |
| Method / path | `POST /api/mcp` (on the Lens BFF/Node server) |
| Default port | `SERVER_PORT` / `PORT` (3000; `scripts/lens-local.sh` picks the next free port above it if 3000 is already in use) |
| Transport | MCP **Streamable HTTP**, JSON-RPC 2.0 |
| Session | **Stateless** — one ephemeral MCP server per request, no `Mcp-Session-Id` |
| Other methods | `GET` / `DELETE /api/mcp` return `405` (no server→client stream in stateless mode) |

The endpoint is stateless on purpose: it scales horizontally and every tool re-reads
**live** data from the REST API, so responses always reflect the current state.

## Authentication

`POST /api/mcp` requires a **signed-in session** that holds one of these permissions:

- `mcp:tool:invoke`, or
- `playground:chat:use`

Send the session either as the browser cookie **`prism_session`** or as a bearer token:

```
Authorization: Bearer <session-token>
```

`<session-token>` is the value of the `prism_session` cookie issued at login (read it from
your browser's devtools while signed in). Requests are introspected against
`GET /api/v1/auth/session`; unauthenticated calls get `401 unauthenticated`, and a session
without the permission above gets `403`.

:::note
A dedicated credential for **third-party** MCP clients (API key / OAuth scope) is a
planned, separate design — today external clients reuse a signed-in session. See
`docs/design/mcp-playground-design.md` (Phase 4) for the open questions.
:::

## Tools

The catalog is generated from Lens' REST surface and grouped by domain. Each tool carries a
**risk tier**:

| Tier | Meaning | Examples |
| --- | --- | --- |
| `read` | Read-only inspection | `list_clusters`, `list_deployments`, `get_deployment_pod_logs`, `get_flow_map_metrics`, `list_storage_volumes`, `search_huggingface_models` |
| `write` | Changes state (create / start / stop / install) | `create_simulation_task`, `start_cluster_bootstrap`, `create_standard_vllm_deployment_run`, `install_gpu_driver`, `create_ai_provider` |
| `approve` | Destructive; needs explicit confirmation | `delete_cluster`, `delete_configuration_artifact`, `delete_deployment_execution`, `delete_evaluation_workflow`, `delete_ai_provider` |

Discover the exact, current list at runtime with `tools/list` (names change as modules
evolve). All tools return JSON; a failing call comes back as an MCP error result
(`isError: true`) whose message is the underlying REST error.

## Connect a client

### Public benchmark evidence

`query_public_benchmark_rag` is a generated **read** tool wrapping
`POST /api/v1/benchmark-rag/query`. Its arguments are the REST request body, and
its text result contains the same JSON evidence response, including Decimal
strings, citations and abstentions. It is available in Lens Assistant read-only
mode, but is **not** part of the Agentic Deployment planner's tool allowlist.

The MCP invocation permission above is necessary but not sufficient:
`benchmark-rag:query:read` must also be granted at **GLOBAL** scope. Only GLOBAL
admins receive it by default; other roles need an explicit GLOBAL grant. Cluster
grants, anonymous callers and the disabled-auth `system` sentinel cannot query.
The adapter signs the actual authenticated caller through the existing internal
HMAC transport; tool arguments cannot supply an identity.

By default, only published public sources are searched: the approved Prism public snapshot,
`VincyZhang/llm-d`, and `llm-d/llm-d-benchmark`. The deployment must have the
published corpus **and its immutable source archive** restored; a database-only
copy is insufficient. `include_internal` is a boolean defaulting to `false`;
without opt-in, there is no internal data, count or identity access.
With `include_internal: true`, authorized stored Agentic evaluation measurements
may also be returned. The GLOBAL RAG grant is still required, together with the
existing `evaluate:run:read` policy in each record's verifiable owning context;
missing/deleted/unverifiable owners are excluded even for admins.
`internal_branch_enabled` reflects opt-in, not permission to every internal record.
The endpoint, operation ID, read tier and planner exclusion remain unchanged.
Answers use `generation_mode: "deterministic"`, not an LLM generation path.
Question planning uses bounded deterministic keyword rules,
not general NLP or LLM inference; explicit structured filters are authoritative.
Automatic keyword rules are English-only. For questions in other languages,
provide explicit `intent` and structured `filters`; language is not inferred.
Figure evidence can include `related_experiments` for explicitly linked
published scenarios; the adapter never guesses experiment identities.
Evidence origins are `public`, `agentic` or `public_and_agentic`. Internal
`agentic_measurement` citations preserve owning-evaluation provenance and declare
`numeric_precision: "stored_float"`: Decimal strings reflect stored Float values,
not exact source tokens. Public raw-byte precision is unchanged.
Only canonical `evaluate:<UUID>` identity in pinned public raw JSON plus matching
metric/statistic/unit/value permits a merge; the public citation and internal
`corroborating_citations` are retained with
`identity_verification: "canonical_evaluate_run_and_metric"`. Unknown overlaps
stay separate, and unauthorized overlaps do not leak. Legacy eight-character
simulation task IDs cannot establish evaluation ownership and are omitted.
`limit` (1–50) bounds total returned envelopes after merges;
`returned_observations` counts those envelopes, while `matched_items` counts
candidate public index items plus authorized internal benchmark records, not
independent experiments or exact distinct runs. `truncated` explicitly reports
omitted results.
Denied, unavailable or malformed upstream results produce
explicit tool errors, not empty successful answers.

See the [request, filters and response contract](/api-reference/modules/lens-assistant#query-public-benchmark-evidence).
This integration has focused local automated coverage; a real deployment has
**not yet been verified**.

Evidence refresh is deliberately **not** an MCP write tool. Trusted
administrators can use the shared target-local `admin refresh` command for
manual Prism snapshots and reviewed commit/periodic repository jobs.
Plans pin full inventories, hashes, counts and publication generations; failures
preserve the current release, and old periodic plans cannot undo rollback or
revocation. See [refresh administration](/api-reference/modules/lens-assistant#administer-reviewed-benchmark-refreshes).
The [fixed evidence baseline](/api-reference/modules/lens-assistant#evaluate-the-fixed-evidence-baseline)
replays known questions, exact values, refusals and authorized internal cases
with independent citation checks. A passing baseline never auto-approves a new
origin, external URL or paper.
The optional internal branch and its owning-Evaluate permissions are unchanged;
simulation/benchmark ingestion improvements are deferred.

### MCP Inspector

1. Start the Lens dev stack (`scripts/lens-local.sh start`).
2. In MCP Inspector choose **Streamable HTTP**, URL `http://<lens-host>:3000/api/mcp`.
3. Add header `Authorization: Bearer <session-token>`, then **Connect** and list tools.

### Generic MCP client config

```json
{
  "mcpServers": {
    "lens": {
      "type": "http",
      "url": "http://<lens-host>:3000/api/mcp",
      "headers": {
        "Authorization": "Bearer <session-token>"
      }
    }
  }
}
```

### Raw JSON-RPC

```bash
BASE=http://<lens-host>:3000/api/mcp
H="Authorization: Bearer <session-token>"

# 1) handshake
curl -s $BASE -H "$H" -H 'content-type: application/json' -d '{
  "jsonrpc":"2.0","id":1,"method":"initialize",
  "params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'

# 2) list tools
curl -s $BASE -H "$H" -H 'content-type: application/json' -d '{
  "jsonrpc":"2.0","id":2,"method":"tools/list"}'

# 3) call a read tool
curl -s $BASE -H "$H" -H 'content-type: application/json' -d '{
  "jsonrpc":"2.0","id":3,"method":"tools/call",
  "params":{"name":"list_clusters","arguments":{}}}'
```

## Notes

- Tools are read/write/approve; the `approve` tier should only be invoked behind a human
  confirmation step (as the Lens Assistant UI does) — an agent must not auto-approve.
- The MCP server never talks to clusters directly: it calls Lens REST, which applies the
  same authentication, RBAC and scoping rules as the UI.
- Because the transport is stateless, a new `initialize` is not required per call, but every
  request must still carry the credentials above.
