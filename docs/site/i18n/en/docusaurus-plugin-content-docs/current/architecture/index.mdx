Lens has a unified server control plane paired with a standalone engine CLI and a
cluster-local inference data plane:

- **Web GUI & Agent MCP (`apps/frontend` + `apps/backend`)**: A single-process Python
  FastAPI backend (`llm_d_lens`, default port `3000`) serves the built React UI
  (`apps/frontend`; Vite `:5173` in development), the REST API, RBAC and audit
  enforcement, the external Agent Task MCP endpoint (`POST /api/mcp`), and the
  internal Lens Assistant tool catalog (`/api/assistant/mcp`). It owns domain logic,
  PostgreSQL persistence, artifact storage, cluster operations, and model-service
  reconciliation.
- **Standalone `llmd` CLI (`apps/lens`, `llm-d-lens-engine`)**: A pure-Python
  (3.11+ & `PyYAML` only) client that drives `kubectl`/`oc`, `helm`, `git`, and
  `kustomize` directly against a Kubernetes/OpenShift namespace without any Lens
  server, database, or Node process (`llmd` is the full CLI; `lens` is currently a
  `--version`/`--help` stub).
- **Cluster data plane**: Model inference traffic bypasses the Lens server and flows
  directly to each cluster's shared llm-d Gateway (`Istio` or `Envoy AI Gateway`),
  authorized by `lens-authz` and routed via `HTTPRoute / Inference Payload Processor (IPP)`
  and `EPP` to `InferencePool` Prefill/Decode `vLLM` pods.

## Layers

| Layer | Responsibility |
| --- | --- |
| Clients & usage paths | **Web GUI** (`apps/frontend` in browser), **Agent Tools** (`opencode`, Claude Code, Cursor, Codex calling `POST /api/mcp`), **Standalone `llmd` CLI** (`apps/lens` directly against Kubernetes), and **Model clients** (OpenAI/Anthropic SDKs or `curl` calling published gateways). |
| Unified Python backend (`apps/backend`, `llm_d_lens`) | Serves the Web UI, REST API, session/PAT authentication (`lens-pat-*`), RBAC and per-cluster scoping, audit logging, `/api/mcp` (46 task tools across 6 profiles), `/api/assistant/mcp` (internal assistant & planner catalog), domain services, deployment planning, cluster operations, and model-service control plane. |
| Data plane | A cluster-local shared llm-d Gateway (`Istio` / `Envoy AI Gateway`, selectable at cluster creation) with `lens-authz` (`ext_authz`) and per-model `HTTPRoute / Inference Payload Processor (IPP)`; each deployment owns an `InferencePool` + Endpoint Picker (`EPP`, `ext_proc`) and `vLLM` Prefill/Decode replicas. |
| Storage | PostgreSQL (embedded or external) for application state, RBAC, catalog entries, and API keys, plus file/artifact storage for deployment bundles, plans, traces, and benchmark logs. Standalone `llmd` stores per-instance state in namespace-local `ConfigMap`s (`lens-instance-<name>`). |

## Request flow

1. **Web GUI (`apps/frontend`)**: The browser calls same-origin `/api/...` routes on the unified Python backend (`llm_d_lens`).
2. **Agent Tools (`POST /api/mcp`)**: External agents (`opencode`, Claude Code, Cursor, Codex) send stateless Streamable HTTP JSON-RPC requests with `Authorization: Bearer lens-pat-*`. Internally, Lens Assistant and the agentic planner call `/api/assistant/mcp`.
3. **Auth, RBAC, and domain execution**: The unified Python backend resolves the caller's session or PAT, enforces route permissions (`mcp:tool:invoke` or `playground:chat:use` for MCP) and CSRF checks, reads or writes PostgreSQL and artifact storage, and runs cluster operations narrowed to the clusters the caller can reach.
4. **Standalone `llmd` CLI (`apps/lens`)**: Runs locally with the caller's kubeconfig, executing `helm template`, `kustomize`, and `kubectl`/`oc` directly inside a single namespace (`Applying → Applied → Deleting → Removed`).
5. **Model inference (data plane)**: Model clients call the cluster-local Shared Gateway directly with `Authorization: Bearer lens-mk-*`; `lens-authz` authorizes the key, `HTTPRoute / IPP` matches the model route, and `EPP` selects a target endpoint in the deployment's `InferencePool`.

## Access model

Access is modeled around a principal with role bindings at global, cluster, or resource scope. A global admin reaches every cluster; a cluster-scoped maintainer reaches only the clusters granted to them. Requests are denied by default, each route maps to a required permission, and the same scoping applies consistently across Web UI pages, REST endpoints, and `/api/mcp` tools. For cluster onboarding without `cluster-admin` permissions, Lens runs preflight checks and splits cluster-scoped prerequisites into an orchestration administrator handoff script.

## Deployment planning

Agentic deployment planning is a deploy-time, retrieval-augmented recommendation step rather than a runtime scheduler. It validates a request, gathers live cluster facts, and retrieves supporting evidence from capacity estimates, prior deployments, completed **Trace Replayer** runs, and **Evaluation** benchmark results. It then ranks only validated candidates and stores a recommendation; nothing is deployed until a person approves it.

For design details, see [Agentic deployment](/architecture/agentic-deployment)
for the planner and approval flow, and [Planning evidence and RAG](/architecture/agentic-planning-evidence)
for evidence sources and retrieval.

## Model service gateway

The model service gateway publishes cluster deployments as OpenAI- and Anthropic-compatible services behind the cluster-local shared llm-d Gateway. The unified Python backend manages **Model Services**, providers, `lens-mk-*` keys, and usage, and installs the shared Gateway at cluster creation; `lens-authz` authorizes each request and `HTTPRoute / IPP` + `EPP` route it to the model service's `InferencePool`. Deployments keep their own `InferencePool` + `EPP` without running a separate proxy.
