## Install online

On Ubuntu 22.04 LTS or newer (x86_64), download and run the online installer.
No repository checkout is needed. Run it as the intended service user, not with
`sudo bash`; it requests sudo only for missing system packages.
The download entry requires Bash, `curl` or `wget`, CA certificates and `python3`
(`sudo apt-get install curl ca-certificates python3` if missing).

Set `VERSION` to `main` for the development version, or replace it with an actual
release tag such as `vX.Y.Z`. Only tags containing the online installer are supported.

With **curl**:

```bash
VERSION=main && curl -fsSL "https://raw.githubusercontent.com/llm-d-incubation/llm-d-lens/${VERSION}/scripts/LensInstaller-Ubuntu-x86_64-online.sh" | bash
```

Or with **wget**:

```bash
VERSION=main && wget -qO- "https://raw.githubusercontent.com/llm-d-incubation/llm-d-lens/${VERSION}/scripts/LensInstaller-Ubuntu-x86_64-online.sh" | bash
```

The installer reads interactive input from `/dev/tty`. After validating the source
archive, it saves `LensInstaller-Ubuntu-x86_64-online.<unique-id>.sh` in the current
directory and prints the path; existing files are not overwritten. Use a writable
working directory. The complete script body must arrive before it can execute.
In automated Bash shells, enable `set -o pipefail` so downloader failures also
produce a nonzero pipeline status.

Interactive mode asks for the install directory (default `$HOME/llm-d-lens`) and
one app/API port (default `3000`); press Enter to accept each default.
The installer downloads a commit-pinned source archive, then provisions Node,
Python 3.11+ and a virtualenv, configures PostgreSQL, builds the app and sets up TLS.
If a compatible Python is missing, it uses pinned uv to install private Python 3.12
under the installation's `.tools/`; system Python is unchanged.
It accepts only a new or empty install directory, not an existing installation.

### Version selection

The script embeds its source version; no version argument is needed or accepted.
`main` installs the development branch as it exists when the script runs. Release
scripts install their tagged source. Both resolve to a commit SHA before downloading;
the installed `.lens-version.json` records the version, SHA and installation time.
Source pinning does not lock every transitive npm/Python dependency.

### Network and failures

Allow HTTPS access to `raw.githubusercontent.com`, `api.github.com`, `codeload.github.com`,
Node.js and package registries, and Ubuntu package mirrors. Private Python provisioning
also downloads from GitHub release assets. Existing `HTTP_PROXY`, `HTTPS_PROXY` and
`NO_PROXY` settings are inherited; certificate verification remains enabled.
If sudo filters proxy variables, configure apt's proxy separately.

Logs are private files under `$LENS_LOG_DIR` (default `~/.local/state/lens/logs/`).
They can contain installer-generated database credentials; do not publish them.
Temporary downloads use `$LENS_SCRATCH_DIR` and are removed on exit. Downloads and
archive checks finish before the install directory is changed; later failures may
leave a partial installation, which is retained for diagnosis. There is no automatic
upgrade, rollback or deletion of that directory. GitHub API rate-limit/network failures
are reported without falling back to another version.

For scripted or CI installs without a terminal, replace the final `| bash` with
`| bash -s -- --silent`.

Other installer options can follow `--silent`. A saved script can still be run
directly with `bash <saved-script-path> [options]`.

Common options:

| Option | Purpose |
| --- | --- |
| `--install-dir DIR` | Install location (default `$HOME/llm-d-lens`). |
| `--app-port PORT` | Web app/API port (default `3000`). |
| `--backend-port PORT` | Legacy alias for `--app-port`; both select the same listener. |
| `--no-https` | Serve plain HTTP instead of auto-HTTPS (self-signed cert). |
| `--no-start` | Install without starting services. |
| `--db-mode embedded\|external` | Use the built-in database or an external one. |
| `-h, --help` | Show every option. |

When auto-HTTPS is enabled, the installer-generated `lensctl.sh` and the local source launcher also enable unverified TLS for the model Gateway's internal `lens-authz` hop (`LENS_MODEL_GATEWAY_AUTHZ_TLS_INSECURE=1`), because the cluster does not trust the self-signed certificate. This is a development convenience and disables certificate verification for that hop, so a network attacker could impersonate authz and forge identity. Use it only on a trusted network. See [Environment variables](/environment-variables) for the security warning and how to disable it.

## Manage the installation

The installer writes `lensctl.sh` into the install directory:

```bash
"$HOME/llm-d-lens/lensctl.sh" start
"$HOME/llm-d-lens/lensctl.sh" status
"$HOME/llm-d-lens/lensctl.sh" stop
```

To remove an installation, run `"$HOME/llm-d-lens/lensctl.sh" uninstall`;
data is kept by default. Use `--purge` to remove data as well, or `--keep-data`
to skip the data prompt. Embedded database retention is controlled separately by
`--keep-db` / `--purge-db`. The online installer itself does not accept uninstall flags.

To upgrade an existing installation instead of a fresh install, see
[Upgrade](/upgrade).

## Install and run from source

From the repository root, use the local source launcher instead of the
Ubuntu installer's packaged deployment:

```bash
hack/lens-local.sh start
hack/lens-local.sh status
```

The launcher prepares Node.js, npm dependencies and the Python environment,
then runs the source frontend on port `5173` and the unified Python API on `3000`.
This serves source code through Vite; it does not replace the production build
command below. `npm run dev` and `npm run dev:web` start both development processes.
After `npm run build`, `npm start` serves the built frontend, API and MCP from
the Python process on one port. Node is needed for frontend builds, not production serving.

`hack/lens-local.sh start` and `restart` regenerate and validate the reuse map before
changing services. Invalid registrations block startup without stopping existing
services; pending user decisions warn without being resolved automatically.
To constrain deployments to a node, pass `--target-node NODE` and optionally
`--kubeconfig FILE`, or set `TARGET_NODE` and `KUBECONFIG`. No target-specific
configuration file is needed. See the [CLI Reference](/cli-reference) for
preflight requirements and every `hack/lens-local.sh` subcommand.

## Optional BLIS exact-estimate runtime

BLIS is not installed by the online installer or backend Python dependencies.
AISimulate remains the default. BLIS installation is a separate, explicit step
on a compatible POSIX host, as the same user and with the same `LENS_CACHE_DIR`
as the backend. No API request downloads, builds or installs a runtime.

Obtain the audited binary and complete input tree from your administrator.
This procedure does not provide a public binary download or build arbitrary
source revisions. The accepted binary is the experimental `762f1605` baseline;
its SHA-256 must be
`c701b5577e06009157c268e19532c0d598576288c40d9f4a95ce515edc529d16`.
The recommended input tree includes all 42 model entries from `blis-catalog`
commit `b5550f750cb51571498577fbdc1c68f78cda67db`, with catalog digest
`ce4886a01c27882c2481aea2f3cac13758d2fc3e3661b71b7ca25ee4dd985923` and whole-input
digest `98cf41670c054d2c98a666381dd57826862ea64a7e8e2dd611e34af9fbce2fd1`.
The original 24-model input tree remains accepted with whole-input digest
`28cc378251abb2bd6be3035bee5ac2c29c1cf42ee2e45afd57a297cfee88ee3a`.
Both profiles keep the same binary and registry locks. Installation recognizes
only these known input locks; it does not trust a digest supplied by the caller.
A different build, even from the same commit, is not accepted automatically.

From the installed Lens directory:

```bash
.venv/bin/python -m llm_d_lens.estimate_tools.blis.install install \
	--binary /absolute/path/to/audited/blis \
	--inputs /absolute/path/to/audited/inputs
.venv/bin/python -m llm_d_lens.estimate_tools.blis.install check
```

Installation validates the locks, copies into private staging, executes the
confirmed eight-request baseline, validates its result and publishes the runtime
under `$LENS_CACHE_DIR/estimate-tools/managed-blis-762f1605` (the default cache root
is `~/.cache/lens`). Failed verification removes staging; existing installations
are never overwritten. The copied inputs and installation record belong to this
optional cache, not the database. Restart the backend after installation; source
users use `hack/lens-local.sh restart backend`, packaged users use `lensctl.sh`
to stop and start the application. Runtime discovery is process-cached.

Alternatively, explicitly set **both** `LENS_BLIS_BINARY` and `LENS_BLIS_INPUTS`
in the backend service environment to administrator-managed absolute paths and
restart it. These paths take precedence over the installed cache and must satisfy
the same locks. Neither `PATH` nor `LENS_TEST_BLIS_*` enables product execution.
To disable the optional runtime, stop the backend, unset both explicit paths,
move the managed runtime directory outside this discovery location and restart.
Moving files does not affect an already running process.

To upgrade an existing installation, first obtain and verify the full-catalog
artifacts, stop the backend and move the old managed directory to a backup
outside the discovery location. Install and check the new artifacts, then start
the backend. Keep the backup for rollback; do not merge files into an installed
runtime or edit its installation record. Saved explicit runtime profile IDs are
not automatically rewritten to the new full-catalog profile.

Model names must match a catalog ID or its declared complete source repository,
case-insensitively. The full catalog is complete for this pinned revision, not
for all Hugging Face models; it still has no `Qwen/Qwen3-8B` entry. Catalog
presence is not certification of every hardware/topology combination or prediction
accuracy. Native construction and per-request validation remain required.

The pinned full hardware catalog contains `a100-80`, `a100-sxm`, `b200`, `b300`,
`gb200-nvl72`, `gb300`, `h100`, `h200` and `l40s`. `a100-80` is explicitly an
alias of A100 SXM, and `h100` describes H100 SXM5; neither is a PCIe entry.
Discovered A100/H100 PCIe devices therefore remain unsupported by this BLIS
profile. Do not select an SXM identity merely to make support pass. Device names
must match a catalog ID or an explicitly approved runtime alias, ignoring case
and treating whitespace and underscores as hyphens. The pinned profiles map
`h100 sxm`, `h100_sxm` and `h100-sxm` to `h100`; they do not map H100 PCIe.
Arbitrary vendor product labels are not automatically equivalent to catalog IDs.

In Configuration, **Exact estimates** lets you select AISimulate, BLIS or both.
AISimulate-only shows native mean token lengths and readable accelerator choices,
mapped internally through hardware profiles. BLIS adds explicit workload, load,
prefix and run controls, plus runtime declarations. Selecting both separates
common inputs from BLIS controls and reports semantics AISimulate cannot represent;
it never drops settings or rewrites the workload to make the tools agree.
Connected cluster information prefills unambiguous accelerator identity and known
uniform node capacity. Unknown or heterogeneous capacity stays blank. Saved inputs
and manual edits take precedence over later discovery. These remain declared
simulation inputs, not resource reservations or verified simulator matches.
Engine versions are simulation declarations, not detected cluster versions. When
BLIS is selected and the version is blank, the panel prefills it from the confirmed
inputs of a unique available managed runtime with a matching engine kind. This
does not overwrite saved or manually edited versions, including a manual clear.
Check support for the explicit topology and workload before
estimating. Results retain independent execution statuses, constraint assessments,
metric definitions and provenance. Cancel aborts the request; editing inputs
clears previous results. Tool choice is saved with the configuration. Saving
declared simulation inputs is optional and requires matching the rendered manifest.

The panel exposes runtime capabilities and confirmed reference configurations.
The confirmed baseline uses constant
128-token input and 32-token output at 2 requests/second, seed 42, 8 requests,
a 60-second horizon and a 30-second request deadline, with no shared prefix.
This is an installation reference, not a request whitelist. Aggregated estimates
may use other models and hardware present in the locked catalog, with compatible
precision/quantization, fabric, topology, vLLM `0.32.0` settings, constant workloads
and explicit run controls. Model source repository aliases must be declared in
the catalog. Multi-node estimates need an explicit catalog fabric; missing
hardware variants such as `h100_pcie` remain unsupported, not approximated by
`h100` SXM. Native-mean workloads are not silently converted. See the
[estimate API](/api-reference/modules/deployments)
for mapping and capability rules.

Runtime availability alone does not establish request support, and compiler
support is not exact-input execution evidence or prediction-accuracy validation.
The installation still verifies the reference case, not every catalog combination.
P/D, search,
capacity, replay and merged rankings are not enabled. Unsupported inputs are
reported per tool without falling back to AISimulate. Existing AISimulate
recommendation routes and Agentic recommendation behavior are unchanged.

```bash
npm run build
npm run type-check
make test-js
make test-python
```

## Documentation site

This site is built with [Docusaurus](https://docusaurus.io/). Preview it locally
with hot reload:

```bash
npm run docs:dev
```

Validate configuration and page paths:

```bash
npm run docs:check
```

The Python MCP catalog is derived from the current API schema and packaged special
tool definitions. Local and installed launchers validate it before starting services;
unexpected skipped operations block startup. It does not require a generated Node artifact.
