When specifying an operator preference for deployment planning, use English, such as
`prefer prefix cache`, `more GPU for performance`, or `use fewer GPU resources`.
The deterministic planner matches English preference keywords; Chinese keyword aliases
are no longer supported.

## Python domain contracts

The models in `llm_d_lens.deploy.contracts` and the
`llm_d_lens.deploy.service.DeploymentService` protocol define the internal
Configuration-to-Deploy boundary. They are not additional HTTP endpoints.
Configuration owns validation/generation of immutable configuration artifacts;
Deploy owns provider execution and lifecycle evidence. Evaluation owns workload
validation and benchmark execution; Simulation does not own deployment lifecycle.

### Commands and immutable artifacts

| Contract | Fields and constraints |
| --- | --- |
| `VersionedPayload` | Nonempty `schema_version`; object `value` defaults to `{}`. The envelope does not prescribe producer-owned keys. |
| `ConfigurationArtifact` | `artifact_id` defaults to a UUID; nonempty `schema_version`, `kind`, `provider_ref`, `checksum`; `media_type` defaults to `application/yaml`; at least one of `content` or `content_ref` is required. |
| `DeploymentCreateRequest` | UUID `request_id`; `input_schema_version="v1"`; nonempty `configuration_artifacts`; `deployment_policy` defaults to a non-null `VersionedPayload(schema_version="v1", value={})`; optional `cluster_snapshot_ref`/`cluster_snapshot`; object `provenance`. |
| `DeploymentKillRequest` | UUID `request_id`; `input_schema_version="v1"`; required nonempty `execution_id`; optional `expected_namespace`/`reason`; object `provenance`. |
| `DeploymentArtifact` | UUID `artifact_id`; nonempty `artifact_hash` and `configuration_artifact_ids`; optional `source_ref`, `manifest_ref`, `manifest_checksum`, `values_checksum`; required `rendered_payload`; `created_at`. |

`provider_ref` selects the deployment provider; it does not transfer configuration
ownership to Deploy. The current `GuideAdapterDeploymentService` is narrower than
the generic DTO: each create call requires **exactly one artifact containing an
inline JSON object** with `media_type="application/json"`. The run planner splits
the public run request into cases; do not pass a generic YAML/content-reference
artifact directly to this adapter and assume it supports it.

`create(request, *, model_token=None, on_initial_execution=None)` returns
`DeploymentExecution`. Runtime binding does not change configuration ownership.
`kill(request, execution)` verifies matching execution IDs, the expected namespace
when supplied, and provider state managed by that service before cleanup. It
does not accept arbitrary resource selectors.

Model-server renderers for baseline, optimized baseline, P/D disaggregation,
tiered prefix cache and precise prefix cache routing share RuntimeClass selection.
They resolve the hardware access mode from the model container's device requests
and copy its optional `runtime_class_name` into the Pod's `runtimeClassName` only
when no explicit RuntimeClass is present. The NVIDIA plugin mode declares `nvidia`,
which must be registered on the target cluster; modes without this setting retain
the cluster default. Router-only and CPU-only Pods are unchanged. This does not
change accelerator resource requests or rewrite saved deployment artifacts.

### Execution, observation and evidence

Ordinary provider rendering maps `maxModelLen`, `maxNumSeqs`,
`gpuMemoryUtilization`, `blockSize` and `maxNumBatchedTokens` from each role
to the corresponding vLLM arguments. P/D uses separate `prefill` and `decode`
values; other providers use `decode` (`precise-prefix-cache-routing` also accepts
`serving`). `model.maxModelLen` supplies a fallback for missing role lengths.
Explicit integer controls must be positive integers; `gpuMemoryUtilization`
must be finite and greater than zero and at most one. Invalid values fail
validation/rendering instead of silently falling back. Applicable
`customParameters` override structured controls. Ordinary rendering replaces both
`--name=value` and `--name value` forms; omitted controls preserve Guide defaults.
Exact published `officialGuide` manifests remain on their existing validated
manifest path rather than being rewritten by ordinary provider parameter mapping.

`DeploymentExecution` carries `execution_id`, `request_id`, `status`, `artifact`,
`configuration_artifacts`, optional `endpoint`/`namespace`/`resource_snapshot`,
`provenance`, `evidence_refs`, optional versioned `diagnostics` and timestamps.
Additional current fields are `forwarded_endpoint`, `monitoring_setup` (setup
audit, not live monitoring status), `data_plane`, and editable descriptive
`metadata` (`display_name`, `description`), separate from origin provenance.

The complete run/case/execution state enums are listed below. A `ready` execution
must contain `DeploymentEndpoint`: `url`, `protocol="http"` and optional
`service_ref`, `model_ref`, `baseline_url`. Endpoint metadata must not carry
credentials, kubeconfig or authorization values.

Shared-memory preparation is recorded under
`artifact.rendered_payload.value.deployment_contract.sharedMemory` and copied to
`diagnostics.value.snapshot.shared_memory`. The report contains `defaultSizeLimit`
(`4Gi`), `addedMounts`, per-container `mounts`, `warnings`, and `manifestChecksum`
for the shared-memory preparation stage (before later placement or tracing).
Ordinary renders complete missing model-server `/dev/shm` mounts; existing mounts
and host IPC are retained. Published `officialGuide` manifests are checked without
shared-memory mutation. Warnings are also logged; invalid or duplicate mount
bindings fail rendering. This does not change the supplied Configuration artifact.

`get(execution_id)` returns `DeploymentExecution`, not another status DTO.
The concrete service looks up its in-memory execution state and raises `KeyError`
for unknown IDs; it is not itself a database query. The worker/DAO boundary owns
durable records and restores execution context when needed. The protocol also
exposes `restore_execution`, `refresh_diagnostics`, `stop` and `clean`; use the
authenticated REST operations below for external clients.

`get_logs(DeploymentLogRequest(...))` returns a `DeploymentLogPage`, separate from
execution metadata:

- Request: `execution_id`, optional nonnegative integer-string `cursor`,
  `limit` from 1 to 1000 (default 100), `follow=False`, and `sources=[]`.
- Current sources are `workload` and `events`, not arbitrary Kubernetes selectors.
  Entries contain `timestamp`, `source`, `message` and optional `severity`.
- Response: `execution_id`, `entries`, `next_cursor`, `complete`, `evidence_refs`.
  `follow=True` sets `complete=False`; this method still returns one page, not a
  streaming iterator or a promise to wait for new logs.
- Archived diagnostics use `ExecutionLogArchive` and
  `deployment-log://<execution_id>/archive` references. Preserve evidence separately
  from database records; see [storage settings](/environment-variables#storage-and-cache-paths).
  Retained snapshots are partial diagnostics, not a complete cluster log history.

### Consumer projections

These are pure DTO helpers, not lifecycle calls or REST permission checks.
`benchmark_input()` requires `ready` plus an endpoint and otherwise raises
`ValueError`. It projects execution ID, artifact, endpoint, namespace and provenance.
`simulation_input()` accepts any execution state and additionally projects
deployment status and the optional resource snapshot/endpoint. It preserves
execution evidence rather than substituting current mutable cluster state.
The helpers exist, but current Evaluation/Simulation routes are not direct
callers; do not describe these projections as their active request API.

```python
from llm_d_lens.deploy.contracts import (
    BenchmarkDeploymentInput,
    DeploymentExecution,
    SimulationDeploymentInput,
)


def benchmark_projection(execution: DeploymentExecution) -> BenchmarkDeploymentInput:
    return execution.benchmark_input()


def simulation_projection(execution: DeploymentExecution) -> SimulationDeploymentInput:
    return execution.simulation_input()
```

## Hardware rendering contract

Deployment capability metadata describes provider behavior; its `variants` array is
empty because variants belong to the selected source catalog. Rendering and
Evaluation use the resolved hardware profile for images, accelerator resources and
scheduling. Legacy configurations can resolve hardware from their rendered DRA or
extended-resource requests; conflicting hardware evidence is rejected.

Python callers can inspect the same source entry points before rendering:

```python
from pathlib import Path
from llm_d_lens.deploy.providers.hardware_profile import guide_overlays

variants = guide_overlays(
    Path("/path/to/llm-d"), "optimized-baseline", accelerator="nvidia",
)
print(sorted(variants))
```

## Backend API

Guide compatibility endpoints keep the `{ "error": "..." }` response shape.
Expected validation failures retain their actionable message and status.
Unexpected catalog/preparation failures return a generic `502` response; unexpected
planning failures return a generic `500` response with `Server-Timing` preserved.
Exception details are logged on the server, not returned to the browser.

### Prepare Guide source

`POST /api/guide-planning/prepare` accepts `guide`, `accelerator`, `modelServer`,
`guideVariant` and the selected `clusterId`. It prepares the official source
without deploying and returns its commit plus manifest-derived controls:

```json
{"ready": true, "commit": "selected-source-commit", "capabilities": {"cacheCpuGiB": false, "rdmaNicCount": true}}
```

The booleans describe supported CPU-cache mutation and a matching profile NIC
claim. They do not depend on variant names. This endpoint is owned by
`llm_d_lens.deploy.guide_planning.prepare`; source loading is implemented in
`llm_d_lens.deploy.guide_sources`.
Python deployment providers use `guide_overlays` (above) and
`llm_d_lens.hardware.resolver.deployment_mode(profile, access_mode)` for the
corresponding source and hardware contracts.

Agentic create and refinement streams use `llm_d_lens.agentic.streaming.planning_stream_response`. The routes retain principal resolution, expected-error classification, and their existing generic error messages. Streams emit `progress` followed by `complete` or `error`; disconnect cleanup cancels and awaits unfinished planning. Gateway operation/log streams remain separate.

Recalculating an Agentic plan does not require an AI provider. Without one,
`AgenticDeploymentService.refine()` refreshes planning facts and uses deterministic
candidate generation and scoring with the new preference. If an available AI
scorer fails, recalculation keeps the validated candidates and returns
deterministically scored alternatives instead.

Agentic candidate planning and approval revalidation use the deployment request's
`max_model_len` and `gpu_memory_utilization` for memory and KV-cache checks, even
when the supplied `planning_facts` contains different values. Deterministic and
AI-generated candidates use the same utilization as the deployed configuration.
PD deployments apply that utilization to both prefill and decode vLLM roles.
The estimate uses GPU capacity and model overhead, not vLLM's measured free KV
cache at startup.

Deployments live under the FastAPI router in `llm_d_lens/deploy/router.py` with the `/api/v1/deployments` prefix.

Use the [installation instructions](/installation) and
[storage environment settings](/environment-variables) for the current monorepo
and Lens storage roots. The old `.llm-d-bench/deploy` and host-specific
`/root/.llm_d_lens/run_store` paths are not the current storage contract.

Execution discovery is read-only and uses `execution_id` as its cross-module
reference; listing does not start port-forwards. Use the execution endpoint
action to obtain a host-reachable URL rather than assuming a persisted
in-cluster endpoint or old tunnel is reachable.

| Record | Lifecycle states |
| --- | --- |
| Run | `queued`, `running`, `succeeded`, `partially_succeeded`, `failed`, `cleaned`, `cancelling`, `cancelled` |
| Case | `queued`, `rendering`, `deploying`, `ready`, `failed`, `stopped`, `cancelling`, `cancelled`, `cleaned`, `cleaned_up` |
| Execution | `draft`, `validated`, `rendered`, `deploying`, `ready`, `failed`, `rolling_back`, `rolled_back`, `cleaned`, `cleaned_up` |

A stopped case has a `rolled_back` execution; these are different state enums.
Benchmarking requires a ready execution with an endpoint and an active cluster
session. Python worker examples below run inside a configured Lens backend;
external clients should use authenticated HTTP so route permissions and resource
scope checks apply.

Optimized and precise routing capability metadata reuse `shared_prefix_routing_workload()` in `llm_d_lens.deploy.capabilities`. Each scenario and recommended workload receives independent nested values; provider-specific baselines and goals are unchanged. Precise-provider calibration and model discovery share lazy modelserver invocation traversal while retaining their respective last-value and first-model selection rules.

Agentic candidate generation requires its first tool batch to contain exactly
`get_cluster_overview` and `search_candidates`. An invalid first batch is not executed;
the generator gives the AI one corrective retry before using built-in candidates. If
the retry also violates the tool contract, the fallback is reported as an invalid
generator response rather than a provider connectivity failure. A tool-call limit
failure retains the round, observed call count, and limit in
`generator_fallback_detail` on the run and `generator.fallback_detail` in its
planning snapshot; `generator_fallback_reason` remains the stable category.

Agentic planning estimates missing exact AIC predictions separately for each validated baseline-vllm,
optimized-baseline, and pd-disaggregation candidate using its workload and GPU topology. The
candidate's estimate is supplied to AI scoring as `aic_estimate`; an unavailable estimate remains
unknown, not a performance or SLO guarantee. Agentic estimates do not pass the original search
TTFT/TPOT targets; they verify the fixed topology and workload without an SLO filter. Generator
fallback also estimates the top three built-in candidates, using the resolved workload when the
failed generator left no tool trace. Unsupported or unavailable topologies remain unknown. Relaxed AIC
search accepts complete configurations using no more than the available GPU budget. Its predictions
do not establish compliance with the original SLO. Agentic preserves the relaxed anchor as a
validated candidate even when the generator suggests only a smaller topology, then estimates its
exact topology and workload. Candidates with known estimates that miss the original latency targets
are marked `not_satisfied`; among comparable misses, smaller relative target violations rank ahead
of GPU savings. Unknown estimates are not treated as failures.
When an external planner scores multiple candidates, its selection rationale explains why each
lower-scored returned candidate ranks below the top choice using the supplied planning facts. Only
the returned top three are scored; no reason is inferred for candidates outside that set.

Planning-fact collection matches discovered accelerator models against registered hardware profiles
to select one AIC system. Unknown, ambiguous, or mixed systems leave AIC evidence unavailable.

AIC support checks and estimates use the SDK release pinned in `pyproject.toml`
(currently 0.12.0), including its bundled support matrix and performance data.
An unsupported P/D result describes that installed matrix, not a hardware-level
prohibition. The 0.12.0 matrix passes Qwen/Qwen3-0.6B on B60/vLLM for P/D;
candidate availability still depends on the requested workload and GPU budget.
After changing the dependency pin, reinstall project dependencies and restart
the backend so support checks and searches use the same SDK release.

### Search or size an AIC workload

The MCP generation and plain-estimate fallback behavior above applies when no load
target is supplied. Agentic load-target planning instead validates the exact native
AIC recommendations, including replica counts outside the ordinary candidate grid.

<Tabs>
  <TabItem value="rest-api" label="REST API">
    **`POST /api/v1/aic/search`**

    `mean_input_tokens` defaults to `4000` and `mean_output_tokens` to `1000`, matching
    native AIC search/recommend. Supply either positive `target_concurrency` or
    `target_request_rate` (requests/second), or omit both for fixed-GPU search.
    Supplying both is rejected with an explanation that AIC does not support joint
    load targets. Agentic maps `planning_facts.workload_profile.concurrency` and
    `.request_rate` to these fields; QPS and request rate are the same quantity.

    With a load target, `gpu_count` is an acceptance budget, not a native recommend
    input. Lens scales the recommended worker pools and accepts only configurations
    within that budget and the TTFT/TPOT targets (native defaults `2000`/`30` ms).
    Unavailable predictions, insufficient capacity or unmet SLOs return an explicit
    error instead of silently selecting a prediction without a load target.
    Agentic forwards that reason to the frontend error alert.

### Start a deployment run

Start a deployment run from one or more already-rendered deployable configurations.

For Router 0.11 endpoint-picker images, planning and installation adapt legacy P/D
plugin settings: `disagg-headers-handler` is handled by `disagg-profile-handler`,
and `parameters.deciderPluginName` becomes `parameters.deciders.prefill`. This also
applies when retrying saved bundles. Source assets and their checksums remain
unchanged; deployment evidence records the derived values actually installed.
Conflicting old/new deciders and custom legacy header parameters are rejected.
Other Router versions and custom image repositories retain their own settings.

The same pure Python transformation is shared by configuration validation and
`llm_d_bench.deploy.providers.deployment_bundle.install_deployment_bundle`:

import yaml

values = yaml.safe_load(saved_router_values_yaml)

### Start a standard vLLM deployment run

Start a Standard Kubernetes Service deployment run using Lens's allowlisted vLLM contract.
The generated namespace uses the backend's configured deployment prefix (for example, `llmd-baseline-vllm-...`).
Standard vLLM deployments use the baseline adapter for rollout readiness and cleanup; they do not require a published Guide manifest's `readinessDeployments` contract.
Only registered Model Cache storage is accepted. It requires a ready entry for the selected model and serves it offline using the entry's downloaded revision; a conflicting custom vLLM `revision` is rejected. Requests using `local-cache` or direct `pvc` storage fail validation. Shared creation preflight also revalidates model/revision readiness and local-disk node synchronization through `llm_d_lens.deploy.providers.storage_mount.require_cached_model`. Ordinary provider rendering mounts the registered cache read-only for serving; `cacheOffline=false` cannot disable its offline flags. Exact published manifests are not covered by those rendering guarantees. Missing or incomplete models must be downloaded or synchronized through Model Cache.
The generated run defaults to preferring replicas on one node without making it mandatory. `placement_replicas` also supports required co-location, balanced distribution, or required separation across model-server Pods in the same rendered manifest. For required co-location, `placement_node_label` can restrict the Pods to a selected cluster node by its `kubernetes.io/hostname` label; the label is checked against that cluster before deployment. Tensor-parallel accelerator claims are requested by each model-server Pod, keeping its TP devices in that Pod. Agentic planning inherits the same fields and applies the selected preset on approval.

### Restart a deployment case

:::warning Current restart limitation

The route exists, but the current worker cleans the old execution and marks its
case `cleaned` before calling `DeploymentPlanService.retry_case()`, which accepts
only the latest `stopped` or `failed` case. Consequently, successful cleanup is
followed by `409`, not a queued replacement. Cleanup has already taken effect;
an error is not evidence that the old resources remain. Do not repeatedly retry
this route expecting it to restore the deployment.

:::

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/v1/deployments/runs/{run_id}/cases/{case_id}/restart`**

Requires `deployment:case:execute`, an active cluster session, and a stopped or
failed case. Body: `RestartCaseRequest`; `model_token` is an optional string
override, with empty/whitespace treated as absent. Send `{}` to omit it.
The declared success shape is HTTP `200`, `{ "case": ... }`, but the current
cleanup/retry conflict prevents that path after successful cleanup.
Lifecycle `ValueError` becomes `409`; invalid bodies return `422`.

```json
{}
```

Current conflict response excerpt (the application adds Problem Details fields):

```json
{
  "status": 409,
  "detail": "only the latest stopped or failed deployment case may be retried"
}
```

## Remote SSH deployment

SSH transport and remote command failures return `502` with
`{ "error": "Remote deployment failed" }`; internal exception details and failing
command output are logged server-side rather than exposed in error responses.
Expected input and policy errors retain their existing status and actionable message.

These legacy endpoints are implemented in the Python module
`llm_d_lens.deploy.remote_deploy`. They
execute commands over SSH rather than create v1 deployment runs. Their current
single-node Intel Data Center GPU/XPU restriction is specific to this legacy
implementation, not the capability limit of the profile-driven v1 API.

SSH operations require `PRISM_REMOTE_DEPLOY_ENABLED=true` in production (enabled
by default outside production). Production targets must also match
`PRISM_REMOTE_HOST_ALLOWLIST`. Defaults remain readable when SSH operations are
disabled, subject to authentication/permission checks.

| Operation | Lens permission |
| --- | --- |
| Defaults | `remote-deploy:target:read` |
| Fingerprint, test | `remote-deploy:target:connect` |
| Start, status, logs | `remote-deploy:deploy:execute` |
| Teardown | `remote-deploy:deploy:teardown` |

Authenticated SSH operations require `target.host`, `username`,
`hostFingerprint` and a nonempty `cards` array of numeric ID strings.
`port` defaults to 22; `authMethod` defaults to `agent` and also accepts `key`
or `password`. Agent authentication requires the BFF's `SSH_AUTH_SOCK`.
Key authentication requires a server-side `keyPath` beneath `PRISM_SSH_KEY_DIR`
(default `$HOME/.ssh`). Password authentication supplies
`credentials.password` on each request; it is not stored or returned.
Fingerprint discovery does not authenticate and does not require cards.
Confirm its result through a trusted channel before using it; a returned
fingerprint is not itself proof of host identity.

Route errors are `{ "error": "..." }`: `400` for invalid input/credentials,
`403` for a production host outside the allowlist, `503` for disabled SSH
operations, and normally `502` for SSH/command failures. Gateway authentication
and permission errors use the gateway's Problem Details format.

### Python HTTP client for remote operations

There is **no Python service-layer equivalent** for these Node endpoints.
The Python tabs below use this HTTP helper instead. The environment variables
in this example are client inputs, not new Lens server configuration.
Set them from an authenticated Lens session; never commit their values.

```python
import os
import httpx

def remote_request(method: str, path: str, body: dict | None = None) -> dict:
    with httpx.Client(
        base_url=os.environ["LENS_URL"],
        cookies={
            "prism_session": os.environ["LENS_SESSION"],
            "prism_csrf": os.environ["LENS_CSRF"],
        },
        headers={"x-prism-csrf": os.environ["LENS_CSRF"]},
        timeout=300,
    ) as client:
        response = client.request(method, path, json=body)
        response.raise_for_status()
        return response.json()

target = {
    "host": "192.0.2.20",
    "port": 22,
    "username": "operator",
    "authMethod": "agent",
    "hostFingerprint": os.environ["VERIFIED_SSH_FINGERPRINT"],
    "cards": ["0"],
}
```

REST request examples below show operation fields; for authenticated operations,
add the complete `target` object above and optional per-request `credentials`.
The Python examples demonstrate the complete request assembly.

## Configuration preparation APIs

These Configuration-domain routes prepare artifacts for Deployments and Evaluation. Request and response models live in `llm_d_lens.configuration.models`. The examples use illustrative cluster/session IDs and guide commits; replace them with an active cluster session and real rendered guide provenance. Saving publishes an artifact; rendering alone does not deploy it.

The workflow is source selection/editing, resolve, render, save, then deployment.
Resolve normalizes each source configuration before capability checking and
validation, returning per-configuration feedback. The candidate source identifies
input origin, not deployment type. Render binds candidate intent to actual Guide
resources; save publishes immutable artifact content, identity and checksums.
Configuration owns normalization, validation and artifact publication; Deploy
owns runtime validation, resource lifecycle, teardown and rollback. Checksums
alone cannot validate topology or resource semantics. These boundaries apply to
both the REST endpoints and their Python service functions below.

The HTTP boundary uses `application/problem+json` errors. Shared `DomainError` instances retain their original status and code (for example a conflict remains 409); they are not converted into an operation-specific 500. Python service calls raise their original exceptions; the route adapters in `llm_d_lens.configuration.router` apply the HTTP mappings below.

### Deployment access APIs (removed)

Deployment sharing and `deployment:run:share` have been retired. Use
[model-service inference grants](/api-reference/modules/model-services#model-inference-grants)
instead. Migration audits and removes existing deployment shares; it does not
convert them into broader model grants.

<Tabs>
  <TabItem value="rest-api" label="REST API">

The former GET/POST/DELETE `/api/v1/deployments/executions/{execution_id}/access`
and `/api/v1/deployments/runs/{run_id}/access` routes, including
`/access/options` and `/access/{binding_id}`, are no longer registered.
They no longer grant, list or revoke access.
  </TabItem>
  <TabItem value="python-api" label="Python API">

Replace deployment-share calls with the model service's scoped grant methods:

```python
from llm_d_lens.model_service.service import default_service

def revoke_model_grant(model_id: str, binding_id: str, principal) -> None:
    default_service().revoke_access(model_id, binding_id, principal=principal)
```

The method requires `model-service:group:share` in the model's cluster and rejects
bindings belonging to another model. Generic binding creation rejects retired
`deployment_run` and `deployment_execution` resource types.
  </TabItem>
</Tabs>
