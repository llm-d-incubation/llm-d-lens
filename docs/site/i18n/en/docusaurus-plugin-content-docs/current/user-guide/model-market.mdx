Open **Model Catalog** to choose a model and deploy it to a cluster.
For your first deployment, use **Manual** mode.

Use the compact **Search models** field beside the category tabs to filter by model name, publisher,
repository, model type, category, or precision. Search ignores case and combines
with the selected category; multiple words must all match. The model count updates
as you type. Use **Clear filters** to reset both search and category.

## Choose a deployment mode

In **One-click deployment**, the **Model Catalog** back button sits in the
content area above the deployment configuration, not in the global top bar.

| Mode | Choose it when |
| --- | --- |
| **Manual** | You want to choose an llm-d Guide template, configure resources or review generated YAML |
| **Agentic** (Experimental) | You want Lens to recommend a configuration for a workload and performance target |

Deployment setup uses the model card's **Context** metadata as its initial maximum
context length, including Agentic recommendations. For example, Qwen3-0.6B starts
with `40960`, not `4096`. Only models with no listed context use the `4096`
default. Standard and Agentic requests accept `256` through `1048576` tokens
without silently shortening the card value; resource and model compatibility
checks still apply. Existing plans and deployments are not rewritten.

## Create a manual deployment

1. Open **Model Catalog**, use **Model categories** to narrow the list, and click a model card.
2. In **One-click deployment**, enter **Deployment name** and choose a ready **Cluster**.
3. Choose **Model cache storage** containing this model. Wait for **This model is ready in the selected cache.** Model cache storage is optional in **Manual** mode.
4. Keep **Mode** on **Manual** and click **Configure deployment**. Review the prefilled model and deployment settings; use **Edit setup** if needed.
5. Check the runtime image, replicas, and tensor parallel size.
6. Under **Guide template**, choose **Guide** and **Accelerator**. Use [Choose an evaluation Guide](/evaluation/guides) to compare the options.
7. For a P/D or tiered-cache Guide, choose a variant from the displayed list. Keep the supplied defaults for the first run.
8. Click **Generate YAML**. If available cards are insufficient but the physical total is sufficient, review the Pending warning and click **Continue & generate**. If the physical total is insufficient, reduce replicas / TP.
9. Review **Generated deployable configuration**. Correct any highlighted errors, then click **Deploy**.
10. On **Deployments**, wait for **Ready**. The deployment is retained without running a benchmark; stop or clean it up explicitly when no longer needed.

YAML generation supports both device-plugin and DRA clusters. Missing DRA device
details do not prevent hardware variant detection from registered Kubernetes
accelerator resources; normal capacity and configuration checks still apply.

Use **Back to model card** to return to the selected model.
To measure performance, see [Run an evaluation](/user-guide/evaluation).

No cluster or cache available? [Add a cluster](/user-guide/clusters),
[create cache storage](/user-guide/storage), and [download the model](/user-guide/model-cache).
If the model is missing from the selected cache, download it there before returning.

Open **Manage model cache** from a selected model to open **Download a model**
directly in **Model cache**. The selected cluster, Hugging Face repository ID, and
storage volume are prefilled and remain editable. After closing the dialog,
use **Back to model** to return
to the selected model with your deployment settings intact. Browser Back also
preserves the selection. Storage choices and model download status refresh when
you return.

Change the runtime image only when you have an image compatible with the selected
hardware. After changing the cluster or Guide source, check the variant selection
again. A resource or network error during generation must be resolved before deployment.

## Get an AI-assisted recommendation

1. Open a model and fill in the deployment name, cluster and cache storage.
2. Set **Mode** to **Agentic**.
3. Choose **Use case** and **GPU capacity for planning**, then review the workload and performance-target fields. **Mean input tokens per request** (ISL), **Mean output tokens per request** (OSL), **TTFT SLO (ms)** and **TPOT SLO (ms)** start blank. Their placeholder examples (`4000`, `1000`, `2000` and `30`) are not submitted as requirements. Mean input length is not copied into P95. There is no end-to-end latency input. In the planning prompt, TPOT targets can also use per-token units: `TPOT <= 20 ms/token` and `TPOT <= 0.02 s/token` both mean 20 milliseconds per token.
4. Leave **AI provider** on **Default (no external AI provider)**, or select a configured provider to help rank the options.
5. Optional: expand **Preference** and enter an English preference, such as `use fewer GPU resources` or `prefer prefix cache`.
6. Click **Generate recommendation**.
7. Under **Validated alternatives**, expand **Why this option** to compare resource use and estimated performance.
8. Click **Deploy recommendation** on the option you choose. Track startup on **Deployments**.

Agentic recommendation generation and recalculation skip model-file presence and
download-readiness checks. A valid registered model-cache storage volume is still
required. You can plan before downloading the model; deployment approval checks
that the model is ready in the selected storage and resolves its current credential
policy. Missing or incomplete models block deployment, not recommendation generation.
Manual and Standard deployment checks are unchanged.

Optionally, expand **Pod placement** before generating a recommendation to choose
where the deployment runs.

Agentic generation and selection offer `optimized-baseline` instead of direct
`baseline-vllm`, including built-in fallback and AIC recommendations. Historical
direct-vLLM configurations are not reintroduced as candidates. Existing plans
and manual Standard vLLM deployments are unchanged.

For load-based sizing, enter either **Concurrent requests** or **Request rate (QPS)**,
not both. These are optional and have no prefilled target. A provided target selects
native AIC recommendation mode; leaving both blank keeps the fixed-GPU search.
Lens validates the exact recommended topology against the selected GPU capacity and
deployment constraints. Joint inputs, unavailable predictions, insufficient capacity
or unmet latency SLOs produce an error in the Agentic workspace with the reason and
next action, rather than silently falling back to predictions without a load target.

To change the recommendation, enter your revised preference below the alternatives
and click **Recalculate selection**. This also works without an external AI provider.

Every new recommendation and recalculation queries published public SQL experiments
before AIC planning, using the selected model. With an external AI provider, relevant
public observations take precedence over AIC estimates in candidate generation and
ranking; AIC supplements missing or inapplicable evidence. Live resource constraints
and explicit operator preferences still apply. Different hardware, workloads, runtime
versions, topologies or metric statistics are not interchangeable.

Public retrieval also filters by the live target cluster's accelerator model, not
the cluster name. Vendor/separator spelling differences may match, but memory size
and PCIe/SXM variants remain distinct. Unknown or mixed hardware is reported;
missing matches never fall back to another hardware family.

Public benchmark records with a missing, blank or `unknown` runtime backend are
treated as `vllm` for retrieval and planning context. Explicitly reported other
backends are preserved and do not match a vLLM plan. This corpus default does not
infer runtime versions or rewrite original evidence.

Under **Decision evidence**, review **Public SQL measured observations** for
the retrieval outcome, original values and units, source path, revision and checksum.
No matches, query failures or missing authenticated global `benchmark-rag:query:read`
permission are explicitly reported, and planning continues with existing evidence.
Plans containing public RAG observations retain that same read-permission requirement.
Without external AI, retrieved observations remain context only: they do not silently
become deterministic performance predictions or change the displayed SLO assessment.

Internal SQL experiments are listed separately. Agentic planning uses SQL evidence
and does not require a document search service or independent search page.

With an external AI provider, both generation and selection prompts put your full
preference before the planning context. Explicit requirements such as one GPU or no
P/D separation take precedence over candidate diversity and performance suggestions,
subject to platform and hardware validity. This is AI guidance, not a guarantee that
arbitrary natural-language requirements are mechanically enforced.

New planning audits retain the full preference and each actual AI request/response,
including tools and retries. They exclude provider authentication headers and API keys.
Treat these audit files as private data; old decisions cannot recover previously
unrecorded exchanges.

**AI score** ranks the alternatives; it is not a measured performance result or
a probability of success. Treat **SLO not met** as a reason to revise the target
or resources. [Run an evaluation](/user-guide/evaluation) to measure the deployed model.

## Adjust optional settings

| Goal | Where to change it |
| --- | --- |
| Change context length or batching | **Advanced settings** in the Manual configuration editor |
| Enable tool calling | **Enable automatic tool choice**, then choose **Tool call parser** |
| Use a deployment-specific proxy | **Deployment environment** |
| Change replicas or accelerator count | **Replicas** and **Tensor parallelism** / **TP** |

If startup reports insufficient KV-cache capacity, lower the maximum context
length or allocate more resources in a new configuration.

For deployments using the NVIDIA device plugin, generated model-server Pods select
the `nvidia` RuntimeClass declared by their hardware access mode unless the source
already specifies a RuntimeClass. This applies to baseline, optimized baseline,
P/D disaggregation, tiered prefix cache and precise prefix cache routing. This
RuntimeClass must exist on the target cluster. GPU requests alone do not inject
devices when the node's default container runtime is `runc`. If vLLM reports
`Failed to infer device type`, check the Pod's RuntimeClass and device access;
`VLLM_LOGGING_LEVEL=DEBUG` only adds diagnostics. Existing Pods and saved manifests
are not rewritten by a Lens update; generate a new deployment to apply the fix.

If **Your role cannot create deployments.** appears, ask an administrator for
deployment access to the target cluster. **Open Deployments** still lets you view
deployments you can access.
