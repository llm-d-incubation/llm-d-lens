Add a cluster before creating storage or deploying a model.
Use its kubeconfig to connect an existing cluster, or use Kubespray to create one on your machines.

## Before you begin: proxy exclusions

If Kubernetes components use an HTTP(S) proxy, keep cluster-internal traffic off it.
Set `NO_PROXY` and `no_proxy` to the same value, preserving existing exclusions and
including localhost, node hostnames/IPs, the API server address, Service/Pod CIDRs,
and cluster DNS suffixes. Example (replace the placeholders and adapt `cluster.local`
if your cluster uses a different DNS domain):

```text
localhost,127.0.0.1,::1,<node-hostnames-and-IPs>,<api-server-host>,<service-CIDR>,<pod-CIDR>,.svc,.svc.cluster.local,cluster.local
```

**Verify these settings on the running `kube-apiserver` process**, not just in a shell
or Lens. For kubeadm, configure its environment in
`/etc/kubernetes/manifests/kube-apiserver.yaml`; kubelet recreates the static Pod,
briefly interrupting API access. Keep manifest backups outside that directory.
CIDR exclusions alone do not cover Service DNS names: missing DNS exclusions can
route webhook calls through the proxy and cause TLS errors or timeouts.

## Register a cluster from a kubeconfig

### Kubeconfig permissions

The simplest and most compatible option is a kubeconfig whose identity has the
`cluster-admin` role. If your security policy requires narrower permissions, save
the helper below to a temporary file, make it executable, and run it with an admin
kubeconfig:

```bash
chmod +x lens-rbac-kubeconfig.sh
./lens-rbac-kubeconfig.sh --kubeconfig ~/.kube/config --output lens-lens-minimal.kubeconfig
```

Upload the generated `lens-lens-minimal.kubeconfig`. The helper creates the
`lens-access/lens-minimal` ServiceAccount and ClusterRole, runs a live smoke test,
and prints the output path. Use `--skip-self-test` only when the target cluster
does not allow the test workloads.

#!/usr/bin/env bash
# Generate the least-privilege Kubernetes identity Lens needs and a kubeconfig
# for it.
#
# The role is deliberately NOT cluster-admin. It is an operator role:
#   * read-only discovery across every resource/API group (Lens renders arbitrary
#     CRDs and its namespace cleanup enumerates every listable namespaced kind);
#   * workload, storage, networking, batch, RBAC and CRD writes needed to
#     deploy/evaluate models, provision model-cache volumes, install the
#     monitoring stack and install/upgrade Gateway/GPU controllers;
#   * no impersonation, no service-account token minting, no
#     authentication/authorization review endpoints and no CSR approval.
#
# Installing arbitrary third-party Helm charts (monitoring, Gateway, GPU
# operator) inherently requires creating ClusterRoles/ClusterRoleBindings, so
# the role includes bind/escalate on those two resources. Everything else is
# scoped to the resources Lens actually uses.
#
# Usage:
#   lens-rbac-kubeconfig.sh [options]
#
# Options:
#   --kubeconfig PATH        Admin kubeconfig used to create the RBAC
#                            (default: $KUBECONFIG, else ~/.kube/config)
#   --context NAME           Admin context (default: current-context)
#   --namespace NAME         Namespace for the ServiceAccount/token
#                            (default: lens-access)
#   --service-account NAME   ServiceAccount name (default: lens-minimal)
#   --cluster-role NAME      ClusterRole name (default: lens-minimal)
#   --output PATH            kubeconfig destination
#                            (default: ./lens-<service-account>.kubeconfig)
#   --skip-self-test         Do not create/delete a throwaway namespace
#   --delete                 Remove the generated RBAC identity and token secret
#   -h, --help               Show this help
#
# The generated kubeconfig uses a long-lived ServiceAccount token. Pass
# --delete first if you want to rotate the token.

set -euo pipefail

    --kubeconfig) SOURCE_KUBECONFIG="${2:?missing value}"; shift 2 ;;
    --context) CONTEXT="${2:?missing value}"; shift 2 ;;
    --namespace) NAMESPACE="${2:?missing value}"; shift 2 ;;
    --service-account) SERVICE_ACCOUNT="${2:?missing value}"; shift 2 ;;
    --cluster-role) CLUSTER_ROLE="${2:?missing value}"; shift 2 ;;
    --output) OUTPUT="${2:?missing value}"; shift 2 ;;
    --skip-self-test) SELF_TEST=0; shift ;;
    --delete) DELETE=1; shift ;;
    -h|--help) usage ;;
    *) die "unknown option: $1 (use --help)" ;;

if ((DELETE)); then

  "${KUBECTL[@]}" delete clusterrolebinding "$CLUSTER_ROLE" --ignore-not-found
  "${KUBECTL[@]}" delete clusterrole "$CLUSTER_ROLE" --ignore-not-found
  "${KUBECTL[@]}" -n "$NAMESPACE" delete secret "${SERVICE_ACCOUNT}-token" --ignore-not-found

  TOKEN="$("${KUBECTL[@]}" -n "$NAMESPACE" get secret "${SERVICE_ACCOUNT}-token" -o jsonpath='{.data.token}' 2>/dev/null || true)"

  [[ -n "$TOKEN" ]] && break
  sleep 2

import json
import os
import sys

cluster_file, output, user, namespace, token_b64, ca_b64 = sys.argv[1:]
with open(cluster_file, encoding="utf-8") as handle:
    cluster = json.load(handle)
# Prefer the CA embedded in the service-account token secret when the source
# kubeconfig did not carry certificate-authority-data.
if not cluster.get("certificate-authority-data") and ca_b64:
    cluster["certificate-authority-data"] = ca_b64
cluster.pop("certificate-authority", None)

config = {
    "apiVersion": "v1",
    "kind": "Config",
    "clusters": [{"name": "lens", "cluster": cluster}],
    "users": [{"name": user, "user": {"token": base64.b64decode(token_b64).decode("utf-8")}}],

FAILED=0
SERVED_RESOURCES=" $("${NEW_KUBECTL[@]}" api-resources -o name 2>/dev/null | sort -u | tr '\n' ' ') "
check() {
  local verb="$1" resource="$2"
  shift 2
  # A CRD that is not installed cannot be authorized; skip it here and let the
  # wildcard group rule cover it once the chart/installer creates the CRD.
  if [[ "$resource" == *.* && "$SERVED_RESOURCES" != *" $resource "* ]]; then
    printf '  SKIP: %-18s %-50s (CRD/API not installed)\n' "$verb" "$resource"
    return 0
  fi
  if ! "${NEW_KUBECTL[@]}" auth can-i "$verb" "$resource" "$@" >/dev/null 2>&1; then
    printf '  MISSING: %-18s %-50s %s\n' "$verb" "$resource" "$*"
    FAILED=1
  fi
}

## Bootstrap a new cluster via Kubespray

1. Open **Clusters → Add** and enter the cluster name.
2. Choose **Bootstrap a new cluster via Kubespray**.
3. For each machine, enter **Host(s)**, **Port**, **Role(s)**, **Username**, and an **SSH private key** or **SSH password**. Use **Add node** for more machines.
4. Under **Network proxy for target nodes**, keep **Auto** to reuse each machine's settings, or choose **Custom for these nodes** and enter the proxy.
5. Click **Run preflight**. Fix failed checks and run preflight again until every host passes.
6. Click **Start bootstrap** and follow its progress.
7. When the generated kubeconfig appears, continue through the registration steps above to **Finish** and **Done**.

Bootstrap changes the target machines. Check their addresses and roles before starting.

## Edit a cluster

1. Select the cluster, then click **Edit cluster**.
2. Change its name, description, proxy, **HF_TOKEN secret** or model-gateway settings.
3. Click **Save changes** and check that the updated values appear.

Component versions are supplied by the Lens release and are not editable here.

### Rotate the HF_TOKEN secret

**HF_TOKEN secret** holds the Hugging Face token this cluster uses to pull gated
models. Lens stores only the Secret's namespace and name; the token value lives
on the cluster and is never shown again.

1. Leave **New token** empty to keep the current token. Type a token only when
   you want to replace it.
2. Change **Namespace** or **Secret name** only to point the cluster at a
   different Secret; Lens creates that Secret when it does not exist yet.
3. Click **Save changes**. The confirmation names the Secret that was written.

Deployments and Model Cache downloads copy the token into their own namespace
when they run, so workloads that are already running keep the previous token
until you recreate them.

## Review cluster health

The cluster list refreshes quietly every five seconds while the page is visible.
The selected cluster's health refreshes every five seconds; other clusters' health
refreshes every ten seconds. No manual refresh is needed. List refreshes preserve
the current selection and search, and retain existing entries with an error message
if an update fails.

1. Select a cluster in **Clusters**.
2. Check **Workers**, **CPU**, **Memory**, **Deployable GPU**, **VRAM**, **Disk**, and **Monitoring**.
   **Memory** and **Disk** lead with the capacity still free out of the cluster
   total, and show the percentage already in use on the **Usage** line below.
   A dash means the cluster cannot report that reading right now, not that
   nothing is free.

Clusters shows infrastructure health and worker nodes, not deployment lists or
individual deployment failures. Click **Deployments** below **Deploy a model** in the
**Target cluster** panel to open the
[Deployments page](/user-guide/deployments) with the selected cluster already set
in its filter. You can change or clear that filter; the entry URL preserves it on reload.
Use that page to manage deployments, endpoints and logs. Deployment monitoring and profiling
remain available through [Observability](/user-guide/observability).

Click **Model services** below **Deployments** to open
[Model services](/user-guide/model-services) with the same cluster preselected in
the service-flow filter. This filter can also be changed or cleared, and its entry
URL restores the cluster on reload or browser history navigation.

When accelerators use DRA, Lens reads their model from ResourceSlice device attributes
even if nodes do not have GPU product labels. The reported model is used to select
the matching AIConfigurator system for hardware-aware recommendations.

## Put worker nodes into maintenance mode

1. In the cluster's **Workers** list, select the nodes.
2. Click **Enter maintenance mode**, review the names, then click **Cordon nodes**.
3. After maintenance, select the nodes, click **Exit maintenance mode**, and confirm **Uncordon nodes**.

**Cordon stops new pods from being scheduled; it does not stop or move existing pods.**
Plan any required workload shutdown or migration separately.

## Delete a cluster registration

1. Open the cluster's **Actions → Delete cluster**.
2. Check the cluster name and the deletion warning.
3. Click **Delete** and confirm the registration disappears from the list.

Deletion also removes this registration's isolated Gateway namespace, normally `lens-gateway-<cluster-id>`, including its Gateway, IPP and authorization resources. The old shared `lens-gateway` namespace and other registrations' namespaces are left alone. If Gateway namespace deletion fails or times out, Lens reports the error and keeps the registration and credentials so you can retry.

Lens also cleans up what it created on the cluster. The cluster's `HF_TOKEN` secret is deleted, and its namespace goes with it when keeping the namespace would serve no purpose: Lens created the namespace, or the secret was the only thing in it. If the namespace still holds anything else, it is kept, and the cluster's built-in namespaces are never touched. For a cluster you are still registering, any storage volume created during the wizard is removed together with its PVC and PV, while model files on NFS or hostPath are kept. A fully registered cluster that still has storage volumes cannot be deleted until you delete those volumes first.
