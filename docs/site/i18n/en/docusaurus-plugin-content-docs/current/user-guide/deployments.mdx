Model selection and per-deployment parameter overrides use the [Model Catalog](/user-guide/model-market). Custom entries and API fields are described in the [catalog API](/api-reference/modules/model-market).

Open **Deployments** to check whether a model is ready, inspect a failure, or manage an existing deployment.

New llm-d Router deployments default to a complete Standalone endpoint, even when the cluster has a ready shared Gateway. Publishing adds a Gateway route; detaching preserves independent access. See [Standalone deployment and Gateway publication](/user-guide/model-services#standalone-deployment-and-gateway-publication).

## Open the deployment creation flow

Manual proceeds directly to **Deployment plan**; Agentic first offers an objective,
with all numeric parameters optional.
No request lengths, prefix reuse or workload shape are invented. These are benefit
hints, not compatibility gates. Agentic
can interpret explicitly stated qualitative workload traits from a goal when an
AI provider is selected; the interpretation is displayed and editable. Without AI,
use structured inputs. Numeric resource and performance limits are never inferred.

Manual ranks supported combinations by SLA status, then the P/D decision, then the greatest
source-verified capability coverage, not the first Guide that renders; on equal coverage a P/D combination wins.
Manual limits `--max-num-seqs` only when you declare request sizes; otherwise vLLM
admits requests by free KV cache. It does not maximize resource use
or claim a measured performance optimum. Unsupported combinations remain explicit.
**Ready for your confirmation** is a compact conclusion; failed checks block deployment and
provide **Retry checks**. Deployment confirmation rechecks current capacity.

Prefix-affinity routing, P/D separation and CPU KV offload can be combined independently.
Routing composition retains the P/D profiles and uses affinity plugins from the same
pinned source revision; incompatible plugins or images are reported explicitly.
Basic attention KV caching is distinct from cross-request prefix caching and CPU
offload. Missing explicit vLLM flags can be configured with a mandatory startup
capability probe in the selected image; this is not a claim of verified runtime support.

Deployment creation requires models registered in [Model Cache](/user-guide/model-cache).
Select a registered cache volume containing the ready model and its revision on the
same cluster. The Advanced configuration editor has only the **Model Cache** source.
For local-disk storage, synchronize new nodes before deployment. Ordinary provider
rendering configures offline serving with a read-only cache mount. Download
or repair the cache in Model Cache first, then create or retry the deployment.

Cache checks follow the active serving roles: P/D checks Prefill and Decode
independently; other providers use Decode. Each role defaults to revision `main`.
An explicit tokenizer must also be ready in the same cache volume; its revision
defaults to the role's model revision unless `tokenizer-revision` is supplied.
Conflicting dependency arguments are rejected. The rendered model and tokenizer
arguments must match the checked dependencies before deployment proceeds.

Ordinary optimized-baseline rendering does not apply custom `revision`, `tokenizer`,
or `tokenizer-revision` arguments, so those inputs are rejected. Configuration-source
overrides and custom `model`, `model-path`, `code-revision`, `hf-config-path`,
`config`, and `download-dir` arguments are not supported by cache preflight.

1. In the left navigation, open **Deployments**.
2. In the page header, click **Create**.
3. Follow [Create a deployment](/user-guide/model-market). The new deployment appears in this list after submission.

Choose **Pod placement** on the setup card before building a plan: prefer one node
(default), require one node (optionally a specific node), distribute evenly or
require separate nodes. The choice applies to Deployment, LeaderWorkerSet and
DisaggregatedSet model servers. Existing deployment APIs and the separate
Configuration editor retain their placement controls. TP devices are requested by
each model-server Pod; planned placement is not shown as actual cluster placement
before deployment.

For P/D, the Prefill, Decode and KV transfer settings include **P/D slices and
placement**: slice count, per-slice Prefill/Decode replicas and TP, the slice
placement policy (`None`, `ExclusiveSlice`, `ExclusiveTopology`) and its node-label
topology key. Lens recommends values from current free devices per topology domain,
narrowest domain first (node, then rack-like labels, zone, region). It splits role
replicas into the fewest equal slices that each fit one domain, so KV transfer stays
local. Latency and reliability objectives use `ExclusiveTopology` when enough
unshared domains exist. If no domain fits a whole slice, placement stays `None`.
Automatic hard placement also constrains role Pods to the domains that can fit a
whole slice, preventing the first Pod from locking the slice onto a smaller node.
This does not reserve devices; regenerate the plan if available capacity changes.
Reviewed values are pinned in the plan and remain editable; non-`None` policies are
hard scheduling rules and Pods stay Pending if no domain can hold a slice. The
recommendation respects Pod placement: distribute evenly or separate nodes exclude
node-scoped slices, and require one node keeps one slice. The slice panel disables
conflicting topology keys, and an explicit conflict is reported when you apply changes.

### Model Cache enforcement limitations

Exact published YAML configurations (`officialGuide`) bypass ordinary provider
rendering. Their final manifests do not yet enforce the same offline flags,
read-only cache mounts, or backing-volume binding. Cache-only deployment is
therefore not guaranteed for this path. Offline environment variables are also
not a network isolation boundary.

2. In the list toolbar, type in **Search deployments** to match a deployment by name, description, model, namespace, guide, or ID.
3. Open **Status** to filter by deployment state.
4. Open the cluster selector and choose **All clusters** or one cluster.
5. If needed, change **Rows per page** and use the pager to move through the list.
6. If no rows match, click **Clear filters**.

The **Cluster** and **Namespace** columns each include a copy button.

## View deployment details

1. In the deployment row, open the actions menu and select **View details**.
2. In the drawer, review the sections **Basic Information**, **Model & Serving Engine**, **Cluster & Environment**, **Network & Endpoints**, and **Audit & Timeline**.
3. Use the copy buttons beside values such as **Namespace**, **Cluster Session ID**, **Container Image**, **Internal Endpoint**, **Forwarded Endpoint**, or **Execution ID** when you need to reuse them elsewhere.
4. If the deployment failed, read the failure banner before making changes.

Wait for **Ready** before calling the deployment. For **In progress**, check the pod logs for startup progress. For **Failed**, read the failure banner and the affected pod's logs.

Missing runtime details are read from the stored rendered vLLM manifest. For P/D
deployments, flat runtime fields are labeled **(Decode)**. Unspecified values remain
unknown rather than being filled with assumed defaults.

Normal Pending or Running-but-not-ready Pods keep a starting deployment **In progress**.
Explicit Pod failures, including image pull failures and OOM, still show **Failed**.
For deployments already marked Ready, the status dot also reflects live model-server Pods. A yellow dot means fewer ready model-server Pods than requested, so serving capacity is reduced. A red dot means no ready model-server Pods remain, so the service is unavailable. These conditions are also reported under **Needs attention**.

**Failed** is not final. A rollout that ran past its progress deadline is recorded
as failed, but the workload often recovers on its own -- a pod that kept crashing
until its model cache was complete, for example. Lens keeps re-checking failed
deployments against the cluster and flips them back to **Ready** once their pods
serve again, so leave the deployment in place rather than recreating it
immediately. If the namespace is gone, the deployment is corrected to **Cleaned**
instead.

Pending Pods waiting for accelerator resources, including DRA scheduler reports
such as `cannot allocate all claims`, keep the deployment **In progress** even
after the rollout progress deadline. Refreshing a deployment previously marked
**Failed** returns it to **In progress** when current diagnostics confirm this
resource wait. The scheduler reason remains available in diagnostics. This does
not release devices held by other deployments; stop or remove an unused deployment
to free them. Container crashes and image-pull failures still count as failures;
Pending alone is not enough to classify a deployment as waiting for resources.

After scheduling, a Running Pod can still be loading the model and not yet Ready.
If rollout reports an exceeded progress deadline, Lens preserves **In progress**
without automatic cleanup while current containers remain within their
`startupProbe` budget (or `readinessProbe` budget when no startup probe exists),
measured from each container's actual start time. Time spent Pending does not
consume this budget. Current crashes, image-pull failures, container restarts and
expired probe budgets are not covered by this grace period. Running alone is not
proof of readiness; the provider's readiness checks must still pass.

## View pods and stream logs

For newly rendered deployments, all providers forward explicit maximum model
length, maximum sequence count, GPU memory utilization, block size and maximum
batched tokens to vLLM. P/D applies Prefill and Decode settings independently.
Role settings override Guide defaults; model-level maximum length is a fallback
when the role does not specify one. Targeted custom arguments take precedence.
Omitted settings retain upstream defaults. These changes do not rewrite existing
Pods or exact published manifests: create a new deployment to apply changed settings.
Check the model-server command and logs when diagnosing KV-cache capacity errors.

Lens checks `/dev/shm` in rendered model-server Pods across all deployment
providers. Ordinary rendering adds a per-Pod, memory-backed `emptyDir` with a
**4 GiB** limit when the mount is missing and host IPC is not enabled.
`baseline-vllm` also defaults to 4 GiB. This avoids the container runtime's
default 64 MiB shared-memory limit without enabling host IPC or changing
the upstream Guide checkout.

Existing mounts and their limits are preserved, including mounts with no explicit
limit and alternative volume sources. Missing limits, alternative sources,
read-only/subpath mounts and existing host IPC produce warnings in service logs
and deployment diagnostics (`snapshot.shared_memory`). An omitted `sizeLimit`
on a memory-backed volume does not mean a 64 MiB limit or unlimited usable memory.
Duplicate `/dev/shm` mounts and invalid volume bindings are rejected.

Exact published manifests (`officialGuide`) are checked but never receive an
automatic shared-memory mount; missing mounts produce warnings instead.
The report is also retained in the deployment artifact's
`rendered_payload.value.deployment_contract.sharedMemory`.
Volumes consume memory as used, not their full limit up front; account for
shared memory when sizing Pod memory. Existing deployments retain their original
manifests; recreate them to receive the new default or missing-mount completion.

1. To see pod status inline, click the row toggle with tooltip **Show pods**.
2. In the expanded row, review the pod table columns **Pod**, **Status**, **Restarts**, **Node**, and **Pod IP**.
3. For the full log viewer, open the actions menu and select **View pods & logs**.
4. Use the node filter or search fields to find the pod.
5. Click a pod card to open **Pod Logs:** for that pod.
6. If a pod has multiple containers, choose the needed **Container: ...** entry.
7. Select **100 lines**, **200 lines**, **500 lines**, or **1000 lines** to change the log tail length.
8. Turn **Previous** on if you need the previous container log.
9. Leave **Auto-refresh (5s)** enabled to keep the pod list and logs live.
10. Use **Filter log lines...** to narrow the log output, or click **Copy** to copy the current log text.

## Graceful shutdown defaults

Lens creates model-server Pods with a **120-second** termination grace period and a **5-second preStop delay**. vLLM containers also receive `--shutdown-timeout=90` when their invocation is a single recognizable `vllm serve` or `python -m vllm.entrypoints...` command (including `sh -c` scripts); compound shell scripts, unrecognized entrypoints and non-literal existing values are left unchanged with a deployment warning. During scale-down, rolling updates or node drains, Kubernetes removes the Pod from routing first; vLLM can then finish in-flight requests for up to 90 seconds before termination. Deployments created before these defaults were introduced must be restarted or recreated to receive them. SGLang does not support the vLLM flag, so only endpoint removal and the grace period apply. For P/D deployments, scale down decode before prefill. When a model container has a `--kv-transfer-config`, Lens sets `kv_load_failure_policy=recompute` in that JSON so Decode can recompute a failed Prefill KV transfer.

## Scale a deployment

1. In the deployment row, open the actions menu and select **Scale deployment**.
2. For a P/D deployment, set **Prefill replicas** and **Decode replicas**. For an aggregated deployment, set **Replicas**.
3. Click **Scale deployment**.

Manual scaling changes live Kubernetes model-server replicas only. Restarting the deployment restores its configured replica count. DisaggregatedSet deployments are created with the declared `spec.slices`; manual scaling changes role replicas and never changes `spec.slices`. For a P/D deployment, scale down Decode before Prefill; Prefill scale-down can interrupt in-flight KV transfers, but Lens configures `kv_load_failure_policy=recompute` whenever a `--kv-transfer-config` is present.

## Run a benchmark against a ready deployment

1. In a ready deployment's row, open the actions menu and select **Run benchmark**.
   The action requires the `evaluate:run:create` permission.
2. Choose a workload: **Short chat** (1,024 input / 256 output tokens at concurrency
   1, 8 and 32), **Long input, short output** (8,192 / 256 at 1, 8 and 16) or
   **High concurrency** (1,024 / 256 at 32, 64 and 128).
3. Optionally enter P95 TTFT and TPOT targets, then click **Start benchmark**.

The benchmark runs an in-cluster harness against this deployment through
`POST /api/v1/evaluate/runs` with its `deployment_execution_id`. You do not choose
Standalone or Gateway routing: the server targets the deployment's own router or, for
a deployment served through the shared Gateway, the Gateway. The deployment is not
changed. Lens opens the benchmark result page after the run is queued.

## Model inference access

Deployment sharing is no longer supported. Admin and maintainers manage
deployments within their cluster scope. Consumers do not get deployment pages
or direct deployment access; publish a model service and use its
[Manage access drawer](/user-guide/model-services#manage-model-access) to grant
inference to users or groups. Old deployment shares are not automatically
converted into model grants.

## Delete a deployment

1. In the deployment row, open the actions menu and select **Delete deployment**.
2. In **Delete deployment**, review **Execution ID**, **Cluster**, and **Namespace**.
3. Leave **Also delete the Kubernetes namespace** checked if you want Lens to remove the namespace and everything inside it, or clear it to remove only the deployment record.
4. In **Type `<phrase>` to confirm**, enter the exact confirmation phrase shown in the dialog.
5. Click **Delete deployment**.
6. If you do not want to continue, click **Cancel**.

## Configure and review Manual or Agentic plans

The deployment setup card is shown first: cluster, deployment name, model cache and
Pod placement. Lens preselects a ready cluster when available, generates the
deployment name and checks the selected model cache. All four fields are edited
directly in the card; a badge shows the model cache state. An unavailable model
cache offers **Prepare model cache**.
Then choose **Manual** or **Agentic** under **Planning mode**. **Workload & limits**
is always visible and optional; placeholders show the computed defaults (model
context length, all free accelerators, full-context KV sizing) and blank fields keep them.
**Reset to defaults** clears every override.
Neither mode asks for hardware specifications or a Guide before planning.

**Generate plan** (Manual) enables the checked core optimizations when compatible,
including Prefill / Decode separation, which is on by default and decided by AIC when a
request shape is given, and opens the reviewed
configuration. **Optimize for** offers Balanced, Low latency and
High throughput to both modes on the same entry screen: Manual uses it to choose the
topology, and Agentic also uses
it to rank optimizations. **Generate plan with AI** (Agentic) opens the generated plan
directly, with no intermediate questionnaire. Keep Balanced to continue without parameters. A restored plan preserves other supported objectives.
Agentic requires an AI provider; without one the Agentic option is disabled. If an AI
request fails, planning stops with the reason and **Use Manual plan** builds a Manual
plan from the same inputs. Neither path establishes a measured optimum.

Resource limits, workload, request sizes and latency targets are collapsed optional
sections. Both modes accept mean input/output tokens and P95 TTFT/TPOT SLA
targets; the **Load target** switch chooses concurrency or QPS (QPS is an Agentic input). Shared-prompt and long-input hints are inferred by
the AI from the goal and can be corrected after planning in Deployment settings. Manual also has an
**Optimizations** checklist; unchecked items become forbidden features. Blank inputs remain unspecified;
saved constraints remain visible when reopened.

The generated plan prominently retains **Manual plan** or **Agentic plan** alongside
the model and cluster. **Change setup** returns to the setup page; existing
backend plans remain saved under their original mode and target.
The **Serving flow** shows a horizontal Request → Endpoint selection → Prefill → Decode → Response path.
Combined serving places both compute phases inside one Model server boundary; P/D uses separate boundaries.
Cache indexing, KV cache, compute configuration and service management connect to the stages they affect.
These are logical processing and configuration relationships, not live traffic or measured placement.

Every functional group is visible, with configured counts and a short summary. Select a group to expand
its optimizations inside the diagram, including off and unavailable entries. Each group has its own pages
of up to four settings; expanding another group collapses the previous one. Select an optimization to open
its source, router or runtime parameters in a configuration drawer. **Stage parameters** inside an expanded group opens broader settings such as replicas, when declared by the source. Supported toggles and detailed editors
use the existing compatibility checks. Unavailable settings explain their status and remain read-only.
There is no separate Stage configuration table or global All settings visibility switch.
Apply edited parameters and check resources before reviewing deployment. Closing the drawer keeps unapplied
changes visible in the plan; discard them explicitly if needed. Narrow screens can scroll the diagram horizontally.
Each optimization has a colored status: Enabled, Required, Disabled, Conflict (cannot be combined with the
current selection or needs a prerequisite), Recipe setting (changed through recipe parameters) and Unavailable
(no deployable implementation in this source revision). Parameter lists are grouped by section and searchable.

While a plan builds, a stepped progress view replaces the partial plan. Each step
shows its elapsed time and an estimate (measured from earlier runs on this browser,
otherwise a default). Select a step to see what runs internally and the events it
reported. **Compose Guides and check resources** is usually the longest step: for
each candidate the server renders the pinned Guide sources with Kustomize, pulls and
templates their Helm charts, binds the model cache and checks devices and memory.
After it finishes, **Planning log** in the plan header reopens the same timeline.

Manual and Agentic are separate: a Manual plan has no Agentic entry. To use Agentic, go
back to setup and choose it under **Planning mode**; the previous plan is kept and can be
restored from the setup page. Recommendations still require resource checks
and explicit deployment confirmation; no performance result is implied.

The **Guides** tab in **Review & deploy** contains the complete
Guide index from the cluster's pinned llm-d revision.
Unavailable, external-operation and unadapted Guides retain their explanations:
being listed does not promise that a Guide or arbitrary combination can deploy.
Selected Guides expose their compatibility choices and source variables with
readable names, for example **Model server**, **Monitoring** and **Infrastructure provider**.
The flow includes independent prefix affinity and precise cache indexing.
The configuration drawer exposes only the selected node's source/router or runtime fields,
including per-replica native CPU cache capacity. Source variants remain editable.
The **Parameters** and **YAML** tabs edit the complete rendered configuration directly.
They open instantly from the reviewed snapshot; a server render is needed only after
the optimization selection changes.

Automatic additions retain each candidate's sized serving topology. Precise cache
indexing and flow control may replace the serving recipe because they keep the same
role shape; the sized replicas and TP are reapplied, and generation falls back to the
sized recipe if the replacement fails source checks. A prefill/decode change is
compared as a separate candidate or enabled explicitly in the editor, which then
sizes both roles. Inventory controller installation requires explicit selection.
Unsupported transport/cache combinations remain excluded without blocking compatible
alternatives; required user selections are never silently dropped.
The Router's narrowly scoped authentication RBAC is managed with the deployment
namespace. Cleanup also waits for these resources to be garbage-collected; an
ownership conflict is an error, never permission to replace an existing grant.

Manual enables every compatible source optimization without using workload benefit
as a gate, in a fixed priority: prefix caching, chunked prefill, prefix affinity,
load routing, precise cache indexing, CPU KV cache, flow control. When two are mutually
exclusive, the higher-priority one stays on and the other explains which optimization
blocks it; disable that one to switch. Explicit exclusions and edits are preserved.
External prerequisites, unresolved choices and resource checks still constrain
generation. Agentic enables only optimizations expected to help the selected
objective; other compatible ones remain available with that reason. Neither mode
installs external prerequisites automatically. A compatible optimization that is off
offers **Enable and edit parameters**. **Apply changes and check resources**
creates a new reviewed source snapshot; unapplied edits block deployment. Changing
selections preserves unrelated final parameter edits by reconciling them with the
newly rendered resources. Conflicting edits block application with an explicit
error instead of silently disappearing; undo the conflicting selection or use
**Discard direct edits** in the Parameters or YAML tab. Legacy snapshots without
an edit baseline require explicit resolution when their base configuration changes.
Disabling native CPU cache retains its capacity for re-enabling.
Enabling **CPU RAM cache offloading** on an existing serving plan, including P/D,
adds a native CPU cache to its workers while retaining its serving topology and
router. Use **Edit parameters** to review the capacity per replica before applying;
the editor uses the saved capacity or its default for a new cache. Explicitly disabled
prefix caching must be enabled first. Applying checks the selected source adapter,
runtime image and host-memory budget; unsupported combinations return their specific
validation error. Selecting two complete serving Guides still reports a conflict.
A changed source revision requires an
explicit decision to discard source edits and adopt the current revision.

Rejected numeric edits restore the last accepted value and display the validation error.
Clearing an explicit **Slices** count returns to automatic sizing while preserving total
Prefill and Decode replicas. A layout is **Recommended** only when both role counts,
slice count and placement policy match the recommendation.
Pod placement and target-node selectors are included before the source snapshot is reviewed;
selected-node capacity is checked rather than relying only on total cluster capacity.
A later placement change requires regenerating the reviewed configuration.
Source-plan evidence requires an identifiable source recipe and a representable CPU-cache
capacity; ambiguous recipes or differing role cache capacities are rejected rather than
treated as baseline/cache-free evidence. Prefix affinity is detected from mounted,
profile-referenced router configuration, and enabling it leaves Decode profiles unchanged.

A compact strip above the serving flow summarizes topology, accelerators, optimization
count and status. **Review & deploy** opens one dialog with **Overview**, **Parameters**
and **YAML** tabs. Overview shows accelerators, topology, cluster,
model cache, the optimizations enabled in the final YAML, checks, warnings and
**Confirm deployment**. Lens selects the **Inference Service** automatically, preferring gateway/router
Services over generic inference-model Services and excluding EPP control and metrics ports.
Equally ranked entries require an explicit choice; with a single choice it is shown read-only.
A Service named `epp` can still supply the HTTP entry on port 80 or 443;
change it only if needed. **Parameters** shows one card per Guide recipe (Guide-level variables
such as the model server; adding or removing Guides is under an advanced disclosure) and one card
per workload with only replicas, container images, resources, engine flags and environment
variable values, named by container and flag; everything else is edited in the YAML tab.
Edits in any tab must be applied and checked before
confirming; the dialog stays open while they are applied. Approval binds the
selected endpoint and exact configuration checksum and rechecks capacity; editing
does not provide a separate deploy path. Legacy saved plans expose **Load Guides
and build source configuration** and retain their old preview in a disclosure.
If the source catalog is unavailable, the error remains visible instead of
silently presenting legacy templates as a fully supported source composition.
The plan view shows the serving flow with a compact **Optimizations** panel floating in the diagram's
empty top-right area, so it never covers stages or reduces the diagram width. Each entry has a
settings button that opens its parameters in place. Select the
expand button to swap: the full table moves to the center and the flow becomes a corner thumbnail
(select it to swap back). The table lists every optimization with a checkbox; checking or
unchecking a supported switch rebuilds and rechecks the plan. Recipe-controlled settings such
as quantization and pipeline parallelism have disabled checkboxes; use their settings button
to edit the owning source configuration. Enabling or disabling a supported optimization in
the flow does the same, so the flow and the table stay in sync. Checked optimizations the plan does not apply
show a status and the reason on their row. The table also lists optimizations that come with the
Guide recipe (for example the token load scorer, or the KV transport used by Prefill / Decode
separation) with a short description; they are checked, configured and counted the same way.
Unchecking the KV transport turns off Prefill / Decode separation; other Guide optimizations are
toggled in the source flow and applied immediately.
Agentic plans also show **Plan**, **Alternatives** and **Benchmark tests** tabs. Alternatives compares reviewed source configurations and evidence.

For Agentic plans, **Benchmark tests** is a separate optional view. Prepare a
test-enabled plan there before selecting the workload and confirming tests.
Its accelerator ceiling starts from the planning constraint or discovered capacity;
unknown capacity requires an explicit value. Saved tests restore their recorded
workload and budget. The form checks required repetitions, resource ceilings and
numeric limits before submission. Interrupted or failed cleanup must be resolved
before starting more tests; submitted deployments cannot start another trial.
Trial evidence displays measured TTFT, TPOT, end-to-end latency, throughput and
error fraction, with missing values left unknown.
For source-backed plans, **Check all source candidates** renders each candidate
before testing, and each selected candidate requires its reviewed inference
Service. Cache variants must be edited and rendered in the Guide configuration;
tests do not silently add an unreviewed native-cache variant. Choosing a measured
winner restores its exact reviewed source configuration.

The budget includes **Winner confirmation repetitions** (default 1): after the
comparison, the leading candidate is redeployed and independently measured with
the same workload. Two candidates with two repetitions plus one confirmation
require five benchmark runs. A failed confirmation retains the comparison evidence
but does not establish a confirmed winner. The latency planning objective defaults
the test objective to lowest P95 end-to-end latency.

The accelerator figure is the planning snapshot (required / available), not reserved or
current capacity. Use **Recheck resources** before approval to refresh the reviewed snapshot;
approval also rechecks capacity.

### Verify optimization mechanisms

Guide availability, compatible configuration, runtime behavior and measured benefit
are distinct evidence levels. Unsupported combinations must retain their reasons;
enabling more flags is not evidence of better performance. Validate the pinned
source revision, runtime image, hardware and workload together.

| Mechanism | Required runtime evidence |
| --- | --- |
| Multi-replica routing | EPP processing, per-backend request counts and cache hits for shared-prefix traffic, followed by distinct-prefix load on both replicas. HTTP 200 alone is insufficient. |
| Prefill/decode separation | Both roles process requests and KV transfer metrics or correlated transfer logs increase. Exclude ordinary combined-serving fallback. |
| CPU KV readback | Write KV to CPU, evict only device KV in an isolated test, repeat the prefix and observe CPU-to-device transfer plus external cache hits. CPU writes alone do not prove readback. |

Prefer a bounded device KV budget and normal traffic for eviction tests. Do not
enable production development/RPC endpoints merely to reset a cache. Keep test
deployments isolated, record failures and clean up only their owned resources.

**Change workload & limits** shows the discovered capacity and current context setting
without inventing traffic values. Accelerator limits can change which combinations
fit; request sizes and concurrency refine capacity estimates; QPS and latency set
performance targets. Blank fields impose no additional constraint.
Use **Rebuild plan** to apply overrides. Manual has no redundant single **Plan** navigation button.
The current plan remains available until a replacement is
created; **Keep existing plan** returns to it. A new configuration revision requires
new review. **Back to edit** returns to the plan.
Use **Confirm deployment** to submit; a changed checksum requires a fresh review.
After confirmation, Lens opens the full Deployments list with the new job marked
**New**. Its status stays in progress until live Pods confirm readiness, so the list,
the summary cards and the status dot always agree. The **Degraded** card counts
deployments with fewer ready model-server Pods than requested.
A deployment is ready only when Deploy succeeds and every
component reports ready; planning status alone is not readiness. Workload
performance still requires measurement.

## DisaggregatedSet review

When a selected Guide supports DisaggregatedSet, configuration exposes the real API
fields: `spec.slices`, `spec.placementPolicy.type`/`.topology`, and **EPP Topology Affinity**
(`topology-affinity-scorer` or `topology-affinity-filter`).
Prefill and decode replicas are per Slice. The resource summary expands all Slices
and leader/worker Pods; TP is not treated as an accelerator resource count.

In both Deploy and Evaluation, P/D configuration always shows **Slice Configuration**
below the topology settings. Controls remain disabled until
the source is recognized as DS. Loading, preparation errors and a Guide without DS
are shown explicitly; **Recheck Slice support** repeats the official-source check, and
the header shows the pinned Guide commit.
Choosing P/D alone does not convert a Deployment-based Guide into a DisaggregatedSet.

Slice count and placement start from the Guide defaults; EPP Topology Affinity defaults to Scorer:

- **Max feasible** is estimated from current free resources for the selected
  placement policy: packing for `None`, domains that each fit one Slice for
  `ExclusiveSlice`, and such domains not used by another DisaggregatedSet for
  `ExclusiveTopology`. Before **Generate YAML** the estimate uses the Guide default roles;
  afterwards it uses the generated roles. It is not a reservation.
- **Recommended** appears only with matching evidence: succeeded Evaluation
  cases for the same model, Guide, cluster, accelerator and per-Slice P/D replicas and TP
  that recorded an SLO-stable rate. Enter a **Target load** to get the fewest Slices whose
  measured rate meets it within the current ceiling. When runs used different workloads or SLO
  targets, choose one under **Evidence**; runs are never mixed across them.
  Otherwise the panel shows
  `No verified recommendation — Guide default: N`. Throughput alone never selects a count.
- **Selected** multiply per-Slice requests by the selected Slice count, and the
  accelerator total checked before generation includes all Slices.
- **Placement** selects the placement type, picks the topology key from
  discovered node labels (or another key), and shows each domain's nodes, free
  accelerators and whether it fits a Slice. When the Guide requests accelerators
  through DRA claims, which the estimate does not count, domains show free CPU and
  memory instead and a note marks the ceilings as CPU, memory and Pod based only.
  Custom labels are marked because Lens cannot
  verify that they reflect physical topology; node labels are changed by orchestration
  administrators, not from this page. A discovered placement is offered as
  **Suggested**.
- **EPP Topology Affinity** offers **Scorer** and **Filter** only. Scorer adds a
  same-Slice score; Filter keeps same-Slice candidates when available. Missing peer
  topology or no matching candidate leaves all candidates eligible, so Filter is not
  a strict same-Slice guarantee. Unset or legacy inherited settings become Scorer
  when generating a configuration; an existing Filter selection is preserved.
- **Evaluation evidence** lists recent measured runs, marks those with the same per-Slice
  shape, and **Apply** copies a run's Slices, placement and P/D values.

Deploying a DS configuration runs preflight checks in the existing deployment flow,
without an additional review dialog. Passed checks proceed directly to deployment;
failures and unknown constraints appear inline under **Deployment checks**.
In Manual and Agentic plan review, **Confirm deployment** submits the plan when preflight finds a placement and no errors. Conditions outside the placement model remain advisory. Incomplete inventory or an inconclusive search still prompts **Accept risks and deploy**.
Its **Slice deployment preview**
shows selected versus feasible Slices, the roles per Slice, total accelerator requests,
placement, EPP routing and the modeled Slice-to-domain and Pod-to-node placement (the real
scheduler may choose other nodes). Check workload YAML, Router
values and checksums under **Deployment resources** when inspecting the preflight evidence. Failed constraints block
execution, including a Slice count with no feasible placement. An inconclusive result requires explicit acknowledgment. A feasible placement does not reserve resources or guarantee admission.
Changing cluster or deployment inputs requires another review. The final plan freezes
rendered inputs and Chart bytes; it does not install missing DS/LWS controllers or CRDs.
Official Guide snapshots require vendored Kustomize dependencies.

Local sources freeze referenced resources, patches, generator inputs and Router
values with a content checksum, not a claim that dirty files match Git HEAD.
Remote custom Kustomize sources render from an exact commit snapshot; external
dependencies and escaping paths must be vendored before planning.
For a stopped or failed independently deployed DS, the **restart-plan API** prepares
a new digest without deleting old resources. Confirm the new plan to start a new
run. Evaluation-owned deployments use the Evaluation workflow's retry action.

Evaluation automatically records a bounded inference probe before benchmarking a reviewed
DS deployment. In Evaluation details, open **Deployments** to inspect **Runtime verification**:
Kubernetes readiness, Slice placement, P/D routing and KV transfer have independent verdicts
and reasons. **Recorded evidence** exposes the captured Pod/Node and request evidence.
The deployment verification API also supports an explicit smoke request and read-only metric
snapshots. A metric snapshot is not a live rate. Slice count changes require a new reviewed configuration.
For instrumented vLLM 0.26.0 NIXL pull workers, it correlates the response ID with
receive completion and producer acknowledgements across all TP ranks, verifies
Pod/engine stability and P/D revision identity, and excludes transfer-failure fallback.
The report records actual P/D Pods, same-Slice/domain results and transferred block
counts. Reports persist as checksummed deployment evidence and remain visible after
reopening details. Unsupported versions/connectors or incomplete evidence remain unknown.
Ready Pods, HTTP success, same-Slice labels and aggregate KV counters are not proof of
request-specific transfer. Routing/KV results remain unknown without correlated evidence.
These checks do not certify physical network bandwidth or safe online rollout.

P/D deployments using Router 0.11 automatically adapt legacy plugin settings when
created or retried. The original configuration is retained, and deployment
diagnostics record the effective Router values. A legacy `disagg-headers-handler`
entry is replaced by the profile handler's built-in header handling; the saved
prefill/decode decision is preserved. A conflicting old and new decider setting
must be corrected before deployment.

## Hardware profiles and guide variants

Deployment rendering resolves hardware through the profile registry. The selected
profile supplies the runtime image, scheduling labels, accelerator resource request
and PCI-selection capability. Custom runtime images remain user-controlled; unknown
hardware does not silently select another vendor's defaults.

Guide variants come from actual Kustomization entry points in the selected llm-d
repository revision, including nested overlays. Changing hardware or source can
change the available variants. A listed overlay can still require cluster resources
such as NIC device classes, storage or runtime support; planning validates these
requirements before deployment.

Automatic generic entry selection prefers the root (`.`), then `base`. If neither
exists, deployment reports the Guide, hardware profile and available variants
instead of silently choosing a platform-specific overlay. Select a compatible
Guide source or explicitly choose a listed variant where supported.

Agentic tiered prefix cache requests native CPU caching without pinning the source
layout. Lens resolves `native/cpu` or `native/cpu/base` from the selected source and
accepts the legacy path. Missing native CPU entries produce an error; Lens never
substitutes another cache implementation, storage tier or platform overlay.

The deployment list cancels superseded filter requests so older results cannot replace the current selection. Cluster names are shown when available, with IDs as a fallback. Deletion still requires the displayed confirmation phrase and preserves the namespace choice; while deletion is pending, submission and dialog dismissal are disabled.

When specifying an operator preference for deployment planning, use English, such as
`prefer prefix cache`, `more GPU for performance`, or `use fewer GPU resources`.
The deterministic planner matches English preference keywords; Chinese keyword aliases
are no longer supported.

## Verify profile-driven Guide configuration

Choose a cluster with downloaded Software Versions and refresh the page. The
hardware profile selects the Guide source root; the selected llm-d checkout
supplies its model servers and Kustomization variants, including nested paths.
Root overlays display as `Default (vllm)` or `Default (vllm-rdma)` instead of `.`.
Selecting a sibling runtime variant remains stable while editing other fields.

For official sources, cache and NIC controls appear after source preparation:
CPU capacity requires a supported cache connector in the rendered containers;
NIC count requires a claim matching the profile's NIC device class. Inspect the
generated YAML and source provenance before deployment. Access-mode settings
come from `deployment.modes`; DRA uses a device claim and plugin mode uses the
declared extended resource. User-selected runtime images remain overrides.

In Evaluation results, open Resources during benchmark. Device allocation
failures display a reason even when engine metrics are available. Plugin device
metrics require kubelet-reported, profile-recognized device identities; an
exporter alone cannot establish which devices belong to the workload. Profile
file edits require restarting the development services and refreshing the page;
this is not a live JSON editor. Existing saved results are not recollected.

## Review a generated deployment

Manual uses the source-backed editor described above. Prefix caching and chunked
prefill can be explicitly excluded without inventing workload characteristics.
Completion only changes source-supported settings; unavailable options retain
their reasons in the Guide and optimization inventory. Explicit runtime controls
remain authoritative. Guide composition supports optimized baseline, precise routing, and NIXL P/D plus native CPU KV cache from the same pinned official source. Runtime images must match. P/D wraps the original NixlConnector first and OffloadingConnector second in MultiConnector on both Prefill and Decode, preserving transport settings and reserving local host memory per model pod. A same-image init container checks connector imports and configuration schemas before startup; it rejects the known vLLM 0.19.0 offloading defect (upstream issues #39500/#39617). This check does not establish GPU correctness or performance. Unsupported transports produce an adapter-specific error; arbitrary connector stacking is not supported. Composition alone does not prove optimal performance.

The P/D CPU-cache adapter currently requires `NixlConnector` with `kv_both` on both roles.
Sources using `kv_producer` and `kv_consumer` remain eligible for P/D without CPU KV offload;
only the added cache combination is rejected. Lens does not rewrite these transport roles or
silently remove an explicitly requested cache requirement.

Use node parameter actions or **All deployment parameters**, then **Apply changes
and check resources**. Manual and Agentic both preserve the reviewed source bundle;
the editor does not silently send parameter changes to an LLM or substitute another
candidate. Explicitly rebuilding workload requirements requests a new recommendation.
Selecting an alternative is not deployment; **Review & deploy** still requires confirmation.

## Measure and compare Agentic candidates

Open **Verify with real benchmarks**, select candidates, set the GPU ceiling,
maximum minutes, benchmark-run budget and repetitions, then choose throughput,
P95 end-to-end latency or throughput per accelerator as the objective. Source-backed
candidates require reviewed inference Services and rendered cache variants. Only
legacy plans retain the optional CPU-cache budget that adds trial variants; include
those repetitions in their budget. Synthetic load starts from the plan's mean input/output lengths and concurrency;
missing values default to 512 input tokens, 128 output tokens and concurrency 4,
with 100 requests. A restored test uses its recorded workload. Expand
**Test workload** to change these values or supply representative inference-perf
YAML, such as a shared-prefix workload for cache experiments.

**Start deployment and benchmark tests** provisions actual cluster resources.
Each candidate is deployed, tested with the same workload and cleaned up before
the next candidate. Complete repetitions must satisfy every configured latency
SLO and the error limit. Missing metrics and failed trials never count as proof
of superiority. Results include benchmark IDs and a ranking of completed trials;
review the best measured candidate before confirming its final deployment.

Use **Stop and clean up** to cancel. Cleanup may outlast the measurement budget;
a cleanup failure blocks further deployment until resolved. Progress is audited
with the candidate configuration and workload. After a service interruption,
the recorded test task is marked interrupted and offers explicit cleanup; it
never automatically resumes deployment. Browser refresh restores the current
plan in the same session. This is bounded candidate search, not an unbounded
self-modifying optimization loop or a claim of global optimality.

The Overview and 3D tabs show each role’s transport and local CPU cache separately. Agentic CPU-cache trials include eligible P/D candidates and compare them with their original configuration using the same workload. The default NIXL-first order prioritizes transport when multiple connectors report a hit; it does not guarantee fewer network transfers. Confirm workload correctness and performance with real measurements.

## Non-Admin (`edit`) cluster deployment planning

When a cluster uses a namespace-scoped Non-Admin (`edit`) kubeconfig, cluster-wide Kubernetes inventory reads (`kubectl get nodes`, `kubectl get pods --all-namespaces`) may return `403 Forbidden`. During deployment planning, slice placement, and target checks, Lens automatically falls back to Prometheus-synthesized node and allocatable accelerator inventory so hardware-profile-driven GPU/XPU scheduling and capacity checks continue without `403` failures. Real `401 Unauthorized` kubeconfig errors are never masked and are surfaced immediately so you can refresh or replace the cluster credentials.

## Per-Namespace Preflight & Orchestration Administrator Namespace Setup

Each deployment targets its own dedicated Kubernetes namespace (`<deployment-ns>`). Before deploying, Lens runs a per-namespace SubjectAccessReview (SSAR) preflight check:

- **Admin kubeconfig**: When all required namespace, workload, and RBAC checks pass, deployment proceeds directly with no extra steps.
- **Non-Admin (`edit`) kubeconfig**: If `<deployment-ns>` or its namespace-scoped RBAC is missing, Lens pauses at **Orchestration administrator namespace setup** and generates a self-contained, idempotent bash bootstrap script (with zero plaintext secrets).
  1. Download or copy the bootstrap script and have an orchestration administrator run it. The script creates the `Namespace`, a namespace-scoped `Role` and `RoleBinding` for the detected kubeconfig identity (or an explicit subject override if auto-detection is unavailable), the per-namespace EPP `system:auth-delegator` `ClusterRoleBinding`, an optional static `PersistentVolume` and bound `PersistentVolumeClaim` when storage is configured, and a non-secret `lens-deployment-bootstrap` marker `ConfigMap`.
  2. Click **Re-check & Deploy** to verify the bootstrap marker and permissions.
  3. Once verified, Lens deploys the workloads into `<deployment-ns>`, copies `HF_TOKEN` from `hf_token_secret_namespace` if configured, and enables namespace-scoped `ServiceMonitor`/`PodMonitor` resources.

## Two-Phase Deployment Deletion on Non-Admin clusters

Deleting a deployment on a Non-Admin (`edit`) cluster uses a two-phase flow:

1. Lens first deletes all in-namespace workload and configuration resources inside `<deployment-ns>`.
2. If deleting the `Namespace` or its per-namespace `ClusterRoleBinding` returns `403 Forbidden`, Lens presents the **Orchestration administrator namespace cleanup** handoff. Download or copy the generated cleanup script for an orchestration administrator to run, then click **Re-check & Delete** to confirm removal and delete the Lens deployment record. (If marker verification is unavailable, **Confirm & Delete Record** removes the Lens record after manual cleanup.)

## Related references

In the deployment creation flow, expand **Why this option** under a validated alternative to see its AISimulate TTFT, TPOT, and throughput estimate when an exact-topology estimate is available. The estimate can appear even when the AISimulate candidate search finds no configuration satisfying the original SLO; in that case, the alternative still shows **SLO not met**. The **AI score** shown beside an agentic candidate is a relative ranking score out of 100; the highest-scoring candidate is normalized to 100. It is not a benchmark result, confidence level, or probability of meeting the SLO. A deterministic fallback shows **Deterministic score** instead.

**Recalculate selection** works without an AI provider. It refreshes the recommendation
using deterministic planning and the new preference; if AI scoring fails, the
alternatives also retain deterministic scores.

Agentic alternatives are checked using the selected vLLM GPU memory utilization
and max model length. The same values are applied when the deployment starts;
actual free KV cache is measured by vLLM at startup and may still be lower than
the planning estimate.
