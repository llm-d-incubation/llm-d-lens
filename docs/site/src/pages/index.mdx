## Three ways to use Lens

<CardGroup cols={3}>
  <Card title="Web GUI" icon="server" href="/quickstart">
    Browser console served by the unified Python backend (<code>llm_d_lens</code>) for multi-cluster governance, visual planning, Model Catalog, Evaluation, Trace Replayer, Model Services, Observability, and Lens Assistant.
  </Card>
  <Card title="Standalone llmd CLI" icon="rocket" href="/cli-reference">
    Pure-Python 3.11+ &amp; PyYAML client (<code>apps/lens</code>) for cluster-admin-free, namespace-scoped GitOps directly against Kubernetes/OpenShift — zero Lens server, database, or Node required (<code>llmd</code> is the full CLI; <code>lens</code> is a version/help stub).
  </Card>
  <Card title="Agent Tools via MCP" icon="bolt-lightning" href="/mcp">
    Stateless Streamable HTTP endpoint (<code>POST /api/mcp</code>, <code>Bearer lens-pat-*</code>) exposing 46 task tools across 6 profiles for <code>opencode</code>, Claude Code, Cursor, and Codex, separate from internal <code>/api/assistant/mcp</code>.
  </Card>
</CardGroup>

## Highlights

<CardGroup cols={2}>
  <Card title="Optimal performance" icon="bolt-lightning">
    Deployments run on llm-d: prefill/decode disaggregation, KV-cache-aware
    routing, KV cache offloading to CPU/SSD tiers, and latency-predicted
    routing raise throughput and cut tail latency on the same GPUs.
  </Card>
  <Card title="Multi-cluster deployment" icon="server">
    Plan, approve and execute inference deployments across Kubernetes clusters
    from a single UI, CLI, or MCP agent workflow, with agentic, workload-guided placement.
  </Card>
  <Card title="Guided evaluation" icon="chart-line">
    Design benchmark experiments, run them against live deployments, and
    analyze and export the results without hand-written scripts.
  </Card>
  <Card title="Trace Replayer" icon="flask">
    Replay registered request traces against an inference endpoint to validate
    behavior and capacity before real traffic arrives.
  </Card>
  <Card title="Model Service gateway" icon="route">
    Publish cluster deployments as OpenAI- and Anthropic-compatible model services
    behind the cluster-local shared Gateway (HTTPRoute / IPP → EPP → InferencePool),
    with <code>lens-authz</code> and per-model selection policies.
  </Card>
  <Card title="Governance built in" icon="shield-check">
    Role-based access control, per-cluster scoping and audit logging apply
    across every UI page, REST route, and <code>/api/mcp</code> tool call.
  </Card>
  <Card title="Observability" icon="gauge-high">
    Bootstrap and maintain the cluster monitoring stack (Prometheus/Grafana) to
    watch GPU utilization and deployment health.
  </Card>

## Architecture

<img src={useBaseUrl('/img/home-3-7d83bcc33b.png')} alt="Lens system architecture" width="100%" />

A single unified Python FastAPI backend (<code>apps/backend</code>, <code>llm_d_lens</code>)
manages any number of Kubernetes clusters, on-premises or in the cloud, from one
control plane: it serves the built Web UI (<code>apps/frontend</code>), REST API,
RBAC and audit enforcement, the external Agent Task MCP endpoint (<code>/api/mcp</code>),
and the internal assistant catalog (<code>/api/assistant/mcp</code>), while persisting
state in PostgreSQL and provisioning clusters, storage, and cluster-local Shared
Gateways directly. For server-free, namespace-scoped workflows, the standalone{' '}
<code>llmd</code> CLI (<code>apps/lens</code>) talks directly to Kubernetes, while
model clients call published gateways with <code>Bearer lens-mk-*</code>.
